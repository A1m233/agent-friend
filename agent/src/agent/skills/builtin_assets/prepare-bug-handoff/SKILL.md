# 准备问题交接

## 目的

把已有调查证据整理成简洁的交接材料，使接收方开发者无需重复整个调查，就能验证结论、复现症状并采取下一步行动。

本 skill 仅限显式触发。诊断结果恰好跨越模块边界，并不授权或要求进行交接。

## 区分交接类型

- 交接给前端、后端、宿主、Engine、服务或其他模块 owner：使用本 skill。
- 把进行中的 feature-delivery 会话转交给另一个 coding agent：改用 `agent-handoff`。

## 输入

使用对话和工作区中已经存在的证据：

- 已观察行为和预期行为；
- 复现步骤或触发条件；
- 日志、运行时数据、截图或测试；
- 已追踪的数据/调用边界；
- 已确认和已排除的假设；
- 证据基础和重要证据缺口；
- 根因置信度；
- 代码锚点和建议 owner。

不要重新运行强制性的端到端诊断。需要验证代码锚点或避免误导性主张时，执行小范围只读检查。如果调查尚未完成，在交接中保留这种不确定性，不要编造确定的 owner 或根因。

## 提问门槛

仅询问会实质改变接收方或交接产物的信息：

- 仅当无法推断目标模块，且不同接收方需要显著不同的内容时，才询问应交给谁。
- 仅当用户要求保存文件却未提供可用目标位置时，才询问文件位置。
- 其他情况下，默认直接在对话中返回可粘贴使用的 Markdown。

当交接可以用中立的模块术语表达时，不要要求用户判断“是哪一方的问题”。

## 工作流

### 1. 验证证据完整性

区分：

- 直接观察到的事实；
- 有代码支持的推断；
- 未经测试的假设；
- 缺失的证据。

检查时间戳、环境、代码版本和日志来源是否与所报告事件匹配。除非日志保证会生成并持久化，否则不要把日志缺失当作证明。

### 2. 确定接收边界

指出最早出现已知错误行为的边界，以及最有能力验证或修改它的模块。使用与证据强度相称的措辞：

- 归属得到强证据支持时，使用“证据指向”；
- 仅在有决定性证据时，使用“已确认位于”；
- 失败边界仍未知时，使用“owner 尚未确定”。

责任归属仍由 maintainer 或团队决定；交接材料只呈现技术证据。

### 3. 构建交接产物

生成完整交接前，阅读 [references/handoff-template.md](references/handoff-template.md)。只保留当前案例有证据支持的章节。

交接材料必须：

- 包含 AI 辅助生成声明；
- 以简短的 TL;DR 开头；
- 让复现步骤和证据易于浏览；
- 区分事实和推断，说明证据基础和置信度；
- 在可用时提供精确的文件、符号或日志锚点；
- 为接收方开发者提供具体的验证路径；
- 如有临时诊断观测代码，记录它们并给出移除或保留建议。

不要包含私有思维链。只包含对验证有帮助的简洁调查历史，例如已经测试的假设及结果。

### 4. 在不产生无关变更的前提下交付

除非用户要求保存，否则在对话中返回 Markdown。如果保存到工程化的 `docs/` 目录树下，遵循该仓库的文档规则和确认流程。准备交接时不要修改业务代码。

交付后，说明建议接收模块；如果仍有未解决风险，同时指出其中最重要的一项。

## 质量门槛

交付前验证：

- 本 skill 是用户明确请求的；
- 接收边界有证据支持，或已经清楚标为未解决；
- 每项根因主张都有对应证据；
- 可获得时，复现步骤最小且可执行；
- 置信度和缺失证据清晰可见；
- 已根据当前工作区检查路径和行号锚点；
- 没有把仅要求诊断的 prompt 转化为用户未请求的交接。

# 问题诊断

## 目的

确定正在发生什么、最早从哪里开始出错，以及证据对根因的支持程度。在向用户索取更多上下文前，先安全地推进只读调查。

## 协作契约

- 提问前先消化对话、工作区、截图、日志和环境上下文。
- 不要把检查清单变成信息采集表。仅当缺失答案无法从现有证据取得、会实质改变下一步行动且不能安全假设时，才提问。
- 非阻塞细节尚不明确时，继续进行有价值的只读调查，并说明重要假设。
- 区分信息请求和行动授权。仅在执行确实需要授权的动作前请求授权，例如修改诊断代码、变更真实系统、收集私有数据、对外协调或发起高成本调用。
- 调查深度与问题相称。本地格式问题可能只需追踪一条数据流；分布式故障可能需要跨多个边界检查日志。
- 把日志查询请求视为证据收集。当证据不足以支持根因结论时，只报告匹配结果和局限，不强行下结论。
- 默认把诊断视为只读工作。除非用户明确要求修改或修复代码，否则不实施修复。

## 工作流

### 1. 界定症状

从现有上下文提取：

- 已观察到的行为；
- 预期行为；
- 已知时，受影响的环境和范围；
- 已知时，复现方式或时间戳。

不要让用户重复已经提供的信息。如果症状已经足够明确，就直接开始调查。

对于涉及数据丢失、安全暴露或级联故障的进行中事故，在根因调查前先识别止损需求。没有所需授权时，不执行止损动作。

### 2. 建立事实基线

沿着从可见症状到权威事实源的最短相关路径追踪。根据问题检查：

- 渲染或输出格式；
- 状态、store 和 API 边界；
- 持久化字段和时间戳；
- 配置和环境；
- 日志、trace 和运行时快照；
- 测试和近期相关变更。

在每个边界记录输入、转换和输出。找出最后一个已知正确点和第一个已知错误点。优先采用直接证据，而不是命名、注释或直觉。

涉及日志或 trace 标识符时：

- 使用用户提供的路径前，先从项目自身的规则、文档、路径辅助工具或运行时配置解析日志位置。不要维护或推断跨项目的绝对路径注册表。
- 解读前确认具体文件或数据流存在，并检查大小、修改时间、时间覆盖范围和轮转情况。明确指出过期或不完整的证据。
- 先搜索精确标识符，再检查附近事件、阶段关键词、错误和相关时间窗口。对于大型日志，先从狭窄的近期范围开始，仅在需要时扩展。
- 对不透明标识符优先使用固定字符串搜索，并在结果中保留路径来源、查询范围、搜索模式和匹配事件。

### 3. 建立或收紧反馈回路

需要主动检查时，定义能够捕获所报症状或区分现存假设的精确信号。构建新验证装置前，优先使用现有测试、查询、脚本、trace 查询或对比方式。

确实需要主动复现时，选择能够经过可疑边界的最低成本入口。默认优先级是：已有专项测试、脚本或 application root，现有 CLI/API/operation，基于稳定应用边界的最小临时脚本，浏览器。程序化入口已经经过同一业务、模型、持久化或可观测性边界时，不得仅以“更接近用户操作”为由改用浏览器。

只有可疑边界属于浏览器交互或展示、非浏览器入口缺少必要能力，或用户明确要求检查 UI 时才使用浏览器。选择浏览器前，记录可疑边界以及更高优先级入口为什么不足；无法指出具体缺口时，不进入浏览器路径。

有效的反馈回路应当：

- **具体**：检查用户的症状或有争议的边界，而不只是检查命令是否完成；
- **可重复**：重复运行能得到稳定结论，或已经测出间歇性故障的复现率；
- **相称**：在问题允许的范围内尽量聚焦且快速；
- **可运行**：agent 可以安全地重复执行，或明确写出所需人工步骤和应捕获的结果。

至少运行一次选定检查，并保留命令或查询、范围、信号和结论。如果缩减案例有助于区分假设，再进行缩减：

- 缩减输入和状态；
- 隔离一个组件或边界；
- 对比正常案例和失败案例；
- 在能够如实代表该行为时使用聚焦测试。

当静态证明、持久化数据或现有运行时证据已经回答问题时，不要把可运行复现设为强制门槛。如果无法建立充分的反馈回路，说明已经尝试的内容，并明确下一步所需的具体产物、访问权限或观察结果，不要越过证据继续推测。

### 4. 形成排序后的假设

只提出证据足以支撑的假设数量。按可能性、区分能力、验证成本和风险排序。

对每个假设说明：

- 它为何符合现有观察；
- 它预测会出现什么新观察；
- 能够支持或证伪它的最低成本安全检查。

避免强制使用“我方 / 对方 / 未知”之类分类。模块归属应当是根据失败边界得出的结论，而不是开始诊断所需的输入。

### 5. 执行区分性检查

优先选择能一次区分多个假设的检查。从只读、低风险检查开始，仅在需要时升级。

- 同时保留支持和反驳假设的证据。
- 仅当该路径保证会产生日志并持久化时，才把日志缺失视为证据。
- 考虑缓存、过期文件、时区、feature flag、并发和环境差异等混杂因素。
- 把每个临时探针映射到它能区分的预测，并且每次只改变一个变量。
- 如果调试器、REPL 检查或现有遥测能够回答问题，优先使用它们，而不是新增观测代码。
- 为临时日志或探针添加唯一且可搜索的标记，记录添加位置，并在使用后移除；除非保留它们有明确理由且已经获得授权。

如果当前可观测性不足，明确缺少的具体证据及获取它的最小方式。添加日志或探针前，告知用户将改动哪些文件或节点、会捕获什么、持久化到哪里，以及后续是否应移除。获得授权后再编辑。

### 6. 证据分类与结论

分别标注证据基础和结论置信度。证据基础标签可以同时使用：

- **code-supported**：已检查的源码或测试支持所提出的机制，但仅凭这些不能证明所观察事件执行了该版本或路径；
- **runtime-supported**：与该事件绑定的运行时产物支持该主张，但仅凭它不能证明是哪份已检查源码或配置造成了结果；
- **reproduction-supported**：可重复检查复现了完全相同的症状，或决定性的反事实按预测改变了结论。

单独记录重要证据缺口：

- **observability-gap**：所需运行时产物未生成、未保留、不可访问或无法归属；
- **runtime-identity-gap**：无法把该事件绑定到实际执行的构建、配置或源码版本；
- **reproduction-gap**：没有足够精确或可重复的反馈信号。

然后标注结论置信度：

- **confirmed**：该主张已由决定性证据证明，例如静态证明、精确复现或反事实，或具备所需身份绑定的“运行时到机制”证据链；
- **strongly supported**：各类证据形成一致链路，且备选解释已显著收窄，但仍缺少一个决定性环节；
- **unconfirmed**：仍存在合理假设，并已指出缺少的具体证据。

同一次诊断中的不同主张可以有不同分类。例如，运行时证据可能确认发生了什么，但由于运行时身份尚未确定，源码层面的原因仍只能标为 `code-supported`。

报告以下内容：

1. 根因或当前最佳解释；
2. 证据及相关代码/数据锚点；
3. 证据基础和重要证据缺口；
4. 置信度；
5. 受影响范围及可能的相邻影响；
6. 最小修复方向，但不执行编辑；
7. 剩余不确定性或下一步所需证据。

如果用户明确要求把结果交接给其他模块或团队，使用 `prepare-bug-handoff`。不要仅仅因为根因跨越模块边界就触发交接。

## 停止条件

当只读调查已经无法取得有意义的进展，并且某个答案确实构成阻塞时，暂停并提出一个简洁问题。典型阻塞包括缺失的私有运行时产物、只有用户才能执行且无法复现的操作，或会让调查进入实质不同路径的歧义。

不要仅根据症状措辞断言模块级根因。证据不足时明确说明，并指出能够区分剩余假设的观察结果。

# 076 · 完善模型请求的 Retry-After 长冷却恢复

- **状态**：open
- **严重度**：medium
- **发现日期**：2026-10-14
- **重新登记日期**：2026-11-25
- **关联需求**：无

## 现象

2026-10-14 的定时日常在读取技能后遇到模型传输错误。中转服务首次返回 500，随后连续返回 503；后续请求未再次到达上游，而是在中转服务内被判定为没有可用认证。该次响应没有 Retry-After，既有短退避在中转冷却结束前耗尽。

当前先将普通网络／临时服务错误的默认退避调整为 2、4、8、16、32、64 秒；本 issue 保留后续按服务端等待提示协调恢复的优化，不记录为本次已实施功能。

## 根因初判

AF 已在 `llm_providers/src/llm_providers/error_normalization.py` 解析 Retry-After 的秒数或 HTTP 日期，`client.py` 也会使用解析后的等待时间，并非完全缺少支持。

现有逻辑将超过 `engine_overload_max_retry_delay_seconds`（默认 30 秒）的服务端等待提示作为停止自动重试的条件。它避免提前重试，但不能在当前模型调用内等待较长冷却后继续；等待边界尚未针对交互和后台任务作进一步区分。

本次上游协议错误的根因仍未确认，不能把这项优化描述成修复协议错误。服务端未提供 Retry-After 时，AF 也无法准确获知内部冷却截止时间。

## 影响与判断

暂时不可用时间较长时，任务可能在服务恢复前结束。延长指数退避只能缓解部分场景，不能代替明确的服务端提示与客户端等待预算。

按用户决定，本次保留现有 Retry-After 行为，不修改中转服务；后续单独评估长冷却恢复。

## 可选修复方向

- 在现有解析能力上评估长冷却提示与任务等待预算的协调，保留取消能力和有界重试。
- 评估将提示保存为重试截止时间，避免跨层传递时重复开始倒计时。
- 覆盖秒数、HTTP 日期、缺失／无效提示、超出预算和等待中取消的确定性测试；避免因恢复模型请求而重复执行业务工具。
- 服务端未提供等待提示的情况继续使用本地退避；中转服务的提示能力属于独立后续工作。

# 051 · 上下文压缩期间桌面端与 IM 缺少明确进度提示

- **状态**：open
- **严重度**：medium
- **发现日期**：2026-08-18
- **关联需求**：[063-context-compaction-reliability](../../requirements/063-context-compaction-reliability/)、[022-im-channel-and-qq-adapter](../../requirements/022-im-channel-and-qq-adapter/)

## 现象

长会话在发送新消息后，运行时可能先进行耗时较长的上下文构建与压缩，之后才真正向模型发起请求。在这段时间里：

- 桌面端只有通用的等待动画或“等待模型响应”状态，没有说明正在整理长对话；
- IM（已在 QQ 私聊观察到）在首段回复产生前没有可见进度，用户看到的效果是 Bot 长时间没有反应。

2026-08-18 的一次真实 QQ 回合中，入站消息于 12:55:48 进入运行时，上下文构建耗时约 88.8 秒；日志确认本轮执行了新的上下文压缩，模型请求在压缩完成后才开始，首个用户可见回复约在 12:57:40 出现。该等待不是 QQ 断线，也不是模型已经开始输出后流式更新失败。

## 根因初判

当前上下文构建与压缩发生在首个模型运行状态事件之前：运行时先完成 `prepare_first_turn()`，随后才进入可向上层投影的模型等待、推理和工具阶段。

因此，桌面端在压缩期间只能展示缺少语义的占位状态；IM 适配器主要消费模型生成后的文本流，更无法在模型请求前解释当前正在进行的工作。系统缺少一个可被不同交互表面稳定消费的“正在准备 / 压缩上下文”运行阶段。

## 影响与判断

- 长会话越容易触发压缩，用户越容易误以为桌面端或 IM 已卡死、断线或漏收消息。
- 用户可能重复发送消息、重启应用或另开会话，进一步增加运行状态与对话连续性的复杂度。
- 当前没有数据丢失或错误执行证据；等待结束后回合仍能继续，因此本 issue 暂不修复。
- 本问题与“模型请求已开始但长时间没有 token”以及“QQ 原生流停留在单个圆点”是不同阶段的问题，不应共用含糊的兜底文案掩盖。

## 可选修复方向

- 在上下文准备开始时就发布稳定的运行阶段，例如 `preparing_context`；实际进入压缩时可进一步标记为 `compacting_context`。
- 桌面端将该阶段明确呈现为“正在整理这段较长的对话……”一类用户可理解的提示，并在进入模型等待、推理、工具或终态时可靠清除或切换。
- IM 在确认压缩会产生明显等待时尽早发送受控的进度提示；需限制频率并避免每轮普通上下文构建都发送额外消息。
- 为桌面端和 IM 分别增加确定性测试，覆盖阶段开始、阶段切换、失败、取消以及终态清理，避免提示残留或重复发送。

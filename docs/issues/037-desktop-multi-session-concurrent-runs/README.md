# 037 · 桌面对话缺少完整的多会话并发运行态

- **状态**：open
- **严重度**：medium
- **发现日期**：2026-07-25
- **关联需求**：045-agent-runtime-unified-execution

## 现象

桌面对话在某个会话仍在流式生成时切换到其他会话，会主动停止原会话的请求和运行。用户无法让一个会话在后台继续生成，也无法在原会话生成期间到另一个会话发起新的对话。

现有诊断已确认：前端使用单一全局 `streaming` 状态和单一全局 `AbortController`；`openSession` / `newSession` 在生成期间会调用 `stop()`。因此会话导航目前同时承担了取消运行的语义。

## 根因初判

后端 `AgentRuntime` 已实现“同 session 串行、跨 session 有界并发”，默认允许多个 session 在 worker 上并行运行；缺口主要位于桌面前端及流连接生命周期：

- 当前消息、流式状态和停止控制器都由单一活动会话独占，没有按 session 保存运行态。
- 流事件闭包直接更新当前页面的消息列表，切换会话后无法安全地继续消费原会话事件。
- 全局 busy 状态会阻止用户在另一个 session 发起新 run。
- 当前 AG-UI HTTP consumer 与后端 run 生命周期绑定；连接被丢弃时会以 `consumer_abandoned` 取消运行，尚不支持断线后重新订阅。

## 影响与判断

用户必须等待当前回复结束后才能安全切换会话；误切会话还会中断生成，影响桌面对话的基本连续性。等待当前 run 完成可以规避，因此严重度记为 medium。

该问题不适合通过删除一次 `stop()` 调用临场修补：这会留下跨会话消息写入、全局 busy 被旧 run 覆盖、停止错对象等竞态。后续应开独立需求，明确应用存活期间的多会话并发范围、独立停止语义、后台完成提示，以及是否支持刷新或断线后重新订阅。

## 可选修复方向

- 前端建立按 session 索引的 run registry，分别持有 controller、状态和当前 run ID。
- 流事件按 session 路由；非当前会话只更新该 session 的后台状态，返回时从持久化详情恢复消息。
- 将发送、停止和 busy 判断收敛为 session 级语义，并在会话列表展示生成中 / 已完成状态。
- 第一阶段仅保证应用进程存活期间的多会话并发；跨刷新、断网和重启的 detached run / 重新订阅能力另行评估。
- 保留后端同 session 串行边界，并补桌面前端到 AG-UI 的跨 session 并发集成测试。

# 059 · 用户桌宠模型改名缺少实时生效路径与 Guide 指引

- **状态**：open
- **严重度**：medium
- **发现日期**：2026-09-04
- **关联需求**：056-desktop-avatar-model-import-and-scaling

## 现象

用户导入 Ark-Models Spine 3.8 模型后，模型列表可能显示安装目录生成的技术名称，例如 `4235_thumpy`，但当前产品没有正式的用户模型改名入口。

一次真实诊断会话中，Agent 为把该名称改成“明日方舟 珊比”，直接修改了根目录的 `catalog.json`。该文件是运行时根据已验证模型状态重新生成的目录，不是用户模型名称的权威来源；当前运行实例也不会因这次外部写入自动更新内存状态或发出 catalog 变更事件，因此 Agent 虽然报告“修改成功”，实际没有取得界面生效证据，后续扫描或校验仍可能恢复旧名称。

模型目录内的 `agent-friend.model.json` sidecar 才保存稳定模型 ID 与名称。但是，仅修改 sidecar 的名称不会改变模型内容 revision；当前导入协调器按 `模型 ID + 内容 revision` 去重，已处理过的模型不会因名称变化重新完成验证和发布，通常需要重启应用才能让名称稳定进入已验证 catalog。

公开 `agent-friend-guide` 的 `arknights-avatar-models.md` 只说明安装后名称来自安装目录，并未覆盖以下内容：

- 用户想修改模型展示名时应走什么受支持路径；
- sidecar 与根 `catalog.json` 的职责边界；
- 不应把直接修改派生 catalog 当成持久改名；
- 当前不支持无重启改名时，Agent 应明确说明限制，而不是猜测内部文件并宣称成功。

## 根因初判

- 产品没有修改用户模型展示名的正式 command、设置入口或原子状态更新流程。
- sidecar 名称没有参与候选模型的 revision / generation 判定；名称单独变化时，扫描结果虽可变化，但已经按 `模型 ID + 内容 revision` 去重的导入协调器不会重新发布 validated entry。
- 根 `catalog.json` 同时承担可重建导入索引、校验缓存与 last-known-good 状态，但没有面向用户或 Agent 的可写契约；直接编辑它无法同步当前运行时状态。
- Guide 没有覆盖改名任务，也没有把 sidecar、catalog 和实时生效边界说明清楚，导致 Agent 从文件表象推断错误的修改目标。

## 影响与判断

用户模型仍可正常加载和使用，但模型列表会暴露技术 slug，用户无法在不中断应用的情况下改成可读名称。需要重启才能完成纯展示元数据修改，与桌面端应有的即时反馈不相称，也容易让 Agent 修改错误文件、留下无效备份或作出未经验证的完成声明。

需求 056 明确不包含应用内模型重命名，但已经要求运行期间自动感知用户模型目录的重命名和修改。本问题是该能力之外新增暴露出的模型展示元数据管理缺口，暂不在本次诊断中扩大为生产代码修复；正式处理需要同时设计后端状态更新、跨窗口事件、UI 或 Agent 操作入口以及 Guide 发布，故登记为 `medium`。

## 可选修复方向

1. 增加以稳定模型 ID 为目标的用户模型重命名 command，校验并规范化新名称后，原子更新 sidecar、候选快照、validated state 和派生 catalog。
2. 改名只更新展示元数据，不改变模型 ID、内容 revision、当前选择、按模型缩放设置或资源缓存；成功后立即发送 catalog 变更事件，使设置窗口和桌宠窗口无需重启即可同步。
3. 为名称单独变化补充确定性测试，覆盖运行中改名、重启后持久化、目录同时重命名、当前已选模型、失败回滚及跨窗口刷新。
4. 根据最终产品入口更新 `agent-friend-guide` 的模型安装 reference 和路由：说明如何改名、何时生效、失败时怎么办，并明确禁止直接修改根 `catalog.json`。
5. 在正式能力落地前，Guide 应坦率标注当前不支持无重启改名；不要把内部文件修改包装成稳定用户流程。

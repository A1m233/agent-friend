# 056 · Scheduled Tasks 的桌面信息架构与 Run 交互尚未确定

- **状态**：open
- **严重度**：low
- **发现日期**：2026-08-23
- **关联需求**：099-global-scheduled-agent-jobs

## 现象

需求 099 已决定本期只交付 Scheduled Agent Task 的后端调度、持久化、执行和查询边界，不实现任何前端或桌面 UI。产品因此暂时没有已确认的 Scheduled Tasks 管理入口，也没有确定 task、occurrence/run 与 Agent 对话在桌面端如何组织。

目前只有以下初步方向，均未形成产品决策：

- Scheduled Tasks 可能在左侧边栏拥有独立入口，与“对话”处于同一层级；
- Scheduled Tasks 内部可能采用 `Task → Run` 两层结构；
- 点击某次 run 后，可能进入一个 Agent 对话视图；
- 进入该 run 后是否允许用户继续对话，以及继续内容是否影响后续周期执行，尚未确定。

## 根因初判

这不是已实现功能的回归，而是需求拆期后有意保留的产品与架构设计缺口。若把 Scheduled Tasks 作为左侧顶层工作区，现有前端导航、会话模块、路由、状态所有权和列表查询边界可能需要调整；当前尚未完成影响分析，不能据此直接认定必须重构，也不应提前把某种层级或交互固化进 099 的后端实现。

## 影响与判断

- 不阻塞 099 的后端调度能力；本期可通过自然对话创建和管理任务，并通过稳定后端关联为未来 UI 留口。
- 在本 issue 解决前，不对 Scheduled Tasks 的入口层级、Task/Run 信息架构、run 的打开方式或对话可继续性作产品承诺。
- 这部分涉及导航、信息架构、会话模型与交互细节，若并入 099 会显著扩大交付和验收范围，因此决定延期。

## 可选修复方向

后续作为独立需求先完成产品和前端边界调研，再决定实现方式：

1. 对照现有桌面导航，验证“Scheduled Tasks 与对话同级”的信息架构是否成立，并评估是否需要重构前端模块边界。
2. 比较 `Task → Run`、任务列表直接展开运行历史等结构，明确 occurrence、run 与 session 在 UI 中分别承担什么角色。
3. 明确点击 run 后是只读运行详情、普通 Agent 对话，还是两者组合。
4. 若允许继续对话，明确续聊只属于该次 session，还是会影响任务定义或后续 occurrence；默认不得隐式污染后续周期执行。
5. 基于 099 已保留的查询、来源元数据和变更能力接线，避免 UI 反向成为调度状态的第二真相源。

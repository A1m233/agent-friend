# 040 · 长会话缺少独立的旧工具结果压缩机制

- **状态**：resolved
- **严重度**：medium
- **发现日期**：2026-08-03
- **关联需求**：009-engine-context-management、063-context-compaction-reliability、065-trustworthy-read-tools-and-tool-runtime、075-tool-result-context-retention

## 现象

长会话在全局摘要触发前会长期保留工具调用结果全文。目标会话最近一次摘要检查点之后，`social_search` 与 `web_search` 的结果字符数约占全部工具结果字符数的 78%；当 prompt cache 没有复用时，约 12.6 万 prompt tokens 会产生显著首包延迟。

当前上下文管理主要在接近模型窗口安全阈值时做整段摘要，尚未在较低水位单独清理已经陈旧、体积很大的工具结果。因而即使普通对话正文并不多，连续搜索、网页抓取或社交平台读取也会快速推高每轮输入。

## 根因初判

工具结果与普通对话历史共用同一套全局上下文压缩时机，缺少按结果年龄、体积、可恢复性和语义类型划分的独立投影层。

直接给每条结果设置很小的固定上限虽然简单，但会破坏后续追问旧证据、核对来源和继续处理搜索结果的能力；在没有质量评估和恢复机制前不适合直接上线。

## 影响与判断

该问题会增加长会话的缓存冷启动延迟、输入 token 成本和触发全局摘要的频率，但目前仍可通过新开会话或等待全局压缩规避，因此严重度记为 medium。

本轮只登记、不实施压缩。缓存诊断日志可以独立补充，不依赖本 issue 的策略决策；工具结果压缩需要先验证对旧结果追问质量的影响，再单独修复。

## 可选修复方向

1. 采用“超过工具结果预算后批量清理最旧结果”的阈值策略，不对每轮或每条结果统一截成固定的小上限。
2. 优先保留最近轮次、当前任务仍在引用的结果、状态变更型工具结果和高价值证据；对只读且可重新获取的大结果优先清理。
3. 清理后在模型视图中留下稳定占位符，说明工具名、结果状态和恢复引用，不保留正文。
4. 原始 session event 保持不变；为证据型结果提供按稳定引用从本地事件恢复或重新读取的能力。
5. 用真实长会话做 baseline/candidate 对比，同时评估 prompt tokens、冷缓存首包延迟、旧结果追问正确性和摘要稳定性，再决定预算、保留窗口和单批最小清理量。
6. 不采用定时 keepalive 或预热请求替代本地上下文治理；该方案增加费用，也不能保证上游缓存驻留。

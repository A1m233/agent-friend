## 1. 背景

当前 QQ 私聊中的助手回复会等 Agent 完整生成后一次性发送。对于较长回答，用户在生成期间只能等待，无法看到内容逐步出现，体感上也难以判断机器人是否仍在正常工作。

QQ 私聊已经具备在同一条消息中持续更新内容的原生流式能力。agent-friend 需要利用该能力改善长回复的等待体验，同时保持现有 Agent 会话、记忆、控制菜单和消息降级语义不变，并留下足够的本地诊断证据，便于排查真实 QQ 环境中的协议、时序和平台错误。

## 2. 目标

1. 让 QQ 私聊中的纯文本和 Markdown 助手回复在生成过程中持续更新，而不是等全部完成后才出现。
2. 确保一次助手回复最终只呈现一份完整正文，不因流式完成、菜单附加或失败降级产生重复消息。
3. 在 QQ 流式能力不可用或调用失败时安全降级，保持用户仍能收到尽可能完整、可理解的回复。
4. 保持现有 Agent 会话持久化、上下文、记忆、模型选择和 QQ 控制菜单语义不变。
5. 为流式生命周期、异常和降级路径提供默认落盘且可随诊断包导出的日志证据。

## 3. 范围

### 3.1 包含

- QQ C2C 私聊中的纯文本和 Markdown 助手回复使用 QQ 原生流式消息能力。
- 同一轮回复在同一条 QQ 消息中持续更新，完成后呈现完整最终内容。
- 对更新频率进行节制，避免按每个 token 发起平台请求，同时保证用户能感知内容持续生成。
- 流式首发失败时降级为现有普通完整消息；流式已经开始后发生异常或取消时，尽可能结束当前消息并向用户留下可理解的最终状态。
- 流式回复完成后继续保证 `☰ 菜单` 可达，且不得为了附加菜单而重复发送完整正文。
- 保持普通对话与 QQ 控制消息的既有边界：普通助手正文进入对应 Agent 会话，流式协议状态和菜单控制消息不进入模型上下文。
- 为流式开始、更新、完成、取消、异常和降级路径记录统一落盘日志。
- 流式日志记录可关联一次入站消息与一次流式会话的必要标识、状态、更新序号、内容长度、耗时、平台错误码和降级原因。
- 流式日志默认不记录凭据和完整对话正文，并进入现有诊断包收集链路。
- 为流式状态、更新节制、顺序一致性、完成、取消、异常和降级补充自动化测试，并执行真实 QQ 私聊 smoke 验证。

### 3.2 不包含

- QQ 群聊、频道或其他非 C2C 场景的原生流式回复。
- 图片、语音、文件、视频及其他富媒体内容的流式传输。
- 为其他 IM 平台实现流式回复。
- 改变 Agent 的 token 生成方式、模型 Provider 流式协议或会话持久化格式。
- 把 QQ 流式协议事件、菜单消息或错误提示写入 Agent 对话上下文。
- 默认记录完整用户消息或助手回复正文。
- 建设面向普通用户的日志查看器或流式调试界面。

## 4. 核心需求

### 4.1 流式体验

- **R-1.1 同消息更新**：符合条件的 QQ 私聊回复必须在同一条消息中持续更新，不得通过连续发送多条正文消息模拟流式。
- **R-1.2 最终完整**：流式完成后的正文必须与 Agent 本轮最终输出一致，且只出现一次。
- **R-1.3 更新节制**：系统必须合并过密的增量内容，避免按 token 调用 QQ 平台，同时不能因节制而退化为始终只发送最终结果。
- **R-1.4 顺序一致**：平台请求延迟或 Agent 快速连续产生增量时，QQ 中展示的内容不得倒退、乱序或被较短的旧快照覆盖。

### 4.2 适用范围与降级

- **R-2.1 C2C 文本范围**：第一期仅对 QQ C2C 私聊中的纯文本和 Markdown 正文启用原生流式回复。
- **R-2.2 非适用场景保持现状**：群聊、富媒体和其他不支持场景继续使用现有完整消息发送链路。
- **R-2.3 首发失败降级**：若本轮尚未成功创建流式消息，系统必须能够退回普通完整消息发送，不得造成用户收不到回复。
- **R-2.4 流中异常收口**：若流式已经开始后发生取消、网络错误或平台拒绝，系统应优先结束当前消息并保留已经生成的有效内容；不得再重复发送完整正文。
- **R-2.5 单轮单路径**：一轮回复一旦成功进入流式路径，不得在正常完成时再走普通正文发送路径。

### 4.3 会话与控制菜单兼容

- **R-3.1 会话语义不变**：启用流式不得改变当前 QQ 聊天绑定的 Agent 会话、模型、上下文、记忆和持久化行为。
- **R-3.2 菜单持续可达**：流式回复完成后，支持消息按钮的 QQ 机器人仍应提供 `☰ 菜单` 入口。
- **R-3.3 正文不重复**：菜单入口的承载方式不得导致完整助手正文被再次发送。
- **R-3.4 控制消息隔离**：流式协议状态、异常提示和菜单交互继续作为通道控制信息处理，不得污染 Agent 会话历史和后续模型上下文。

### 4.4 落盘日志与诊断

- **R-4.1 生命周期覆盖**：日志至少覆盖流式开始、更新、完成、取消、异常、普通消息降级和最终发送结果。
- **R-4.2 可关联性**：同一轮的日志必须能通过安全的关联标识串联入站消息、Agent 回合、流式会话和最终结果。
- **R-4.3 排查字段**：日志应包含阶段、更新序号、累计内容长度、调用耗时、平台响应状态或错误码、重试或降级原因等排查所需信息。
- **R-4.4 隐私边界**：日志不得记录 Bot 凭据、访问令牌或其他秘密；默认不得记录完整用户消息和助手正文。
- **R-4.5 统一落盘**：日志必须进入项目统一日志目录，并被现有诊断包收集，无需用户额外开启开发模式才能获得基础证据。
- **R-4.6 失败可见**：即使流式初始化本身失败，失败原因和后续是否成功降级也必须落盘，避免只看到“最终没流式”而无法区分能力、网络或实现问题。

## 5. 验收标准

- **AC-1**：在 QQ 私聊中触发一段足够长的纯文本或 Markdown 回复时，用户看到同一条消息至少发生一次中间更新，最终内容完整且没有重复正文消息。
- **AC-2**：快速连续增量及网络响应乱序条件下，QQ 消息内容保持单调前进，最终结果不被旧快照覆盖。
- **AC-3**：流式首发失败时，本轮自动降级为普通完整消息，用户仍能收到完整回复，且日志明确记录首发失败和降级结果。
- **AC-4**：流式已经开始后发生取消或更新失败时，QQ 中保留已生成的有效内容并得到可理解的收口；不会再收到一份重复的完整正文。
- **AC-5**：群聊、富媒体和其他非适用消息继续走既有发送链路，行为不退化。
- **AC-6**：流式完成后 `☰ 菜单` 仍可访问，且菜单的发送或展示不会复制助手正文。
- **AC-7**：同一轮普通用户消息和最终助手正文仍正确归属当前 Agent 会话；流式中间状态、错误提示和菜单控制消息不进入会话历史或模型上下文。
- **AC-8**：本地日志可以按一次消息关联出流式开始、更新、完成或异常、降级及最终结果，并包含序号、累计长度、耗时和平台错误信息。
- **AC-9**：默认日志和诊断包中不出现 Bot 凭据、访问令牌及完整对话正文；流式相关日志随现有诊断包成功导出。
- **AC-10**：自动化测试覆盖流式生命周期、节流、并发顺序、首发失败降级、流中异常、取消和普通发送兼容路径，项目规定的检查门禁全部通过。
- **AC-11**：使用真实 QQ Bot 完成一次 C2C 长文本流式 smoke，确认同消息更新、最终完整、菜单可达及日志证据均符合预期。

## 6. 依赖与约束

- QQ 原生流式消息当前仅作为 C2C 私聊能力使用；其他聊天范围不由本需求扩张。
- QQ 平台能力、频率限制、错误码和消息状态约束必须以接入时可验证的官方协议与真实行为为准。
- 现有 `qqbot-agent-sdk` 若未直接提供所需接口，具体接入方式在技术方案中确定，但不得通过不稳定的私有实现细节破坏现有认证和发送链路。
- 真实 QQ smoke 会产生实际平台交互，执行前按项目授权规则告知用户测试内容和大致消息数量。

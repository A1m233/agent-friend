# 156 · 桌宠原生崩溃修复与崩溃留证

## 状态

CONFIRMED

确认日期：2026-10-08。用户确认本次需求同时修复已定位的崩溃，并补齐后续崩溃的留证与定位能力。

## 背景

2026-10-08，Windows 安装版 agent-friend 0.4.0 的主程序异常退出，后台服务随之退出。常规产品日志没有给出崩溃调用栈。进一步查询系统转储并寻找匹配的构建符号后，才定位到桌宠光标后台线程获取窗口时，窗口运行时对象复制过程中的非原子引用计数检查触发进程终止。

本次的直接终止路径已经由转储、匹配符号和事故构建源码确认；引用计数最早被破坏的原因仍未由当前小转储完全证明。跨线程复制是现有证据支持的优先调查与修复方向，不能把这一推断写成已经完成复现的事实。

现有 panic 日志不能覆盖这次原生终止；产品诊断入口未纳入主程序系统崩溃证据；构建符号也没有独立于可清理构建缓存的保留契约。用户期望同时解决本次崩溃，以及后续只能知道“程序退出了”却无法继续定位的问题。

## 目标

1. 修复本次桌宠光标采样触发的原生崩溃，并核对同一风险边界上的其它窗口调用。
2. 让受支持的原生崩溃和 Rust panic 默认留下可离线定位的本地证据，正常退出与原因未知的异常结束能够区分。
3. 让对应构建的符号在后续构建、缓存清理和正常升级后仍可用于定位。
4. 用户重启后可通过已有诊断入口导出崩溃摘要和证据，采集缺失、符号不匹配等情况必须明确可见。

## 范围

### 包含

- Windows 主程序本次原生崩溃的修复、确定性机制验证和有边界的运行时回归。
- 桌宠持续光标采样与并发窗口事件下的稳定性；维持当前光标跟随、透明区域穿透及多屏缩放的既有行为。
- 检查并处理与本次已确认崩溃共享风险机制的窗口运行时访问；具体边界由技术方案与验证证据确定。
- Windows 主程序的 Rust panic、原生异常终止、正常退出及无法确定原因的非正常结束的证据覆盖与分类。
- 主程序与产品自有后台服务之间的退出关联，能够区分已知的服务先退出、主程序先退出和证据不足。
- 崩溃时间、进程与会话、构建身份、异常和故障位置，以及还原调用栈所需的证据关联。
- 可分发构建的精确匹配符号留存与离线定位入口。
- 既有诊断包对崩溃摘要、证据完整性和采集失败的表达；原始内存转储单独选择导出。
- 证据的存储上限、保留与清理、隐私边界，以及受控异常验证。

### 不包含

- 不相关的桌宠视觉、交互重设计或其它历史 issue 的修复。
- 首期实现 macOS/Linux 原生转储能力；公共代码改动仍须保持这些平台可编译，并如实表达未支持能力。
- 默认上传崩溃转储、引入云端崩溃平台或自动向外部服务发送用户数据。
- 保证任意断电、内核故障或外部强制终止都能恢复调用栈；这类情形应明确表示证据边界与未知原因。
- 仅凭一次压力验证宣称所有长期稳定性问题已经消失。

## 验收条件

- [ ] AC-1：本次崩溃的直接机制有与事故构建绑定的证据；修复针对该机制，明确区分已确认事实、推断和剩余不确定性。
- [ ] AC-2：修复有确定性回归验证；在记录配置、时长、操作与构建身份的桌宠持续采样及并发窗口操作验证中，未复现本次终止。光标跟随、穿透和多屏缩放行为保持兼容。
- [ ] AC-3：受控 Rust panic 和原生崩溃发生后，重启可发现对应证据，并能使用精确匹配符号还原预设故障位置；主程序崩溃不要求崩溃中的进程成功完成普通日志写入。
- [ ] AC-4：正常退出不会误报为崩溃；无法确定原因的非正常结束不会伪造异常码或调用栈；后台服务退出与主程序退出的关联及证据不足情况可区分。
- [ ] AC-5：可分发构建的二进制与符号有可校验的对应关系，清理普通构建缓存后仍可定位对应版本；缺失或不匹配符号时明确拒绝错误归属。
- [ ] AC-6：默认诊断导出包含崩溃摘要、证据覆盖和采集错误，原始内存转储仅在单独选择时导出；旧诊断包仍能被现有消费者兼容读取。
- [ ] AC-7：验证存储不可写、证据缺失/损坏、保留上限和清理场景；这些失败不会让产品静默声称已留证，也不会影响用户会话与设置数据。
- [ ] AC-8：受控崩溃与运行时验证隔离于用户的真实安装和数据；项目检查与对应打包/诊断契约验证通过，最后由用户确认验收。

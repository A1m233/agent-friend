# 045 · AgentRuntime 统一执行入口与调度生命周期

## 状态

已确认（Confirmed）

## 背景

[014 · engine main loop 与 bridge push](../014-engine-main-loop-and-bridge-push/requirement.md) 已建立 `AgentRuntime`、事件源、Hook 与主动事件 push 通道，让 bedtime、idle reflection 等系统触发轮能够进入统一 outer loop。但当前用户触发路径仍存在旁路：AG-UI、OpenAI compatible、voice、IM 等入口并非全部由 `AgentRuntime` 统一驱动，部分路径直接执行 conversation inner loop，再额外镜像事件给订阅者。

这使系统在运行生命周期上仍有多套语义：不同入口不一定经过相同 Hook 与收尾逻辑；全局单消费者会让一个慢轮阻塞其他 session；用户消息与低优先级主动事件没有明确调度关系；取消、异常终态和慢订阅者背压也缺少统一契约。随着文本、语音、IM 与主动事件同时使用，这些差异会直接影响响应及时性、会话顺序和故障恢复能力。

本需求把 `AgentRuntime` 从“主动事件调度器”收口为所有 Agent 运行的统一执行控制面，同时保留现有 conversation inner loop、各 channel 的流式协议和 voice 低延迟策略。

## 目标

- 所有用户轮和系统主动轮都受同一套运行生命周期、调度约束、Hook 与终态收尾管理。
- 同一 session 的运行严格有序，不同 session 之间可以在受控范围内并发，避免无关会话互相阻塞。
- 用户实时输入优先于尚未执行的低优先级主动事件；过期或重复的主动事件不会形成无意义排队。
- 每轮运行都有稳定身份、明确状态和唯一终态，失败与取消也能完成必要收尾。
- OpenAI compatible / voice 路径纳入统一运行控制，但继续保持逐增量输出和 channel 专属低延迟能力。
- 慢订阅者或断开的客户端不会阻塞 Agent 执行，也不会导致无界积压。

## 范围

### 包含

1. **统一运行入口**
   - AG-UI 文本对话、OpenAI compatible 入口、voice 持久会话、IM 用户消息与系统主动事件均纳入统一运行生命周期。
   - 各入口继续输出原有协议形态；统一执行控制不得要求客户端切换协议。
   - 统一后不再依赖“入口直接执行 inner loop，再旁路镜像运行事件”的双路径行为。

2. **统一运行身份与状态**
   - 每轮运行具有唯一 `run_id`，并关联 session、来源与 channel。
   - 运行至少可区分排队中、执行中，以及完成、失败、取消、跳过、过期等终态。
   - 每轮运行只能进入一个终态；终态必须可被调用方和订阅方一致识别。

3. **Session 级顺序与跨 Session 并发**
   - 同一 session 同一时刻最多执行一轮，事件和会话落盘顺序稳定。
   - 不同 session 可在受控并发上限内同时执行；单个慢 session 不应全局阻塞其他 session。
   - 并发上限应可配置，并提供适合桌面单机运行的保守默认值。

4. **优先级、过期与合并**
   - 用户实时输入优先于尚未开始的 cron、idle reflection 等低优先级主动事件。
   - 主动事件可声明有效期；超过有效期仍未开始时直接进入过期终态，不再生成迟到回复。
   - 同一 session 内语义相同、尚未开始的可合并主动事件不得无界重复排队。
   - 优先级不得破坏同一 session 已经确认的用户轮顺序。

5. **第一阶段取消能力**
   - 尚未开始的运行可以取消，取消后不得进入 conversation inner loop。
   - 流式客户端断开时，取消信号应传播到对应运行。
   - 已开始运行采用 cooperative cancellation：在 LLM 流事件、工具调用之间等安全边界停止后续工作，并完成统一收尾。
   - 同一 session 正在执行低优先级主动轮时，新用户输入可发出取消信号；系统在安全边界停止主动轮后处理用户输入。
   - 本期不承诺强制终止底层不支持取消的同步 provider 或 tool 调用。

6. **完整运行收尾**
   - 正常完成、失败、取消、跳过与过期都必须形成明确终态。
   - 已进入执行阶段的运行，即使 conversation、LLM、tool 或事件投递发生异常，也必须执行统一的 PostTurn / 清理路径。
   - 失败或取消过程中已合法落盘的部分事件不得导致 session 无法继续使用。

7. **流式与订阅投递可靠性**
   - OpenAI compatible / voice 继续逐增量返回模型输出，不退化为整轮完成后一次性响应。
   - Voice 可继续使用短回复、token 上限、工具启停、延迟 trace 等 channel 专属策略；统一生命周期不等于统一生成参数。
   - 慢订阅者不得阻塞运行线程，也不得产生无界等待任务。
   - 订阅方应能按 `run_id` 区分运行，并收到完成、失败或取消等终止信号。
   - 异常终止后不得遗留无法释放的 turn buffer 或订阅状态。

8. **可观测基础字段**
   - 运行日志和跨层事件应能关联 `run_id`、`session_id`、source/channel 与最终 outcome。
   - 至少能观察排队耗时、运行耗时和 voice 首文本增量关键时间点，以判断统一入口是否引入明显延迟退化。
   - 本期只铺统一关联与生命周期字段，不建设完整 tracing 平台或可视化看板。

### 不包含

- 工具风险分级、参数二次 schema 校验、人工批准、幂等键、工具级超时与副作用治理。
- 工具调用并行化或异步工具协议改造。
- 持久化 run checkpoint、进程重启恢复、暂停后等待人工输入再恢复。
- 多进程、跨主机或分布式调度。
- Planner、router、subagent、evaluator 等多 Agent 编排。
- `agent-cli` 的 Runtime 迁移或新增维护投入；CLI 保留直接调用 `Conversation` 的兼容开发入口。
- 前端任务中心、运行队列列表或新的取消交互 UI。
- 完整 tracing 平台、成本看板或 trajectory eval 平台建设。
- Voice provider、RTC、TTS / ASR 链路本身的重构。
- 强制终止底层不支持取消的同步 LLM/provider/tool 调用。

## 需求

### R-1 · 统一入口与协议兼容

- **R-1.1**：所有面向用户或系统触发的 Agent 运行必须进入统一运行生命周期，不允许新增绕过该生命周期的 conversation 执行入口。
- **R-1.2**：AG-UI、OpenAI compatible、voice 与 IM 的既有客户端协议和用户可见流式行为保持兼容。
- **R-1.3**：conversation inner loop 的工具循环、上下文管理、persona、memory 与会话事件语义保持现有职责，不因 outer loop 统一而复制第二套实现。
- **R-1.4**：各 channel 可以保留专属执行参数，但必须服从统一 session 顺序、取消和终态规则。

### R-2 · 运行生命周期

- **R-2.1**：每轮运行具有唯一 `run_id`，跨入口、Runtime、conversation、日志和流式出口保持关联。
- **R-2.2**：运行状态转换必须单向、可判定且只能结束一次。
- **R-2.3**：跳过和过期属于正常可解释终态，不应伪装为执行失败。
- **R-2.4**：失败和取消必须携带面向系统的原因分类；不得向用户暴露 provider、内部异常或堆栈等技术细节。

### R-3 · 调度隔离

- **R-3.1**：同一 session 的运行严格串行，不允许两个运行同时修改同一 session。
- **R-3.2**：不同 session 在有界并发范围内互不阻塞。
- **R-3.3**：达到并发上限时，新运行进入有界、可观测的等待状态，不得无界创建执行线程或任务。
- **R-3.4**：运行调度与 session 文件锁职责分离；文件锁继续保护落盘完整性，Runtime 负责业务轮顺序。

### R-4 · 实时输入优先

- **R-4.1**：尚未开始的低优先级主动事件不得延迟同 session 的新用户输入。
- **R-4.2**：已开始的低优先级主动轮收到新用户输入后进入取消流程，在安全边界结束后让出 session。
- **R-4.3**：系统不得通过强杀线程破坏 session 或留下未知工具副作用。
- **R-4.4**：主动事件的过期与合并结果必须可观察，便于区分“没有触发”“被合并”和“等待后过期”。

### R-5 · 取消与异常收尾

- **R-5.1**：排队中的运行取消后不得调用 LLM、tool 或写入用户/assistant 会话事件。
- **R-5.2**：已开始的运行取消后不得继续启动下一次 LLM 调用或下一个 tool；当前不可中断调用返回后应尽快结束。
- **R-5.3**：客户端断开只是取消来源之一；取消生命周期不得依赖某一种 HTTP 框架或协议。
- **R-5.4**：执行阶段的所有终态都必须经过统一清理和 PostTurn 路径；PostTurn 可根据 outcome 判断是否执行 memory observe 等旁路行为。
- **R-5.5**：服务关闭时停止接收新运行，并对排队和在途运行形成明确处理结果，不得把仍在执行的线程伪装成已停止。

### R-6 · Streaming 与背压

- **R-6.1**：协议入口提交运行后应能立即消费该运行的增量事件，不需要等待整轮结束。
- **R-6.2**：慢订阅者的积压必须有明确上限和处置策略，且不能反向阻塞 Agent 执行。
- **R-6.3**：每个已开始并对外暴露事件的运行都应向订阅者发送终止信号，包括失败和取消。
- **R-6.4**：订阅者断开或事件投递失败不得改变 conversation 的执行结果，但应留下可诊断记录。

### R-7 · 性能不退化

- **R-7.1**：统一入口不得把 voice/OpenAI 流改为整包响应。
- **R-7.2**：不同 session 的慢运行不得增加 voice/user 轮的排队时间。
- **R-7.3**：同 session 的必要顺序等待应可观测，不能与 LLM/provider 延迟混在一起。
- **R-7.4**：验收时应比较改造前后的 voice 首文本增量链路；如出现明显新增 Runtime 固定开销，不得以“架构统一”为理由接受退化。

## 验收标准

- **AC-1 · 入口统一**：分别从 AG-UI、OpenAI compatible 持久会话、voice、IM 和系统主动事件触发运行，均可观察到统一 `run_id`、生命周期和 Hook；既有响应协议与 session 投影保持兼容。
- **AC-2 · 同 Session 串行**：向同一 session 并发提交两轮，第二轮必须在第一轮终态后才进入 conversation；最终事件顺序稳定、会话可继续。
- **AC-3 · 跨 Session 并发**：一个 session 使用可控慢 fake LLM/tool 时，另一个 session 的用户轮能够在并发上限内独立开始并完成，不等待前者结束。
- **AC-4 · 用户优先**：同一 session 存在尚未执行的 idle/cron 事件时，新用户输入优先执行；已开始的低优先级主动轮收到用户输入后在安全边界取消并让出 session。
- **AC-5 · 过期与合并**：重复主动事件不会无界排队；过期事件不进入 conversation，且能区分 merged / expired 结果。
- **AC-6 · 排队取消**：取消尚未开始的运行后，LLM、tool 与 session 消息事件均没有该轮副作用，运行终态为 cancelled。
- **AC-7 · 在途取消**：流式客户端断开后取消信号能到达运行；运行不再启动后续 LLM/tool 步骤，并发送或记录 cancelled 终态。
- **AC-8 · 异常收尾**：让 conversation、LLM、tool 和 listener 分别在可控位置抛错，运行均只产生一个终态；PostTurn/资源清理执行，session 不损坏，订阅 buffer 不残留。
- **AC-9 · 慢订阅者隔离**：订阅队列达到上限时，处置符合既定背压策略；Runtime 和其他订阅者仍可继续处理，且不会持续增长挂起投递任务。
- **AC-10 · Voice 流式与延迟**：voice/OpenAI 入口仍逐增量返回；voice 专属参数继续生效；新增 Runtime 层的排队耗时与首文本增量时间可测，未出现明显固定延迟退化。
- **AC-11 · 安全关闭**：有排队和在途运行时关闭服务，新运行被拒绝，既有运行按约定完成或取消；关闭返回后没有被错误标记为已停止的存活 Runtime worker。
- **AC-12 · 全量门禁**：相关单元/集成测试通过，`./scripts/check` 全绿；用户完成最终验收后方可标记需求完成。

## 约束与兼容性

- 保持单设备、单 bridge 进程的产品假设；本需求不扩展为分布式执行平台。
- Session JSONL 仍是会话事实来源；运行调度状态不应破坏既有会话读取和历史兼容性。
- Memory 的 `observe` / `retrieve` 领域契约不因本需求改变；运行 outcome 只决定何时以及是否调用现有能力。
- 各 channel 的输出编码继续由各自协议适配层负责，Runtime 不承载 AG-UI、OpenAI 或 IM 的 UI/协议渲染逻辑。
- 所有自动化测试优先使用 fake/mock LLM 与 tool；真实 LLM 或 voice 观察型验收执行前另行获得用户明确授权。

## 开放问题

- 运行状态是否需要全部进入持久 session event，还是其中部分只属于进程内执行状态，由 `design.md` 在“会话事实 vs 运行事实”边界下决定。
- 不同入口的默认优先级、主动事件默认有效期和合并键如何表达，由 `design.md` 根据现有 source 与 channel 装配确定。
- 并发上限的默认值、配置入口与测试覆盖方式由 `design.md` 决定。
- 慢订阅者采用丢弃最旧、丢弃最新、断开订阅者或可恢复游标中的哪一种策略，由 `design.md` 结合当前 SSE/push 契约决定。
- 客户端断开后是否保留已经流出的 partial assistant 文本，沿用现有 conversation 中断语义还是增加运行级区分，由 `design.md` 核对最新主干行为后决定。

# 055 · 打包制品与版本治理

## 状态

已确认（Confirmed）

## 背景

项目已经具备 Windows x64 完整运行时与 NSIS 安装包的标准打包入口，但现有打包缓存、中间产物和最终安装包都落在执行命令的仓库工作目录中。在 Codex worktree 等多工作树开发方式下，每个 worktree 会各自保存或丢失这些内容，造成缓存重复、磁盘占用不可控、历史制品难以查找，也容易把某个临时 worktree 误当成发布制品的长期存储位置。

现有流程能够校验多个产品版本字段相等并生成 SHA-256 与 release manifest，但尚未形成完整的版本操作和制品治理边界。版本查询、版本更新、同版本覆盖、源码状态标识以及正式构建与本地调试构建的区别，需要有稳定且可重复执行的项目入口。

同时，Rule、Skill 和脚本之间的职责需要收敛：确定性的路径、版本和安全校验应由脚本强制执行；Rule 负责约束项目边界；Skill 负责引导和编排打包流程，而不是分别复制一套判断逻辑。

## 目标

- 最终安装包及其校验文件、manifest 保存在当前电脑的稳定目录中，不依赖任意仓库 checkout 或 worktree 的生命周期。
- 打包缓存和中间产物不长期占用仓库目录，并能在多个 worktree 并存时避免互相覆盖或误用。
- 提供统一、可查询、可校验的产品版本工作流，避免 Agent 或开发者手工在多个文件中搜索替换。
- 让稳定 release、可分发 trusted-beta 和不可分发 local-test 具有显式且不会互相冒充的版本渠道语义。
- 可分发正式构建具有明确的源码身份、版本、构建环境与不可变制品语义。
- 保留本地调试构建能力；调试构建可来自 dirty worktree，但不能与正式制品混淆。
- 让打包 Rule、Skill 和脚本各自承担清晰且不重复的职责。

## 范围

### 包含

- 治理现有 Windows x64 本地打包流程产生的缓存、中间产物和最终制品。
- 为最终制品提供脱离仓库与 worktree 的默认固定目录，并允许调用者显式覆盖。
- 为缓存和构建工作区提供电脑级默认目录；多个 worktree 或并发构建之间必须具有安全的隔离边界。
- 提供标准入口查询：
  - 项目当前产品版本；
  - 本机固定制品目录中最新的有效制品版本；
  - 当前版本与已有制品之间的关系。
- 提供标准入口显式设置产品版本，并保持需要一致的产品版本元数据同步。
- 校验产品版本符合 SemVer，并在正式构建时阻止版本倒退、版本不一致和无提示的同版本覆盖。
- 正式构建默认要求源码工作区干净，并记录可复核的源码 commit、构建标识和关键工具版本。
- 本地调试构建允许 dirty worktree，但必须在制品命名、目录或 manifest 中清晰标识为非正式构建，并与可分发正式制品隔离。
- 普通安装包与 trusted-beta 敏感安装包继续使用清晰、不可误认的隔离和警告语义。
- 每个可信内测开发周期显式配置一次下一稳定版本；具体 trusted-beta 预发布版本由标准脚本按有效历史制品自动递增，不改写源码稳定版本。
- 更新项目 Rule，使后续打包与路径相关改动必须遵循统一的打包路径入口和制品边界。
- 提供或更新项目 Skill，使 Agent 执行打包、查询版本或设置版本时统一调用标准脚本，并在执行前后展示关键结果。
- 为路径解析、版本治理、构建模式和制品防覆盖行为补充自动化测试。

### 不包含

- 上传或查询 GitHub Release、对象存储、制品仓库等远端发布系统。
- 在普通本地打包过程中自动联网判断远端最新产品版本。
- 自动决定应升级 major、minor 还是 patch；产品版本变更保持显式操作。
- CI/CD 发布流水线、Windows 代码签名、自动更新或更新服务器。
- macOS、Linux、Windows ARM64 安装包。
- 改变安装后的应用目录、用户数据目录、桌面设置目录或日志目录。
- 把内部 Python package metadata 强制同步为桌面产品版本。
- 改变现有完整运行时内容、trusted-beta 凭据注入语义或安装态业务行为。

## 需求

### R-1 · 固定且分层的电脑级路径

- 最终制品必须默认写入当前用户可稳定访问、可人工查找的电脑级目录，不得默认写入仓库或 worktree。
- 缓存与中间构建工作区必须和最终制品分层，避免清理构建缓存时误删可分发制品。
- 默认路径必须符合 Windows 当前用户目录语义，不要求管理员权限，也不得使用漫游用户数据存储大体积构建缓存。
- 调用者可以通过项目支持的显式入口覆盖默认根目录，以支持 CI、临时磁盘或其他受控环境。

### R-2 · worktree 与并发隔离

- 可安全复用的下载缓存应按锁定版本和完整性信息复用。
- PyInstaller、Tauri、Cargo 等构建中间产物必须具有构建级或 worktree 级隔离，不能因为两个 worktree 同时打包而互相覆盖。
- 构建完成或失败后，不应在源码树中遗留大体积 staging、敏感 seed 或被误认成最终制品的文件。
- 清理操作必须只作用于已解析并验证的打包工作目录，不得扩大到用户目录、仓库根或其他不相关路径。

### R-3 · 统一版本查询与设置

- 标准脚本应能输出项目当前产品版本及其一致性状态。
- 标准脚本应能从本机固定制品目录的有效 manifest 中查询最新制品版本；损坏、缺字段或校验不通过的目录不得被当作有效最新版本。
- 产品版本设置必须由显式版本输入触发，校验 SemVer 后同步所有需要保持一致的产品版本字段。
- stable 产品版本及 trusted-beta 下一稳定目标都必须由显式版本输入触发；脚本只允许在已确认目标内自动递增 beta 日期/序号，不得自行决定 major/minor/patch。
- 普通打包不得隐式修改源码稳定版本，也不得自行联网查询或选择远端版本。
- 内部 Python package 版本与桌面产品版本属于不同概念，本需求不要求二者统一。

### R-4 · 正式制品的不可变与可追溯

- 可分发正式构建默认只接受 clean worktree。
- 正式构建必须记录产品版本、源码 commit、dirty 状态、构建标识、平台、分发类型、关键工具版本、生成时间、安装包大小和 SHA-256。
- 如果目标版本和分发类型的正式制品已经存在，默认必须拒绝覆盖；任何允许替换的维护操作都必须显式、可识别且不能静默发生。
- 版本低于本机最新正式制品时必须拒绝正式发布；同版本重试可以在隔离的临时工作区中进行，但不能自动替换已发布制品。
- manifest 与安装包必须能够互相校验，查询“最新版本”时不得只依赖目录名或文件名。
- stable release 必须显式声明 release 意图；trusted-beta 必须使用高于当前安装、低于目标 stable 的预发布版本；local-test 不得作为可分发升级包。

### R-5 · 本地调试构建

- 开发者和 Agent 可以从 dirty worktree 生成本地调试构建，用于验证尚未提交的修改。
- 调试构建必须明确标识为非正式、不可发布，并记录源码 commit 与 dirty 状态。
- 调试构建不能占用正式版本的不可变制品位置，也不能影响“本机最新正式版本”的判断。
- 调试构建仍需执行与其目标相称的完整性检查；允许 dirty 不等于绕过版本一致性、敏感资源清理或安装包校验。

### R-6 · Rule、Skill 与脚本职责

- 路径计算、版本解析、SemVer 比较、Git 状态、制品发现、防覆盖和 manifest 生成必须由项目脚本实现并测试。
- Rule 只声明长期边界、唯一入口和禁止事项，不复制脚本中的目录拼接、命令流程或字段算法。
- Skill 只负责调用标准脚本、向用户展示构建模式与关键输入、执行必要验证并回报最终路径；不得自行搜索替换版本或拼接产物目录。
- 后续改变默认路径、版本规则或制品布局时，应修改脚本真相源，并同步评估 Rule、Skill、脚本文档和测试，不得叠加互相冲突的补丁式说明。

## 验收标准

- [x] AC-1：从两个不同 worktree 执行路径查询时，最终正式制品根目录相同且位于仓库外；中间构建目录不同，不会互相覆盖。
- [x] AC-2：打包完成后，仓库和 worktree 中不保留最终安装包、下载缓存或大体积持久构建目录；必要的瞬时 staging 在成功和失败路径上均被安全清理。
- [x] AC-3：标准版本状态命令能输出一致的项目产品版本、本机最新有效正式制品版本，以及是否允许生成新的正式制品。
- [x] AC-4：显式设置一个合法新版本后，需要同步的产品版本文件保持一致；非法 SemVer 或部分写入失败不会留下半更新状态。
- [x] AC-5：dirty worktree 的正式构建 fail closed；同一 dirty worktree 可以显式生成带明显 debug/dirty 标识的本地调试构建。
- [x] AC-6：已存在同版本、同平台、同分发类型的正式制品时，再次正式构建不会静默删除或覆盖原制品。
- [x] AC-7：低于本机最新正式制品的版本不能生成新的正式制品；调试构建不参与最新正式版本判断。
- [x] AC-8：普通包与 trusted-beta 敏感包在目录、文件名、manifest 和警告信息上保持隔离，敏感临时资源在成功或失败后均被清理。
- [x] AC-9：正式制品 manifest 至少包含版本、commit、dirty 状态、build ID、平台、分发类型、关键工具版本、时间、文件大小和 SHA-256，且安装包哈希核验通过。
- [x] AC-10：项目 Rule 和打包 Skill 都引用标准脚本入口；其中不存在另一套版本比较或固定路径拼接逻辑。
- [x] AC-11：路径、版本、正式/调试模式、防覆盖和 manifest 的核心行为有自动化测试覆盖，项目全量检查通过。
- [ ] AC-12：裸打包不能隐式发布；显式配置下一稳定版本后，连续 trusted-beta 构建自动得到单调递增的预发布 SemVer，源码稳定版本保持不变，最终 stable release 高于同目标 beta，local-test 仍不可分发。

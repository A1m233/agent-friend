## 背景与目标

已有历史分页、列表虚拟化和执行状态持久化仍不足以保证长会话的打开体验。用户关心的是首次看到真实历史内容的等待，以及等待期间能否正常输入和切换，而不是仅有缓存命中时读取足够快。

本需求优先保证首屏与编辑响应，并在用户发送之前后台准备可复用的 LLM 调用状态。上下文加载本身的进一步提速为次要事项；只有当它阻塞首屏、编辑、切换，或使发送准备长期不可用时才成为本期必要治理对象。

## 范围与需求

### 1. 首屏与历史续页

- 打开历史会话，首次请求最近 10 轮；向上加载更早历史时，每次 30 轮。保留完整回合的既有语义，不丢失或打乱消息、工具调用及其结果。
- 不在首屏出现后无条件自动补满 30 轮。
- 固定最近 10 轮的内容，只增加更早历史时，首屏所需工作量不得随完整历史线性增长，用户首次看到内容的时间不得因此明显增长。
- 首屏请求不得同步扫描、完整校验或重建全部历史，也不得等待与完整历史长度相关的后台维护完成。
- 重启、内存缓存为空、索引落后以及后台维护并发等慢路径同样在范围内，不以缓存命中的平均耗时替代最慢路径分析。
- 旧会话的首次读取、迁移和恢复必须纳入方案，不默认豁免。只有单体日志、缺少可直接定位数据时的兼容策略仍需在方案阶段解决；未解决不得宣称首屏目标已经满足。
- 旧数据兼容必须由产品在用户设备上自动完成，不能依赖开发者或用户手工运行迁移脚本。不得将安装或使用新版的前提设为一次性完成全部旧会话迁移；具体按需兼容、增量补齐策略仍待方案确认，不因此自动放宽旧会话首屏目标。
- 首屏完成指真实历史内容首次绘制并可阅读；骨架屏、加载提示和错误提示不算成功首屏。
- 最近回合本身特别大时，须单独评估首屏响应量和展示成本，不把这种成本与更早历史增长混淆；完整内容仍须可访问。
- 聊天展示所需的数据随新事件持久化。旧会话首次打开后应能复用已取得的展示页，重启应用和继续追加消息后仍可读取。首次补齐与再次打开分别验收。

### 2. 发送前后台准备

- 用户打开会话后，在发送之前后台准备可复用的模型上下文与执行状态；复用既有持久化能力，避免无必要的重复准备。
- 准备不得阻塞历史首屏、输入和会话切换，也不得通过共享资源竞争实质拖慢这些操作。
- 后台准备不提前发起 LLM 请求、执行工具或提交用户消息。依赖本轮输入的工作在实际发送时完成。
- 准备状态在内部维护；正常加载不新增“正在准备 / 可以先输入”等可见提示、动画或占位区域。尚未就绪时仅限制发送，失败时保留草稿并提供错误与重试入口，不无限等待。
- 用户切换会话、模型或相关配置后，准备结果必须对应当前会话与有效配置；旧结果不得覆盖新选择或用于错误的发送目标。
- 连续切换不得无限累积准备任务和驻留状态。准备完成后的实际发送应复用仍有效的结果，不再次无条件重做全部准备。

### 3. 编辑与发送能力分离

- 历史加载或发送准备期间，用户仍可输入、粘贴、编辑草稿和切换会话、模型等操作；不能仅因这些等待禁用整个输入框。
- 草稿按会话正确保留，历史加载完成、准备完成或准备失败均不得覆盖用户正在编辑的内容。
- 不具备发送条件时，仅限制依赖该条件的发送动作；正常短暂准备不额外展示原因，确实失败时再反馈。按钮与回车等快捷发送入口遵循同样的限制。
- 只读会话及既有权限约束仍有效，不因解除加载态禁用而允许原本禁止的操作。

### 4. 输入框区域在前后端独立加载

- 输入框、模型与推理强度选择、权限模式、附件能力、语音入口状态及草稿等输入区域所需信息，必须与历史正文读取和执行上下文恢复独立。不能只解除前端禁用而让其后端请求继续读取全部历史。
- 编辑器及本地草稿先行可用。其余控件只依赖自身真正需要的数据，分别处理加载和失败；一个控件暂不可用不能让整个输入区域等待。
- 当前会话模型、推理设置和权限等轻量信息的读取，以及模型等配置修改，不以历史分页返回、全历史投影、索引重建或 LLM 上下文就绪为前置条件。
- 历史响应不得覆盖用户已经修改的配置或草稿；配置请求与后台发送准备必须绑定正确的会话和版本。
- 元数据尚未取得时不得将默认模型冒充会话的已确认配置。允许先编辑或选择待应用配置，但实际应用和发送仍须通过会话身份、只读与权限等必要校验。
- 对需要独立服务的附件、语音等能力，如实反映自身可用性；不因历史慢禁用，也不承诺在其必要服务不可用时仍可执行。

## 性能口径与待确认目标

- 计时起点：应用已经启动，用户点击打开一个本地历史会话。
- 计时终点：目标会话真实历史内容首次绘制并可阅读。
- 覆盖请求等待、后端读取、传输、前端解析与投影及绘制；应用进程启动耗时和模型首字时间单独统计。
- 必须固定首屏内容，逐级增加更早历史，并分别测量热状态、重启后读取及前述慢路径。观察最大值和分位数，不能只比较平均值。
- 同时验证后台准备并发时的首屏和编辑响应，避免单独运行时快、真实并发时退化。
- 输入区域单独记录编辑器可交互、会话配置返回及控件就绪时间；人为延迟或阻断历史读取时，独立输入链路仍须可工作。
- 初步工程目标：正常打开争取 100–300 ms，P95 不超过 500 ms，受控慢路径争取不超过 1 秒。这些数值未完成基线验证，也尚未作为硬验收阈值获得确认。
- 在技术方案阶段明确测试设备、数据规模、单页大小、重复次数和允许的增长幅度，再确认具体性能预算。不承诺任意硬件、任意大小正文及数据损坏情况下的绝对耗时上限。

## 不包含

- 为降低首屏耗时删除历史、改变模型记忆内容或缩减模型有效上下文。
- 仅为准备状态提前调用真实模型或产生工具副作用。
- 对模型服务的推理时间、网络时延或首字时间作固定上限承诺。
- 与本期首屏、编辑和发送准备无关的通用上下文系统重构。

## 验收条件

- [x] AC-1：首次历史读取为最近 10 轮，向上续页每次 30 轮；消息顺序、回合完整性、工具关联及历史导航保持正确。
- [x] AC-2：固定首屏内容并增加更早历史，首屏不出现随全部历史线性增长的读取或处理工作；完整链路测量满足后续确认的性能预算。
- [x] AC-3：覆盖重启、内存缓存为空、索引落后、后台维护并发与旧会话兼容；不能只以缓存命中路径通过验收，也不能把加载或错误提示算作真实首屏。
- [x] AC-4：历史加载及执行准备期间可编辑草稿和切换会话、模型；草稿不丢失、不串会话、不被迟到响应覆盖。
- [x] AC-5：发送前后台准备自动开始，无真实模型调用或工具副作用；不阻塞或实质拖慢首屏和编辑，连续切换不会无限堆积任务。
- [x] AC-6：发送就绪状态准确，按钮与快捷键限制一致；失败可恢复且保留草稿，配置变化后不会复用失效状态，实际发送复用有效准备结果。
- [x] AC-7：正确区分首屏、编辑响应、发送就绪及模型首字耗时；结果绑定实际代码与运行态，缺失或未执行的验证明确标注。
- [x] AC-8：延迟、失败或取消历史请求时，输入区域仍可独立显示草稿、读取自身所需配置及执行合法配置修改；后端调用不触发全历史读取、重建或执行恢复，旧响应不覆盖新选择。
- [x] AC-9：以旧版本用户数据验证产品内自动兼容，正常路径无需开发者或用户运行脚本，也不要求预先迁移全部会话；中断、重启、失败重试不会丢失或重复数据，首次历史性能单独核验，不能用自动兼容通过替代首屏达标。

## 技术方案阶段需确定

- 如何让首屏直接读取必要内容，并与全历史维护、校验及执行准备解除等待关系。
- 旧格式、索引失效和恢复期间如何提供准确内容，避免把全量恢复转移到首次打开。
- 可提前准备的状态边界，以及与本轮输入、配置变化、写入所有权和已有运行任务的关系。
- 后台准备的优先级、取消、失败恢复和资源回收，以及并发时的响应保证。
- 超大单轮的首次展示方式、完整内容访问和既有引用导航行为。
- 性能基线、具体预算与真实桌面端验收安排。
- 输入区域轻量数据的独立来源、读写接口、版本关系，以及旧数据下的自动初始化边界。

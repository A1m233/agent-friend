# 132 · 任务中断恢复与状态呈现一致性 — 技术方案

## 状态

CONFIRMED

确认日期：2026-09-16。用户确认以可靠提交边界决定自动恢复，替代此前未确认的“输出部分文字后默认手动继续”建议。

## 现状分析

- `llm_providers/client.py` 默认网络重试一次；过载使用独立次数与退避参数。SDK 重试已关闭，等待支持取消。当前流重试通过是否产生文字判断能否重放，文字后断流直接转为 `LLMStreamInterruptedAfterOutputError`。
- `Conversation._run_tool_loop_body` 统一执行正常的模型／工具循环，但当前主要在完整模型响应结束后提交 assistant turn 并执行工具。展示层的消息阶段结束，不自动等价于已提交的完整模型历史。
- `continue_after_tool_error` 是单独的无工具生成路径；其校验依赖有效事件流最后一项必须是 `run_error`，与 Runtime 写入的生命周期事件冲突。
- Runtime 已有运行标识、取消令牌、会话执行互斥和持久终态。`sessions/recovery.py` 已区分工具运行中、结果未知、已完成和原运行实例丢失。
- 前端继续入口根据错误码与成功工具块自行推断资格，随后追加新 assistant 占位。历史投影按 run 生成消息，缺少恢复尝试与原任务的明确关联。
- 等待事件的 `max_attempts=2` 在 Conversation 中重复出现；只改 Provider 常量不能使界面次数自动正确。

## 方案设计

### 1. 责任与恢复边界

| 边界 | 所有者 | 行为 |
| --- | --- | --- |
| 一次传输尝试 | Provider adapter | 发出请求、翻译错误及标准流事件；不自行执行工具 |
| 一个模型步骤的自动恢复 | Conversation 与 Provider 共用重试预算 | 最多首次请求加 5 次重试；在可靠历史上继续，不新增用户消息或运行 |
| 工具事务 | 现有 tool runtime、checkpoint 与 session recovery | 保留执行事实与结果；不因模型断流重放工具 |
| 失败后的手动继续 | Runtime 会话执行边界 | 校验指定来源运行，创建有关联的新尝试并进入正常工具循环 |
| 用户可见任务状态 | 持久运行事实及统一投影 | 聚合已明确关联的尝试，实时和历史使用同一规则 |

自动恢复保持原 run；手动继续使用新的 run，旧运行终态保持不可变。关联是追加事实，不把失败历史改写成成功，也不创建另一套工作流存储。

### 2. 单一重试预算与等待

- 一次逻辑模型步骤拥有一个预算：`max_retries=5`，首次尝试编号为 1，总尝试上限为 6。恢复后完成该模型步骤、执行下一批工具并进入新的模型步骤时，才创建下一份预算。
- Provider 内部的请求重试和 Conversation 层的断流恢复消费同一预算；不得两个循环分别重试 5 次。SDK 自动重试继续关闭。
- 网络和临时服务错误统一使用该上限；过载、临时限流仍保留分类和退避策略，不把余额不足、鉴权错误、权限拒绝或策略限制改成可重试错误。
- 沿用取消感知等待与指数退避，尊重可用的服务端重试建议。服务端要求的等待超过允许自动等待范围时转为可解释的等待／失败，不提前请求违背其限制。
- 状态事件由预算事实生成：首次等待不显示“重试 1/5”；后续显示“正在重试 1/5”至“5/5”。清除 `max_attempts=2` 等重复常量；日志另保留总尝试序号。
- 只有预算耗尽或不可恢复边界才产生终态错误；每次重连不是一条新的 `run_error`。

### 3. 按提交状态恢复流

区分三个层次：客户端可见增量、完整模型条目、可靠提交的工具事务。不能用“曾显示文字”或“看见右括号”代替完成信号。

| 状态 | 恢复处理 |
| --- | --- |
| 没有完整输出，只有活动信号或残缺参数 | 放弃本尝试的临时缓冲，从已提交历史重试；残缺工具不执行 |
| 已显示文字，但消息未完成 | 保留为带中断标记的临时展示片段；恢复时替换对应片段，不能与新响应盲目拼接，也不作为完整 assistant item 输入模型 |
| 完整模型条目已可靠提交 | 保留该条目及稳定标识；从其后的历史继续，不撤销已提交前缀 |
| 工具已启动或已完成 | 收集或重新关联已知执行结果，提交工具结果后再继续；不重新启动同一事务 |
| 工具结果未知、持久化失败或历史不闭合 | 停止自动模型请求，先进入现有恢复检查；仍无法确定时明确暂停 |

实施时沿用 `SessionModelHistory` 和 rollout 的既有提交协议。支持可靠 item 完成信号的 adapter 将完整条目提交给同一 owner；仅提供响应级完成信号的 adapter，在完整响应前继续以整个未完成响应为临时区。不得伪造 provider 完成信号，也不得从 UI phase 事件反推工具参数完整。

断流恢复清理的是当前尝试尚未提交的文本、推理续接状态和工具参数；不删除此前工具结果或重建已经执行的工具批次。Provider 私有续接数据只能在其对应提交边界仍有效时复用。

临时文字替换、完整消息提交和最终失败均带稳定的运行／步骤／条目标识。实时流与历史重载遵循相同提交事实，不以文本前缀匹配作为去重机制。

### 4. 手动继续进入完整工具循环

- 恢复请求必须指定来源运行；客户端不能只发送 session id 让后端猜“最后一个错误”。后端在会话互斥边界内核验来源归属、终态、最新任务边界与恢复资格。
- 生命周期事件不阻止恢复；判断基于来源运行及其任务历史，而不是最后一条事件的类型。新用户消息、编辑重发或已产生更新的恢复尝试后，旧目标失效。
- 重复提交同一恢复请求复用同一结果或返回稳定的已受理状态。不同请求竞争同一来源时只允许一个成为有效续行；无效请求不追加聊天错误或空运行。
- 资格验证在持久化新 `run_started` 之前完成，并在真正取得执行权后保持有效，避免检查与启动间竞态。
- 使用既有上下文装配、人格、附件、Skill、工具权限及正常 `_run_tool_loop`。保留原任务输入与结果，不追加假的用户消息，不走 `tools=None` 的总结捷径。
- 恢复关系至少包含来源运行与任务根运行，随运行开始事实持久化，并透传快照、实时事件和历史查询。服务端解析与校验关系，客户端不能任意合并任务。
- 旧 `/continue-tool-result` 入口如需保留，必须委托同一恢复实现；不能继续维护两套执行语义。旧调用缺少来源时只在唯一且有效的来源可确定时解析，否则返回明确的刷新提示。

### 5. 副作用、取消和重启

- 已有调用标识、执行 checkpoint 和工具结果是事务事实源。模型请求恢复本身不调用工具重放接口；后续新的工具选择继续经过正常授权和执行校验。
- 运行中事务保持已有执行归属；原运行实例丢失时使用 recovery adapter 和持久化部分证据，保留结果未知语义。
- 未知副作用不通过全局禁用工具处理；若有安全的状态查询，先查证再决定后续动作。无法查证时请求用户必要决策，禁止宿主自动重复原动作。
- 用户停止中断等待与后续请求；停止后收到的迟到事件不能重新激活运行。后续用户明确继续是新授权动作，不是自动恢复。
- Bridge 或应用重启只做状态协调，不自动重新发模型请求。客户端重连订阅既有运行，不创建新运行。
- 历史用户授权不能覆盖已变更的操作范围；恢复仍接受当前权限、模型可用性及渠道能力校验。

### 6. 状态与界面投影

- 每个任务恢复链共用一个当前状态区域，正文与工具活动按实际发生顺序保留；每次尝试仍拥有独立 run id 和诊断终态。
- 重试中更新活动状态；最终失败显示一次错误与“继续任务”入口；用户继续后原状态转为“正在继续”，失败则更新该区域，完成后移除当前失败态。
- 后端返回恢复能力，前端不再靠错误码白名单和“至少一个成功工具块”决定是否能继续。
- `run_error` 与 `run_terminal` 是同一次失败的不同事实，不生成两条错误。多次投递按事件和运行身份幂等处理；旧尝试的迟到错误不能覆盖新尝试状态。
- 未知关联的旧历史继续按原 run 展示，不根据相邻时间或相同文案擅自合并。
- 活动耗时按关联运行的已知执行区间累计，自动退避属于当前运行时间，手动等待不计为执行耗时；重启造成未知区间时不伪造精确总数。空尝试不独立渲染“用时未知”消息行。
- 不同用户任务、独立工具失败及未关联的运行错误不受任务恢复去重影响。

### 7. 涉及模块

| 模块／入口 | 修改职责 |
| --- | --- |
| `llm_providers/src/llm_providers/client.py`、流事件与 adapters | 预算、错误分类、可取消退避、可靠完成信号 |
| `agent/src/agent/conversation.py`、`sessions/model_history.py` 与 rollout | 共用恢复循环、临时输出与可靠历史边界、工具结果续接 |
| `agent/src/agent/runtime/`、`sessions/recovery.py` | 会话内恢复受理、尝试关联、取消与重启协调 |
| `agent_bridge/src/agent_bridge/routes/meta.py`、协议错误和会话查询投影 | 明确来源的恢复请求、恢复能力、状态关联与稳定拒绝结果 |
| `frontend/src/services/`、`stores/conversation.ts`、`stores/sessionProjection.ts` | 实时／历史一致投影、恢复请求幂等、活动运行选择 |
| `frontend/src/pages/chat/components/MessageList.tsx` 与现有状态组件 | “继续任务”、单一状态区域、重试次数和耗时 |
| 上述模块现有专项测试及 Runtime／Bridge 集成测试 | 故障注入、尝试次数、持久化重载、跨层竞态 |

恢复辅助逻辑按现有模块边界落位，避免继续扩大 Conversation 或前端 store 中的重复分支；不另造通用工作流引擎。

## 影响分析

### 上下游与兼容

- 运行事实字段采用兼容的增量扩展；旧事件没有关联信息时仍可读取，不能凭猜测补写关联。
- 请求准备、usage/cache 观测与日志保留逐尝试信息，用户界面合并不影响诊断归因和真实请求统计。
- IM、语音、调度入口共享重试政策，但遵守原有取消和工具能力边界；不自动为这些渠道新增桌面恢复交互。
- 更新上下文装配消费者清单和相关类型时沿用原 owner；恢复不新增人格或通用 prompt 副本。
- 运行时 Python 改动在实现时按 frozen-runtime-packaging 规则分类；本阶段不触发安装包构建。

### 验证方法

优先使用 fake Provider、受控流事件与可计数的副作用工具，经真实 Runtime／Bridge 入口验证，不只直接调用 Conversation helper。覆盖第五次成功、全部失败、取消退避、部分文字替换、完整条目后断流、残缺参数、已完成工具后请求失败、后续新工具、多次手动继续、并发点击、过期目标、重启、历史分页与事件乱序。

界面单测同时覆盖实时事件与持久历史重载，确保两条路径输出相同任务状态；诊断保留原始尝试。具体验收标准仍以 requirement.md 为准。

真实 LLM 不作为确定性故障恢复的必要前提；需要行为观察时另行确认调用范围。桌面截图／DOM 验收在获得用户授权后执行；未执行不宣称真实桌面效果已验证。合入前执行项目 `scripts/check` 并取得用户验收。

### 风险与限制

- 多次重试增加等待和潜在成本，必须始终可取消且预算可观测。
- 跨 provider 的完整条目能力不同，不允许以同一事件名掩盖提交语义差异。
- 本方案防止宿主因恢复重放已执行事务，不承诺外部系统全局 exactly-once，也不凭模型返回相似命令判断它一定属于重复请求。
- 部分输出处理涉及显示与模型历史两个边界；实现发现无法满足已确认提交语义时，应报告具体限制并回到方案讨论，不能静默退回纯文本总结或全部手动恢复。

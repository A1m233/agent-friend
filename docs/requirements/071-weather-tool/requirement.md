# 071 · 天气查询

> Weather Query

## 状态

CONFIRMED

## 1. 背景

agent-friend 已具备网页搜索、可信读取、附近地点搜索等工具，但尚无专门的天气能力。当用户询问“北京今天冷不冷”“今晚几点下雨”“周末适合出门吗”或“当地有没有台风、暴雨等预警”时，模型只能依赖普通网页搜索或已有知识，无法稳定获得位置明确、时间可信、字段结构化的实时天气与官方预警。

天气信息会直接影响用户的出行与安全判断。普通天气问题需要当前、逐小时和多日预报；极端天气场景还必须区分官方已经发布的预警、仅由预报体现的潜在风险、没有有效预警以及预警数据不可用。任何含糊、过期或未经权威来源支持的结论都会损害用户对 Echo 的信任。

因此，本需求要为 Agent 增加与附近地点搜索同级的独立天气查询工具，让 Echo 能基于可靠天气数据回答用户问题，并在查询天气时同步关注目标位置的官方极端天气预警。

## 2. 目标

1. 让用户能查询指定地点的当前天气、逐小时预报和多日预报。
2. 让 Agent 能回答降雨时段、温度变化、风况等与日常安排直接相关的问题。
3. 每次天气查询同步检查目标位置的有效官方天气预警，并在存在预警时优先提醒用户。
4. 对地点、数据时间、单位、预警来源和可用状态保持透明，不猜测位置、不使用过期信息、不把服务不可用误报为“没有预警”。
5. 保持天气、地点、空气质量等能力边界清楚，同时为未来增加相关环境能力保留合理扩展空间。

## 3. 范围

### 3.1 包含

- 支持以用户明确提供的城市、区县、地点名称、地址或可靠坐标查询天气。
- 支持当前天气，包括天气现象、温度、体感温度、湿度、降水、风向、风速、阵风和能见度等可用信息。
- 支持逐小时预报，用于回答降雨开始与结束时段、温度变化、风况变化等问题。
- 支持多日预报，包括每日主要天气、最高与最低温、降水和风况等可用信息。
- 每次成功发起天气查询时，同步检查同一目标位置当前有效的官方天气预警。
- 有有效预警时，在最终回答中优先呈现其事件、影响区域、有效时间、风险等级和官方行动指引等关键信息。
- 对官方预警与模型根据预报作出的风险提示进行明确区分；没有官方预警依据时不得使用“已发布预警”等表述。
- 对“没有有效预警”“该地区不在预警覆盖范围内”和“预警服务暂时不可用”给出可区分的结果。
- 返回或保留足以判断数据可信度的信息，包括实际查询地点、当地时区、观测或预报有效时间、数据更新时间、单位和预警发布机构。
- 地点缺失、同名或存在合理歧义时要求用户澄清，不根据系统时区、IP、语言习惯、历史聊天或其他弱语义静默推断当前位置。
- 查询失败、无数据、凭据缺失、额度耗尽或服务不可用时，给出自然、可理解且不泄漏内部实现细节的反馈。
- 工具调用、结果和失败继续遵守现有会话事件、隐私、错误处理、运行预算和工具使用约定。
- 天气能力作为独立工具接入，不并入附近地点搜索，也不要求模型把多个 provider 底层步骤自行编排成一次天气查询。

### 3.2 不包含

- 获取设备当前位置或新增系统定位权限。
- 根据 IP、系统时区、语言、历史聊天或长期记忆自动推断用户当前位置。
- 后台持续监控天气、订阅地点、主动推送预警或跨重启恢复预警任务。
- 空气质量、花粉、过敏原和生活指数；这些能力可在未来作为独立或相邻能力扩展。
- 历史天气、气候统计与长期趋势分析。
- 雷达图、气象地图、台风路径图或其他交互式可视化。
- 海洋、航空、农业等专业气象产品。
- 修改附近地点搜索、路线、导航或地图能力。
- 修改现有工具循环、调用预算、超时、并发或重复调用检测策略。
- 使用普通网页搜索结果冒充结构化天气数据或官方预警。

## 4. 核心需求

### 4.1 查询入口与地点边界

- **R-1.1 用户意图入口**：Agent 应能通过一个面向天气查询意图的工具完成当前、小时、多日和官方预警查询，而不是要求模型自行拼接多个底层数据接口。
- **R-1.2 支持的地点**：查询地点可以来自用户明确提供的城市、区县、地点名称、地址或可靠坐标。
- **R-1.3 禁止静默推断**：用户未提供足以可靠确定的位置时，Agent 必须询问地点，不得根据系统时区、IP、语言、历史聊天或相似地名自行猜测。
- **R-1.4 歧义澄清**：地点存在跨国家、跨城市、同城多候选或其他合理歧义时，必须提供足以区分的候选信息并请求用户确认。
- **R-1.5 查询地点透明**：成功查询后，最终回答应让用户知道实际采用了哪个地点；不得把近似匹配或候选地点隐瞒为用户原始输入。

### 4.2 当前与预报天气

- **R-2.1 当前天气**：能够返回目标地点当前可用的天气现象、温度、体感温度、湿度、降水、风向、风速、阵风和能见度等信息。
- **R-2.2 小时预报**：能够提供足以回答近期降雨时段、温度变化和风况变化的逐小时预报。
- **R-2.3 多日预报**：能够提供未来多日的主要天气、最高与最低温、降水和风况等信息。
- **R-2.4 按需回答**：工具结果应支持 Agent 围绕用户问题选择相关字段作答，不要求在每次回复中机械罗列所有天气指标。
- **R-2.5 时间与单位**：天气结果必须携带明确的当地时区、有效时间和单位；涉及“今晚”“明早”“周末”等相对时间时，以目标地点的当地时间解释。
- **R-2.6 数据时效**：当前天气与预报必须保留观测、预报或更新时间。数据明显过期、时间缺失或无法可靠判断时，不得当作最新天气回答。

### 4.3 官方极端天气预警

- **R-3.1 默认检查**：每次天气查询都应同步检查同一目标位置当前有效的官方天气预警，无需用户另外追问“有没有预警”。
- **R-3.2 优先呈现**：存在有效预警时，最终回答应先提示与用户安全和安排最相关的预警，再补充一般天气信息。
- **R-3.3 预警关键信息**：在来源提供时，预警结果应保留事件名称、标题、影响区域、发布时间、生效或开始时间、结束或失效时间、严重程度、紧迫程度、确定性、官方说明、安全指引、发布机构和来源链接。
- **R-3.4 官方语义保真**：预警等级、事件类型、颜色和行动指引以发布机构的实际信息为准。Agent 不得擅自升级、降级、改写成本地不存在的等级，或补造未提供的避险要求。
- **R-3.5 生命周期**：系统应能正确识别有效、更新、取消、替代和过期等预警状态，不向用户继续展示已取消、已被替代或已经失效的预警作为当前风险。
- **R-3.6 官方预警与风险提示分离**：Agent 可以依据预报提醒“预计可能有强降雨、高温或大风风险”，但只有实际取得官方预警时才能声称“气象部门已发布预警”。
- **R-3.7 状态可区分**：成功确认没有有效预警、目标地区无预警覆盖、预警查询失败和预警数据时间不可信必须是不同状态；后三者不得回答成“当前没有预警”。
- **R-3.8 覆盖透明**：预报可用但官方预警不可用时，仍可回答天气，但必须明确说明本次未能核实官方预警。

### 4.4 可信性、失败与工具协作

- **R-4.1 事实依据**：当前天气、预报、时间和官方预警结论只能依据本次天气工具实际返回的数据，不得由模型常识或普通网页摘要补造。
- **R-4.2 网页搜索边界**：天气工具失败时，不得仅凭普通网页搜索结果宣称已完成结构化天气查询或官方预警核验；网页搜索可用于补充用户明确要求的新闻、公告原文或背景信息。
- **R-4.3 可恢复失败**：地点需要澄清、服务未配置、额度耗尽、请求受限、暂时失败或无数据时，应提供与状态相符的自然说明，并在可能时给出可执行的下一步。
- **R-4.4 内部信息保护**：面向用户的失败说明不暴露 provider、API、SDK、鉴权字段、内部错误码或调用栈。
- **R-4.5 现有运行时兼容**：天气工具沿用现有 Tool Protocol、会话事件、可信数据标记、凭据管理和工具运行时，不建立另一套工具循环或会话记录机制。
- **R-4.6 扩展边界**：天气工具只承载天气与官方天气预警。未来增加空气质量、花粉、专业气象或主动通知时，应能通过相邻能力、扩展字段或新的工具接入，而不要求破坏天气工具的核心查询语义。

## 5. 用户体验与信任边界

- Echo 可以自然表达“我看看天气”或“我查一下有没有预警”，但只有实际调用天气工具后才能声称已经查询。
- 最终回答应围绕用户意图组织，不把原始结构化结果、技术字段或内部状态机械倾倒给用户。
- 有极端天气预警时应清楚、醒目但不过度渲染，优先转述官方行动建议，不自行制造恐慌。
- 用户只问普通天气时，有预警也要主动提及；没有预警时无需每次冗长强调，只需在与问题相关时自然说明。
- 地点不明确时，宁可用一句简短问题澄清，也不要给出可能属于另一座城市的天气。
- 预报具有不确定性。越远期的预报不得用确定语气承诺必然发生，尤其不能把预报风险表述成已经发布的官方预警。
- 工具不可用或预警覆盖不足时，应诚实说明能力缺口，不用“目前一切安全”等无证据结论安慰用户。

## 6. 验收标准

### 6.1 地点与基础天气

- [ ] 用户提供唯一明确的城市或地点后，Agent 能查询并说明实际采用的地点。
- [ ] 用户未提供地点时，Agent 会请求补充地点，不根据系统时区、IP、语言或历史聊天静默推断。
- [ ] 输入存在同名地点或合理多候选时，Agent 会展示可区分信息并等待用户确认，不擅自选择。
- [ ] 当前天气查询能返回可用的天气现象、温度、体感温度、湿度、降水和风况，并带有效时间与单位。
- [ ] “今晚几点下雨”一类问题能依据目标地点当地时间和小时预报回答降雨时段。
- [ ] 多日天气问题能返回相关日期的最高与最低温、主要天气、降水和风况。
- [ ] Agent 只选择与用户问题有关的字段自然作答，不在每次回复中罗列全部指标。

### 6.2 极端天气预警

- [ ] 自动化测试证明普通天气查询也会同步检查同地点的官方有效预警。
- [ ] 存在有效预警时，Agent 会在一般天气之前提示预警，并保留事件、影响区域、有效时间、严重程度、发布机构和可用的官方行动指引。
- [ ] 多条预警同时存在时，Agent 能优先呈现更紧急、影响更严重或与用户问题更相关的预警，同时不遗漏仍然重要的其他预警。
- [ ] 更新、取消、替代和过期预警不会被错误地继续当作当前有效预警展示。
- [ ] 模型根据预报提示强降雨、高温或大风风险时，不会在缺少官方预警数据的情况下声称“已发布预警”。
- [ ] “没有有效预警”“地区无预警覆盖”“预警服务失败”和“预警数据时间不可信”能被可靠区分。
- [ ] 天气预报成功但预警不可核实时，Agent 会正常回答天气并明确说明未能核实官方预警。

### 6.3 可信性、失败与回归

- [ ] 天气结果包含实际地点、当地时区、数据有效或更新时间和明确单位，过期或时间不明的数据不会冒充最新结果。
- [ ] 地点无结果、凭据缺失、额度耗尽、限流和暂时失败均有可区分的失败行为与自动化覆盖。
- [ ] 天气工具失败后，Agent 不会用 `web_search` 冒充已经完成天气或官方预警查询。
- [ ] 工具结果缺少某个可选字段时，Agent 会省略或明确说明未提供，不会推测或编造。
- [ ] 现有 `web_search`、`web_fetch`、`nearby_place_search`、日期时间工具及会话工具事件行为不退化。
- [ ] 默认自动化测试不触发真实天气、地图、搜索、LLM 或其他付费外部 API。
- [ ] 项目统一检查脚本全部通过。

## 7. 待技术方案确认

- 天气 provider 如何满足目标地区的预报质量、官方预警覆盖、许可、成本和稳定性要求，是否需要在预报与预警之间采用多个可替换数据源。
- 地点文本如何解析为可靠位置，以及如何复用附近地点搜索已形成的歧义处理经验而不耦合两个用户意图工具。
- 一次天气查询内部如何组织当前、小时、多日和预警请求，避免不必要调用，同时保证默认预警检查不被遗漏。
- 各 provider 的天气字段、预警事件、等级、颜色和生命周期如何归一化，同时兼容未来新增值和地区特有语义。
- 天气数据的时效阈值、缓存、超时和部分成功策略如何定义。
- 工具输入如何表达查询时间范围与所需信息，工具输出如何控制上下文体积并保留必要证据。
- 天气凭据如何接入现有运行时配置并按既有配置生效机制刷新服务。
- 未来空气质量、花粉、专业气象和主动预警通知应通过何种稳定边界扩展。

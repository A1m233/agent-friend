# 077 · Windows 安装升级完整性、运行时一致性与安装器本地化

## 状态

CONFIRMED

## 背景

agent-friend 已能生成包含桌面壳和冻结 Python 运行时的 Windows NSIS 安装包，并支持向可信用户人工发送新版安装程序进行覆盖升级。现有流程能够构建、校验和安装完整产品，但真实用户升级时暴露出一个未被现有验收覆盖的完整性缺口：安装程序在写入 `agent-friend-runtime.exe` 时报告文件被占用，用户当时没有看到旧桌面壳仍在运行，之后系统又表现为似乎完成了安装。

事后诊断包采集于新安装动作之后，只能证明当时已经运行了新版桌面壳，不能完整还原安装失败瞬间。现有证据强烈提示桌面壳、冻结运行时或内置资源存在版本错配风险，但诊断包没有记录可交叉验证的运行时安装身份，因此不能把具体混装状态断言为已确认根因。

该安装事件发生在已登记的 Windows 息屏恢复后全局黑屏事故之后，不能反向解释原始黑屏。黑屏仍由 issue 043 独立跟踪，本需求不预设或修复其图形链路根因。

这次问题也说明，仅检查可见桌面进程、仅验证目标文件存在、或仅依靠开发态测试，无法证明真实覆盖升级是完整的。安装流程、运行时生命周期、安装身份、诊断能力和交付门禁需要形成一套可以由机器验证的闭环，同时改善当前安装器仅以英文呈现的问题。

## 目标

- Windows 安装程序成功结束时，桌面壳、冻结运行时和随包资源必定属于同一次完整安装，不能留下已知的混装状态。
- 安装或升级被占用文件、异常进程、损坏内容或中断阻塞时，在破坏现有可用版本前停止，或明确拒绝启动不完整版本，并给出可行动的提示。
- 产品能够识别并管理自己拥有的后台运行组件，不要求用户猜测或手动寻找不可见的残留进程。
- 覆盖升级继续保留既有用户数据、桌面设置、系统凭据、开机自启选择和单一安装身份。
- 已存在 production 安装时，安装器根据已安装版本提供明确的升级、修复、迁移或卸载语义，不能通过普通目录选择留下第二处 production 程序目录。
- 用户显式更改安装位置时，只迁移产品程序文件和系统入口；用户数据、设置、日志与系统凭据继续使用既有平台路径，不随程序目录搬迁。
- 安装态能够验证并导出桌面壳、运行时和资源的安装身份，使现场诊断可以直接判断是否发生版本错配或不完整安装。
- Windows 安装器默认使用简体中文，同时支持英文，并允许用户在安装开始前选择界面语言。
- 把真实安装与覆盖升级的关键约束固化为标准脚本、自动化检查和 Agent 工作流门禁，避免后续仅凭代码检查或文件存在就宣称安装问题已解决。

## 范围

### 包含

#### 安装与覆盖升级完整性

- 适用于当前 Windows x64 普通安装包、trusted-beta 安装包和本地测试安装包。
- 新装、同一安装身份上的更高版本覆盖升级，以及从当前固定运行时目录布局升级到新布局，都必须有明确且一致的结果。
- 安装流程必须识别会影响本次升级的 agent-friend 桌面壳、冻结运行时及其产品自有子进程，而不能只依赖用户是否看到旧窗口。
- 在开始替换产品文件前，应安全停止本次升级实际涉及的产品自有运行组件；无法安全处理时应停止安装并说明被阻塞的对象和下一步操作。
- 不能把“忽略某个无法写入的核心文件”视为成功升级。核心文件缺失、无法替换、校验失败或身份不一致时，安装不得进入可正常启动的新版本状态。
- 成功安装必须有可验证的完整性状态。仅检查路径存在或进程能够启动不足以证明升级完成。
- 失败路径不得删除或改写 sessions、memory、personas、IM 数据、桌面设置、系统 keyring 凭据等用户资产。
- 在无法保留旧版本继续运行的失败场景中，产品必须阻止不完整版本继续工作，并向用户提供可行动的恢复信息，不能静默带病运行。

#### 产品进程生命周期

- 桌面壳仍是随包后端运行时的生命周期所有者。
- 正常退出、异常退出和升级关闭都应处理由该桌面壳启动的产品自有运行时进程及其子进程。
- 进程处理范围必须以产品所有权和本次安装影响为边界，不得因为进程名称相似而终止用户的无关程序。
- 已存在的旧版本残留进程或当前版本异常退出，不应让下一次安装在没有明确提示的情况下写出混装目录。

#### 安装身份与运行时一致性

- 每个可安装构建必须具有可核验的安装身份，至少能够区分产品版本、构建来源和具体构建。
- 桌面壳、冻结运行时和随包资源必须能够证明自己属于同一个安装身份。
- 桌面壳在接受后端“已就绪”状态前，必须确认对方是当前安装所期望的运行时，而不是端口上恰好存在的旧进程或其他进程。
- 身份缺失、无法读取或不一致时，应进入明确的安装/运行时错误状态，不能继续提供表面正常但实际混装的服务。
- 用户导出的诊断包必须包含足够的非敏感身份与完整性信息，用于判断当前桌面壳、实际运行时和随包资源是否一致。

#### 兼容与迁移

- 已安装 0.1.7 及当前固定 `runtime` 目录布局的用户，可以直接运行新版安装程序完成升级，不要求先卸载旧版本。
- 覆盖升级后仍只保留一个 agent-friend 产品安装实例，不产生重复的应用入口或开机自启项。
- 已登记 production 安装存在时，目标目录等于原目录则执行原地升级或修复；目标目录不同时必须进入显式的安装位置迁移流程，成功后旧程序目录不再保留为第二处安装。
- 安装位置迁移只处理程序目录内的桌面壳、冻结运行时、版本化 payload、内置资源、receipt 与卸载文件，并更新卸载注册表、快捷方式和开机自启指向；不得移动或删除平台用户数据、设置、日志和 keyring 凭据。
- 已安装版本高于安装包版本时，安装器必须在任何进程停止、文件写入或系统状态修改前终止，并显示“当前已安装的 agent-friend 是更新的版本，此安装包无法继续”。不得提供继续安装、覆盖、迁移或卸载入口。
- 既有用户数据、桌面设置、系统 keyring 凭据、trusted-beta 凭据导入语义和开机自启选择保持可用。
- 卸载继续清理产品安装内容和失效启动项，但不扩大到现有产品约定之外的用户资产。

#### 安装器本地化

- 安装器至少提供简体中文和英文两种完整界面语言。
- 首次运行且没有已保存的用户选择时，安装器默认使用简体中文，不因 Windows 当前界面语言为英文而自动改成英文。
- 交互式安装允许用户在实际安装前显式选择语言；用户已明确选择过英文时，后续升级可以延续该选择。
- 项目自定义的进程占用、完整性失败、恢复建议和 trusted-beta 警告必须与安装器主体使用同一语言，不能出现主体中文、自定义错误仍为英文的割裂状态。
- 无界面的自动化安装模式不得因语言选择或交互提示挂起，并应通过稳定的失败结果让调用方判断是否安装成功。

#### 诊断与交付门禁

- 标准打包入口必须对安装身份、运行时完整性信息和安装器语言资源执行确定性检查。
- 自动化测试必须覆盖安装状态判定、身份一致性、异常进程与失败路径中可稳定断言的逻辑。
- 每次改变 Windows 安装布局、核心运行时内容、进程关闭策略、安装身份或安装器钩子时，都必须执行与影响相匹配的真实安装或覆盖升级验收，不能只运行单元测试或检查安装包已生成。
- 真实升级验收必须使用项目标准脚本和实际生成的安装程序，覆盖正常升级和至少一个核心文件被占用的失败/恢复场景。
- 不把虚拟机作为本需求的默认验收前提。同机自动验收必须使用与真实产品完全隔离的测试安装身份、安装目录、卸载注册表、快捷方式、启动项、用户数据、日志、端口和凭据命名空间。
- 高频自动故障注入不得修改当前真实 agent-friend 安装；它应使用同一 Windows 账户下的隔离测试身份。隔离矩阵通过后，必须在当前账户对真实产品身份执行一次与普通用户相同的覆盖升级验收。Coding Agent 执行前仍需说明会停止和更新当前安装并取得用户授权；首次验证新安装机制时可以额外保留安装目录备份作为开发安全网，但备份不是用户日常升级的前置条件。
- 项目 Rule、Skill 和脚本必须对上述门禁保持一致：脚本负责可执行的机器校验，Rule 约束不能绕过的边界，Skill 编排构建与验收；Agent 不得自行用较弱检查替代既定门禁。
- 未执行、被环境阻塞或失败的真实安装验证必须如实记录，不能被标记为通过，也不能仅凭代码推断关闭相关验收项。

### 不包含

- 修复或关闭 `docs/issues/043-windows-resume-global-black-screen/`；本需求只保持证据边界，不改变其根因状态。
- 应用正文、设置页或聊天界面的全局多语言系统。
- 应用内更新检查、下载安装包、更新服务器、发布源或静默后台更新。
- 将 Windows 安装技术迁移为 MSIX、MSI 或新的外部 bootstrapper。
- 保证任意 Windows 安装器都具备操作系统级、全目录的原子事务与自动回滚。
- 要求开发者准备虚拟机、Windows Sandbox 或额外的 Windows 本地账户才能执行标准安装验收。
- 支持 Windows ARM64、macOS 或 Linux 安装包。
- 同时安装多个 agent-friend 产品版本或多个更新通道。
- 终止 Chrome、系统 Python、开发者自行启动的无关服务，或其他不属于当前产品安装的进程。
- 改变用户数据、设置、日志和系统凭据的现行平台路径约定。

## 需求

### R-1 · 成功结果必须完整

- 安装程序只有在本次安装的所有核心组成均写入、校验并可被同一安装身份识别后，才能报告成功。
- 任一核心组成被跳过、仍被占用、校验失败或来自不同构建时，安装结果必须失败或保持在可明确恢复的非激活状态。
- 启动阶段必须再次验证安装状态，防止安装器异常退出、用户误点“忽略”或磁盘内容被事后破坏时静默运行混装版本。

### R-2 · 精确处理产品自有进程

- 安装前检查应覆盖会锁定待升级文件的产品自有运行组件，而不只检查主桌面窗口。
- 安装程序应优先执行受控关闭；无法关闭时，在修改核心文件前失败并提供对象明确、可重试的提示。
- 产品自有运行时在桌面壳正常或异常结束后不应长期成为孤儿进程。
- 任何强制结束行为都必须限制在已证明由 agent-friend 拥有且阻塞本次操作的进程范围内。

### R-3 · 壳、运行时与资源身份一致

- 桌面壳选择和启动的运行时必须属于当前安装身份。
- 运行时就绪响应必须能证明实际响应者的身份；只证明端口可连接或服务返回通用 ready 不足以通过。
- 当前安装所使用的核心资源必须可追溯到同一构建，缺失或错配时给出稳定错误。
- 身份信息不得包含 API secret、用户消息或其他敏感用户内容。

### R-4 · 旧安装可安全迁移

- 当前已分发的固定运行时目录安装可以直接升级到新版本。
- 迁移过程必须兼顾旧运行组件仍在运行、旧安装不完整和首次重试等状态。
- 升级完成后旧布局不会继续被误选为当前运行时，也不会让诊断结果把旧文件误报成实际运行版本。

### R-5 · 失败可理解、可恢复

- 交互式安装失败应明确说明失败阶段、受影响对象和用户可以采取的动作。
- 失败提示不得把正常用户预设为“没有关闭旧程序”；当存在不可见后台组件时，应由产品负责识别并准确说明。
- 重试必须重新验证真实状态，不能在核心文件仍未就绪时直接继续到成功。
- 自动化安装应以稳定的非零失败结果结束，不能停在等待人工点击的对话框。

### R-6 · 中文默认且中英文安装体验一致

- 首次运行安装器时，语言选择和后续安装页面必须默认使用简体中文；英文 Windows 上也保持该默认值。
- 简体中文和英文必须覆盖安装、升级、卸载及项目自定义提示的关键路径。
- 语言选择只影响安装器展示，不改变安装身份、路径、用户数据或升级行为。
- 新增项目自定义安装提示时，必须同时提供两种语言；缺少任一语言应被机器检查阻止。

### R-7 · 诊断能够区分混装与正常安装

- 诊断包应分别记录当前桌面壳构建、预期运行时、实际响应运行时和核心资源完整性状态。
- 诊断结果应能区分“安装完整但运行时启动失败”“端口由错误进程占用”“壳与运行时身份不一致”和“安装内容本身不完整”。
- 安装失败后的诊断不能仅采集已经成功启动的新桌面壳，而缺少本次安装状态和实际运行时身份。

### R-8 · Coding Agent 不得弱化安装验证

- 安装相关代码变更必须先标注影响类型，并据此选择自动化检查、安装器生成验证和真实安装/升级验收。
- 只要改动可能影响安装时写入、产品进程生命周期、安装身份、运行时选择或安装器提示，就不能以“测试通过”“文件存在”或“本机能启动”替代真实覆盖升级证据。
- 标准工作流必须让 Agent 在执行前展示将验证的旧版本、新版本、安装包类型、语言和故障场景，在执行后记录实际结果与未覆盖项。
- 同机高频 smoke 默认只能操作专用测试身份。最终真实升级验收应按普通用户路径直接升级当前账户的既有安装；Coding Agent 在执行前必须说明影响并取得用户明确同意，但不得把虚拟机、额外 Windows 用户、手工备份或复杂预检变成产品的正常升级步骤。
- Agent 不得手工拼接另一套安装路径、身份算法或验证命令绕过项目标准入口。
- 完整源码身份与安装行为验证资格必须分离：文档、Rule、Skill、进度记录或测试等不会进入安装包的变化，不应单独迫使同一安装行为输入重跑完整候选矩阵；产品代码、安装器、运行时、依赖、版本、打包配置、矩阵契约或构建环境变化时必须使既有报告失效。
- 是否可以复用既有矩阵只能由标准脚本比较机器报告中的安装包验证指纹决定；Coding Agent 不得凭 Git commit、完整源码 hash、文件名、时间或主观判断宣称“代码相同”。系统不能确认影响范围时按需要重跑处理。
- 门禁失败、验证未执行或证据不足时，Agent 必须停止宣称需求已验收或问题已解决。

### R-9 · 已安装产品交互与唯一安装位置

- 没有同身份旧安装时，安装器显示普通“安装”流程并允许选择程序目录。
- 已安装版本低于安装包版本时，主操作是升级原安装；可提供次级“更改安装位置”入口，但不得把“是否先卸载”这类实现细节作为普通用户决策。
- 已安装版本等于安装包版本时，提供修复/重新安装、迁移安装位置、卸载和取消；不使用暗示多实例的“Add/Install”文案。
- 已安装版本高于安装包版本时，只允许关闭安装器，使用固定双语提示拒绝降级；silent/passive 模式稳定返回非零结果。
- 安装位置迁移必须把旧目录与新目录作为同一事务的两个程序根处理：新程序完整性未通过时保留旧安装；切换成功后更新所有系统入口并清理旧程序目录，最终不得有两处受管理的 production 安装。
- 迁移不得调用会删除用户数据、设置、日志或凭据的卸载语义。迁移前后这些平台 namespace 保持不变。

### R-10 · 可信内测包必须形成真实的可升级版本序列

- 面向可信测试者日常分发的带凭证安装包属于 trusted-beta 预发布渠道，不得标记为不可分发的 local-test，也不得消耗稳定 release 版本。
- 每个开发周期由用户显式指定一次下一稳定版本；标准脚本只自动分配该目标下单调递增的 beta 日期/序号，不得自行决定 major、minor 或 patch。
- stable release、trusted-beta 和 local-test 必须是显式互斥的构建意图；裸打包命令不能默认为正式发布。只有用户明确要求正式发布时才能生成 stable release。
- trusted-beta 的精确 SemVer 必须进入安装器版本、桌面壳/运行时 build identity、Tauri Windows 版本和应用内部版本判断。build ID 只用于追溯与完整性，不参与升级顺序。
- 目标版本缺失、过期、系统时钟导致版本不单调、源码 dirty、目标制品已存在或候选不高于已有正式制品时，可信内测构建必须在读取凭据和生成安装包前失败。

## 验收标准

- [ ] AC-1：在没有同身份旧安装的 Windows x64 环境中，普通本地测试安装包能够以简体中文和英文分别完成交互式安装、启动和卸载；首次启动在中文和英文 Windows 上都默认选中简体中文，语言选择器可切换到英文。
- [ ] AC-2：从现有 0.1.7 固定运行时目录安装直接覆盖升级到候选版本，不先卸载；升级后仍只有一个产品实例，sessions、memory、personas、IM 数据、桌面设置、系统 keyring 凭据和开机自启选择保持可用。
- [ ] AC-3：旧桌面壳仍在运行时启动升级，安装程序会在写入核心文件前识别并受控关闭相关产品组件；若关闭失败，则在核心文件被修改前终止并显示当前语言的可行动提示。
- [ ] AC-4：桌面壳已经退出、但旧冻结运行时或其产品自有子进程仍锁定核心文件时，升级不会报告成功或留下可启动的混装版本；解除阻塞后重试能够完成升级。
- [ ] AC-5：模拟核心运行时文件缺失、被跳过、损坏或来自旧构建时，安装完整性检查不能通过；桌面壳拒绝把该运行时视为就绪，并给出可诊断的明确状态。
- [ ] AC-6：Windows 上正常退出和可控模拟的异常退出后，由桌面壳启动的冻结运行时进程树均被回收；不会影响不属于当前 agent-friend 实例的同名或无关进程。
- [ ] AC-7：成功运行的安装态能够证明桌面壳构建、预期运行时、实际就绪运行时和核心资源属于同一安装身份；诊断包包含这些非敏感字段及一致性结论。
- [ ] AC-8：端口已由旧版运行时或其他进程占用时，桌面壳不会仅凭通用 ready 响应进入正常状态，并能区分身份错配与普通启动失败。
- [ ] AC-9：简体中文和英文均覆盖项目自定义的进程占用、安装完整性、恢复建议和 trusted-beta 警告；自动化检查会阻止只新增单一语言提示。
- [ ] AC-10：无界面的自动化安装在需要人工处理的阻塞场景中不会挂起，并返回稳定的非零结果；成功场景不弹出语言或错误交互。
- [ ] AC-11：普通包、trusted-beta 包和本地测试包继续保持现有隔离、凭据与制品治理语义；trusted-beta 升级后不会泄露 seed，也不会丢失已导入的系统凭据。
- [ ] AC-12：安装状态判定、身份匹配、运行时选择、进程所有权边界和本地化完整性中可稳定断言的行为都有自动化测试，项目全量检查通过。
- [ ] AC-13：使用项目标准脚本和实际生成的 Windows 安装程序，在当前 Windows 账户下以专用测试身份完成隔离升级矩阵，至少包括旧固定布局 → 候选版本升级、主壳运行中升级、孤儿运行时锁文件失败/恢复、身份错配拒绝启动和中英文安装；测试不修改真实 agent-friend 的安装目录、注册表、快捷方式、启动项、数据、日志、端口或凭据命名空间，报告记录安装包身份、环境、结果及未覆盖风险。
- [ ] AC-14：在隔离升级矩阵通过后，当前账户的既有 0.1.7 安装可以像普通用户一样直接运行候选安装包完成一次真实覆盖升级，不要求 VM、额外 Windows 用户或用户手工备份；Coding Agent 执行前单独取得操作授权，验证过程不读取、导出或改写真实凭据内容。
- [ ] AC-15：项目打包 Rule、package-release Skill、脚本帮助和机器门禁对安装影响分类与必跑验证保持一致；Coding Agent 无法仅凭文件存在检查或 mock 结果把真实升级 AC 标为完成。
- [ ] AC-16：交互式安装器根据未安装、旧版本、同版本和更新版本四种状态分别显示安装、升级、修复/重新安装和拒绝降级的产品语义；不再显示暗示多实例或暴露实现细节的 “Add/Install”“不卸载继续安装”。
- [ ] AC-17：production 已登记在目录 A 时，用户选择目录 B 会进入显式迁移；成功后程序文件、卸载注册表、快捷方式和开机自启均只指向 B，A 不再保留为第二处安装，用户数据、设置、日志和 keyring namespace 及内容保持原位。
- [ ] AC-18：已安装版本高于安装包版本时，交互式安装显示“当前已安装的 agent-friend 是更新的版本，此安装包无法继续”并只允许关闭；silent/passive 返回稳定非零结果，且安装目录、运行进程、注册表、快捷方式和自启均未改变。
- [ ] AC-19：候选报告包含不含凭据的安装包验证输入指纹；相同安装行为输入和构建环境的 production ordinary/trusted-beta 构建可以显式复用已验证矩阵，只有文档、Rule、Skill、进度记录或测试变化时无需重跑；任一生产/打包输入、矩阵契约或构建环境变化都会由脚本拒绝旧报告，无法分类的变化安全地要求重跑。
- [ ] AC-20：配置下一稳定版本 `X.Y.Z` 后，连续可信内测构建自动得到严格递增且低于 `X.Y.Z` 的 `X.Y.Z-beta.<UTC YYYYMMDD>.<sequence>`；它能升级前一可信版本，最终 stable release 又能升级所有同目标 beta。裸 `all`、dirty 可分发内测、自动 major/minor/patch、同版本 build ID 冒充升级和分发 local-test 均被机器门禁阻止。

## 证据边界

- 用户截图确认安装程序在写入冻结运行时 executable 时遇到文件占用；截图不能证明占用者身份。
- 事后诊断确认新版桌面壳已经运行，并表明现有诊断缺少实际冻结运行时身份；它不能完整还原安装过程，也不能单独确认最终磁盘上每个文件的来源。
- “新版桌面壳 + 旧版运行时”的混装风险有较强代码与时间线支持，但在补齐运行时身份之前保持为高置信推断，不写成已确认事实。
- 本次安装失败晚于 issue 043 报告的黑屏事故，因此不能作为黑屏根因证据。

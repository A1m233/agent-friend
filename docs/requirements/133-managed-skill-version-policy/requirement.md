# 受管 Skill 的更新策略与安装版本分离

## 状态

CONFIRMED

## 背景

用户希望一个受管 GitHub Skill 持续跟随 main，并提供当时提交号供核验。Agent 使用 `--update <name> --ref <commit>` 后，安装器把提交号保存为后续更新来源。次日普通更新仍检查该提交，输出 Already up to date，导致“主干已经最新”的错误结论。

当前源码确认了以下机制，但尚未绑定历史案例的运行版本或完整日志：

- 本次 ref 与长期更新来源共用一个字段，更新成功后覆盖来源记录。
- 候选内容相同时，事务提前返回，可能遗漏用户明确要求的来源变更；现有测试也固定了这一行为。
- 来源记录保存 ref 和包摘要，没有实际解析到的 commit。
- 无变化输出没有明确区分跟踪、固定和历史意图不明的来源。

本需求解决通用版本与更新语义，不针对 maa-daily 添加特例。

## 目标

- 区分长期更新策略、本次实际安装版本和独立的版本核验条件。
- 普通更新不会因为核验用提交号而意外永久固定在历史版本。
- 用户有意固定版本时得到稳定、明确且可审计的结果。
- 更新结果准确说明实际检查的来源及安装版本，不把内容相同表述为未检查来源的最新状态。

## 范围

### 包含

- 受管 GitHub Skill 首次安装、显式更新及接管路径中的版本选择与来源记录。
- 跟踪分支、显式固定版本、本次版本选择和核验条件的清晰边界。
- 旧参数与旧来源记录的兼容策略；意图不明的历史来源不得被自动改为 main。
- 内容不变时的来源策略和版本证据保存，以及真正无变化时的幂等行为。
- 安装器说明、Agent 工具指引、可信更新回执与同轮生效链的协调。
- 确定性回归测试及现有保护机制的回归验证。

### 不包含

- 修改用户当前已安装 Skill 的内容、来源记录或固定状态。
- 运行 MAA、游戏或目标 Skill 的业务任务。
- 后台或批量更新、Skill 商店、新增管理界面或非 GitHub 来源。
- 对历史 Agent 行为作缺少日志支持的模型侧归因。
- 自动执行真实 LLM 验证、发布安装包或部署。

## 关键信息

- 跟踪来源用于决定后续普通更新检查哪里；实际安装版本用于核验与审计；完整包摘要继续用于安装完整性及本地修改检测。
- “必须等于某提交”与“分支已包含某提交”是不同条件，不能擅自互换。
- 历史来源无法证明用户有意固定，也不能仅通过字符串形状推断为跟踪分支。
- 内容相同不代表仓库版本、更新策略或来源相同。
- 与需求 129 的同轮生效能力兼容：策略或审计信息变化不应伪造内容变化，真实内容更新仍可被可信回执识别。
- 具体参数名、记录格式、迁移方式和错误结构在技术方案阶段确认。

## 验收条件

- [x] **AC-1 持续跟踪**：跟踪分支的 Skill 经核验或单次指定版本操作后，后续普通更新仍按其明确的长期策略检查，不意外固定。
- [x] **AC-2 显式固定**：用户可明确固定版本；后续普通更新保持固定，输出明确说明固定版本及检查范围，不宣称主干最新。
- [x] **AC-3 版本证据**：成功安装、更新和无变化结果明确展示更新策略、实际安装 commit 与内容摘要；无法取得必要版本证据时不伪造成功。
- [x] **AC-4 核验隔离**：核验条件不改变长期来源；不满足条件时明确失败，不推进安装内容或来源记录。
- [x] **AC-5 历史兼容**：可读取已有来源记录，保留原来源语义；历史 commit ref 意图不明时明确提示，只有用户显式选择才转换为跟踪或固定策略。
- [x] **AC-6 元数据更新**：候选内容相同但用户明确改变来源策略时，正确保存变化；来源、版本和内容均相同时不重复改写。
- [x] **AC-7 保护与恢复**：本地修改保护、同源限制、并发检测、候选校验、失败恢复与安装完整性校验不回归；元数据写入失败不产生虚假成功。
- [x] **AC-8 入口一致**：首次安装、接管、更新及下载/git 路径遵守一致的版本契约；旧调用的行为变更有明确迁移指引。
- [x] **AC-9 Agent 与同轮生效**：使用说明和 Agent 指引区分核验、跟踪、固定及实际版本；新参数和结果仍被可信回执链正确处理，内容未变时不反复加载正文。
- [x] **AC-10 验证与隔离**：新增语义及相关保护机制有确定性测试，项目规定检查通过；验证使用隔离目录，不修改现有 Skill 安装状态，不运行 MAA 或游戏。

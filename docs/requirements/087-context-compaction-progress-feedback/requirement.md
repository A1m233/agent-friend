# 上下文压缩进度与持久记录

## 状态

CONFIRMED

## 背景

长会话在处理新消息前可能需要先压缩上下文。压缩耗时较长时，桌面端只能显示通用等待状态，IM 端则可能在首段回答出现前长时间没有可理解的反馈，用户无法判断系统仍在工作、已经卡住，还是消息没有送达。

上下文压缩本身已经是会话生命周期中的重要活动。它不仅需要在执行期间提供即时反馈，还应在成功后作为历史事实留在桌面对话时间线中，帮助用户理解一次较长等待发生了什么。该活动不属于用户或助手的自然语言对话，也不应进入后续模型上下文。

本需求承接 [Issue 051](../../issues/051-context-compaction-progress-invisible/)，补齐实际压缩开始、成功、失败和取消时面向桌面端与 QQ 私聊的用户反馈。

## 目标

- 实际进入上下文压缩后，及时向用户说明系统正在整理较长对话，避免把正常工作误判为卡死或断线。
- 压缩成功后，在桌面对话时间线中留下可持久读取的完成记录，并在重新加载会话后继续展示。
- 让 QQ 私聊在压缩等待期间获得受控的临时进度，同时保持最终回答仍通过原有流式消息自然呈现。
- 让压缩进度与完成结果具备稳定、可诊断、可确定性验证的行为边界。

## 范围

### 包含

- 只在本轮实际进入上下文压缩时发布明确的压缩活动；普通上下文准备和未触发压缩的对话不显示压缩提示。
- 桌面端在压缩进行期间即时展示用户可理解的进行中状态，例如“正在整理较长对话……”。
- 压缩成功后，将对应的进行中状态收束为完成记录，例如“已整理较长对话”，并按发生顺序保留在当前会话的时间线中。
- 桌面端切换会话、刷新前端或重启应用后，仍能从会话历史恢复并展示成功压缩记录。
- 同一会话多次成功压缩时，每次压缩都保留各自的完成记录，时间顺序与实际发生顺序一致。
- 压缩失败或取消时可靠结束进行中状态，不留下虚假的成功记录；失败原因保留在可诊断信息中。
- QQ 私聊在实际压缩开始后，通过当前回复所使用的原生流式消息显示临时进度；产生最终回答后，由同一条流式消息继续更新为回答内容。
- 为运行时活动、桌面端投影、会话恢复和 QQ 流式更新提供确定性自动化验证，并允许在无需真实 LLM 或超长自然对话的受控条件下触发压缩。

### 不包含

- 改变上下文压缩算法、摘要质量、触发阈值、性能或可靠性策略。
- 为普通上下文准备、模型首 token 等待、工具执行或其它长耗时阶段统一增加进度反馈。
- 解决 QQ 原生流已经开始后停留在单个圆点或停止更新的问题；该现象继续由独立问题跟踪。
- 在 QQ 中额外发送或永久保留“已完成压缩”消息；QQ 的压缩提示只服务于本轮回答产生前的临时反馈。
- 向用户展示压缩摘要正文、内部上下文结构、精确 token 数、百分比或剩余时间估计。
- 将压缩活动伪装成用户消息或助手消息，或让其参与后续模型上下文。

## 关键信息

- 压缩活动是会话时间线中的系统活动，不是自然语言对话内容。桌面端可以持久展示它，但模型输入不得把它当作用户或助手发言。
- “进行中”只表示实际压缩尚未结束；“已完成”只表示压缩已经成功。失败、取消或未真正触发压缩时不得产生成功记录。
- 进行中状态需要尽早出现，不能等到压缩结束或模型请求开始后才补发；完成记录必须与对应的进行中活动保持同一语义身份。
- 持久记录只表达用户需要理解的事实，不泄露摘要内容、内部策略或可能快速失真的精确进度。
- 桌面端与 QQ 使用同一压缩生命周期语义，但呈现方式不同：桌面端保留成功历史，QQ 只在当前流式回复中临时展示。
- 验收应以可控触发、可暂停和可恢复的压缩过程为主，不依赖偶然达到阈值的真实长会话或一次长达数十秒的线上等待。

## 验收条件

- [ ] AC-1：本轮实际开始上下文压缩后，在压缩完成前即可观察到明确的进行中活动；未触发压缩的普通回合不会产生该活动。
- [ ] AC-2：桌面端在压缩进行期间展示“正在整理较长对话”或等价的明确提示，不继续只显示无法解释当前工作的通用等待状态。
- [ ] AC-3：压缩成功后，对应的进行中活动转为完成记录；切换会话、刷新前端或重启应用并重新加载该会话后，完成记录仍然可见。
- [ ] AC-4：同一会话发生多次成功压缩时，桌面时间线保留多条相互独立的完成记录，顺序与实际压缩顺序一致，不覆盖或合并历史记录。
- [ ] AC-5：压缩失败或取消后，进行中状态可靠结束且不产生成功记录；会话仍可按既有错误或取消语义继续处理，失败原因可通过诊断信息定位。
- [ ] AC-6：压缩活动不作为用户或助手消息进入后续模型输入，也不向用户暴露摘要正文、精确 token 数、百分比或剩余时间估计。
- [ ] AC-7：QQ 私聊在实际压缩开始后，通过当前回复的同一条原生流式消息先展示明确进度，并在首段回答产生后继续更新为最终回答，不额外发送重复的静态消息。
- [ ] AC-8：QQ 私聊在压缩完成后不单独保留“已完成压缩”消息；未触发压缩、压缩失败和取消时不会遗留错误的进度占位。
- [ ] AC-9：桌面端和 QQ 对压缩生命周期的消费不会改变非压缩回合、正常文本流、工具调用、错误和取消的既有行为。
- [ ] AC-10：自动化测试可以使用受控上下文窗口与可暂停的压缩实现，分别验证“开始事件先于完成”“成功后持久恢复”“失败或取消不留成功记录”和“QQ 同消息替换”，不要求调用真实 LLM 或构造不可控的超长会话。

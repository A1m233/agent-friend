# GitHub Skill 手动更新

## 状态

CONFIRMED

## 背景

agent-friend 已通过 builtin `skill-installer` 支持从 GitHub 安装 Skill，但当前安装脚本在目标目录已经存在时直接拒绝，`skill-installer` 也明确不负责更新已有 Skill。用户要求更新已经安装的 GitHub Skill 时，系统没有受支持的确定性路径。

[issue 054](../../issues/054-malformed-tool-call-misreported-as-runtime-boundary/) 已修复非法工具参数被误报为运行边界的问题，但同时记录并保留了上述独立能力缺口：Agent 曾在缺少真实更新能力时编造不存在的覆盖参数，既没有完成用户目标，也无法安全处理来源、失败和本地修改。

本需求只补齐该真实场景所需的最小更新闭环，不把裸 Skill 安装扩张成通用包管理、市场或自动更新系统。

## 目标

- 让用户能够通过现有 builtin `skill-installer` 显式更新单个、由 agent-friend 管理的 GitHub Skill。
- 让 GitHub Skill 的安装来源和当前内容版本可追溯，并只允许已确认的同源原位更新。
- 在替换现有 Skill 前完成隔离下载和有效性校验，任何失败均保留当前可用版本。
- 识别已受管理 Skill 的本地修改，避免更新时静默覆盖用户改动。
- 让重复更新保持幂等，并复用现有 catalog watcher 在无需重启的情况下发现成功更新。
- 为功能上线前已经存在、缺少来源记录的 GitHub Skill 提供一次性、需用户明确确认的接管路径，使 issue 054 暴露的既有用户场景能够真正闭环。

## 范围

### 包含

#### 单个 GitHub Skill 的显式更新

- 更新由用户明确发起，一次面向一个已安装 Skill。
- 更新继续通过 builtin `skill-installer` 及其确定性脚本完成；Agent 不手工拼装 Skill 包，也不编造脚本未支持的参数。
- 更新对象仅限 agent-friend 自身个人 Skill 目录中、来自 GitHub 仓库的普通目录 Skill。
- 支持沿用现有 GitHub 访问方式处理公开仓库，以及当前凭据环境已经能够访问的私有仓库；本需求不新增凭据获取或管理能力。

#### 最小来源与版本记录

- agent-friend 从 GitHub 成功安装 Skill 后，记录足以精确指回来源的仓库身份、仓库内 Skill 路径和使用的 ref。
- 同时记录已安装 Skill 包的完整内容版本；内容版本必须能够稳定区分两个不同的包内容，而不能只依赖可移动的分支名或用户可编辑的版本文案。
- 来源与内容版本属于 agent-friend 的安装管理状态，保存在单个 Skill 包之外；复制、移动或共享原始 Skill 目录时，不应夹带 agent-friend 私有的安装记录。
- 更新成功后，来源记录和内容版本与新安装内容保持一致；失败时二者均保持原值。
- 本需求只保留当前已安装版本所需的最小记录，不维护历史版本列表。

#### 同源更新

- 已受管理 Skill 只能由相同 GitHub 仓库、相同仓库内 Skill 路径的新内容原位更新。
- ref 属于可追溯信息；用户明确指定新的 ref 时仍必须保持仓库和 Skill 路径身份不变，并记录实际采用的 ref 和内容版本。
- 不同仓库或不同 Skill 路径不能借“更新”覆盖现有 Skill；系统应说明来源不一致并停止。
- 更新结果必须向用户说明 Skill 名称、来源以及是否已更新、已经是最新或未能更新。

#### staging 校验与失败保护

- 新内容在接触现有安装目录前，先完整下载到隔离的临时区域。
- staging 中的候选包必须通过与正式 catalog 兼容的 Skill 格式、入口和可发现性校验；发现无效 `SKILL.md`、名称不一致、不可读内容或其它阻止 catalog 使用的问题时不得替换旧版。
- 下载、鉴权、解包、路径安全、校验或替换任一步骤失败时，现有 Skill 目录仍保持更新前的可用内容，来源与版本记录不前移。
- staging 和更新过程不自动执行候选 Skill 携带的脚本，也不因其声明扩大权限。

#### 本地修改冲突

- 更新前比较当前已安装内容与上次成功安装或更新记录的内容版本。
- 二者不一致时视为存在本地修改或无法解释的内容漂移；首次更新尝试必须停止并向用户说明将被替换的 Skill、同源 GitHub 来源以及继续后本地修改会丢失。
- 用户未确认、拒绝或取消时，现有内容和安装记录保持不变。
- 用户在看到上述事实后再次明确同意放弃本地修改时，系统允许沿用正常 staging、校验和失败恢复流程完成同源覆盖更新。
- 显式覆盖只处理已受管理 Skill 的同源更新，不能改变仓库或 Skill 路径，也不能绕过无来源旧 Skill 的独立接管确认。
- 本期不提供 diff 展示、三方合并、持久备份、补丁迁移或自动冲突解决。

#### 无来源旧 Skill 的一次性接管

- 当目标 Skill 已存在但没有本需求定义的来源与内容版本记录时，系统不得把它静默视为同源安装。
- 系统应明确说明无法验证其原始来源、也无法区分旧版本和本地修改，并展示用户本次提供的 GitHub 来源与将被替换的目标 Skill。
- 只有用户在看到上述事实后再次明确同意，系统才可按正常 staging 和校验流程替换旧内容，并在成功后建立来源与内容版本记录。
- 用户未确认、取消操作或任一步骤失败时，旧 Skill 保持不变。
- 一次性接管只解决功能上线前的既有安装迁移，不成为绕过受管理 Skill 同源和本地修改检查的通用覆盖入口。

#### 幂等更新与 catalog 热刷新

- 候选包内容版本与当前已记录内容版本相同时，更新返回“已是最新”，不重写 Skill 内容，也不制造无意义的 catalog 版本变化。
- 成功替换后复用现有 catalog watcher；用户无需重启应用、Agent 或会话，刷新完成后的后续用户轮能够发现并激活新内容。
- 正在执行的用户轮继续使用该轮开始时冻结的 Skill snapshot，不因中途更新替换已经选定的指令或脚本。
- 更新后的新内容不回写或篡改已经进入会话历史的旧 Skill 正文。

#### 诚实行为与诊断

- `skill-installer` 的指引必须明确区分首次安装、已受管理更新、已经是最新、本地修改冲突、异源冲突和无来源旧 Skill 接管。
- Agent 只能在确定性脚本成功完成相应动作后声称安装、接管或更新成功。
- 不具备更新条件时，Agent 应如实报告缺失条件或失败原因，不得编造 `--force`、虚构未来自动执行或把普通命令结果当作 Skill 更新成功证据。
- 核心安装记录、更新、接管、冲突、失败保护、幂等和 catalog 刷新路径具备确定性自动化回归覆盖；issue 054 中“用户要求更新已有 Skill”的真实场景作为行为回归锚点。

### 不包含

- `~/.agents/skills` 等跨客户端共享 Skill 目录的安装接管或更新。
- 手工创建、符号链接、目录链接、builtin、项目级或非 GitHub Skill 的更新管理。
- 批量更新、更新全部 Skill、检查是否有更新、轮询、启动时检查或后台自动更新。
- Skill marketplace、在线目录、推荐、搜索、评分或发布流程。
- 签名发布、签名校验、信任分级、供应链审计或第三方安全扫描服务。
- GitHub token、SSH key、Git credential 或其它凭据的创建、保存和管理。
- 历史版本列表、版本选择、长期旧版缓存和用户主动回滚。
- 本地修改的 diff 展示、静默或未经确认的覆盖、三方合并、持久备份、补丁迁移或自动冲突解决。
- Skill 管理、更新提示、版本浏览或冲突处理的专用桌面 UI。
- 自动执行候选 Skill 的脚本，或根据候选 Skill 内容扩大文件、网络和命令权限。

## 关键信息

- 本需求来源于 issue 054 已修复事故中明确保留的产品能力缺口；issue 054 的运行时错误语义已经关闭，本需求不重新实现或重新关闭该修复。
- “同源”以 GitHub 仓库身份和仓库内 Skill 路径为核心；分支、tag 或 commit 等 ref 是获取和追溯维度，不得改变目标 Skill 的来源身份。
- “内容版本”表示整个已安装 Skill 包的稳定内容身份，至少覆盖 `SKILL.md` 及包内实际安装的其它资源；具体摘要算法和记录位置在技术方案中确定。
- 安装管理状态与 Skill 包内容分离；具体 lock 文件位置、schema 和一致性写入方式在技术方案中确定。
- “本地修改”只表示当前安装内容偏离上次成功记录，系统不需要推断改动是谁、何时或出于什么目的产生。
- “失败保留旧版”要求更新失败后旧 Skill 仍可被 catalog 正常发现和使用；不等于提供面向用户的历史版本或回滚功能。

## 验收条件

- [ ] **AC-1 首次安装可追溯**：通过 builtin `skill-installer` 从 GitHub 安装单个 Skill 后，系统记录其仓库、仓库内路径、ref 和完整包内容版本；catalog 能正常发现该 Skill。
- [ ] **AC-2 同源更新成功**：用户明确要求更新已受管理 Skill 时，系统从记录指向的同一仓库和 Skill 路径取得新内容，完成 staging 校验后替换旧版，并报告旧、新内容版本和来源。
- [ ] **AC-3 异源覆盖被拒绝**：使用不同仓库或不同 Skill 路径更新已受管理 Skill 时，系统拒绝覆盖并说明来源冲突，现有内容和记录不变。
- [ ] **AC-4 staging 失败保留旧版**：下载失败、候选包缺少或包含无效 `SKILL.md`、名称不匹配、内容不可读、路径不安全或替换失败时，旧 Skill 仍可被 catalog 正常发现和激活，来源与内容版本记录不前移。
- [ ] **AC-5 本地修改冲突与显式覆盖**：修改已受管理 Skill 的任一已安装内容后发起更新，首次尝试识别内容偏离、展示同源来源和丢失风险并保持现状；用户拒绝或取消时不发生变化，用户再次明确同意后才允许按正常安全流程覆盖更新。全程不静默覆盖、不自动合并，也不把未完成操作报告为成功。
- [ ] **AC-6 无来源旧 Skill 接管**：面对目标目录已存在但没有来源记录的 Skill，首次尝试不会覆盖；系统说明无法验证的事实并取得用户再次明确同意后，才以用户提供的 GitHub 来源完成 staging、替换和记录建立。拒绝或失败时旧内容不变。
- [ ] **AC-7 幂等更新**：对来源和内容版本均未变化的 Skill 重复发起更新，系统稳定返回“已是最新”，Skill 内容、来源记录和 model-visible catalog 状态不发生无意义变化。
- [ ] **AC-8 catalog 热刷新与轮次隔离**：会话保持运行时成功更新 Skill，无需重启即可在刷新后的后续用户轮发现和激活新内容；更新期间已经开始的用户轮继续使用原 snapshot，历史中的旧正文不被改写。
- [ ] **AC-9 Agent 使用真实更新路径**：面对 issue 054 类型的“更新已有 GitHub Skill”请求，Agent 使用 builtin `skill-installer` 支持的确定性更新流程；遇到接管确认、冲突或失败时如实反馈，不编造 `--force`、不存在的命令参数或未来自动执行承诺。
- [ ] **AC-10 范围隔离**：共享目录、非 GitHub Skill、批量或后台更新、版本历史、回滚、本地修改合并和 UI 均不会因本需求获得隐式实现或行为承诺。

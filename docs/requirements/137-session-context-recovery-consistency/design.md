## 现状与责任边界

1. `Conversation._usage_scope` 混合输入计量身份和输出设置；`usage_anchor` 把未知 reasoning 逐段预留整窗口；恢复只读 assistant 事件而遗漏工具轮 usage。
2. 编辑重发先持久化业务分支，模型候选直到 provider 接受才提交。中途失败会遗留旧 model history；下一次 reconcile 因分支不一致重建全部业务历史。
3. Bridge 多入口分别配置 error_callback，遗漏入口没有错误正文落盘。Runtime 已拥有失败异常与运行身份，Bridge 仍拥有错误映射和可公开文案。
4. 中断修复扫描全部历史 interrupted run，把泛称“上一轮”的 marker 追加到末尾；模型只看到正文，看不到归属 metadata。

## 方案

### 输入计量与压缩

- 版本化 input usage 兼容性，只排除已知不改变输入表示的输出强度、输出上限和传输超时设置；会话、模型、路由、输入协议、附件表示及未知设置继续参与判定。工具和文本变更仍按组件计量。
- 新计量记录使用新版本身份；旧 v3 只在其原配置可由历史事件恢复且旧 digest 可验证时转换。无法验证不猜测，不跨路由复用；旧版本保持可读。
- 恢复扫描所有已支持的 usage owner（assistant_message、tool_call_request），按 active 分支选择最新记录；无效最新记录不得隐式倒退到更旧可信值。
- 未知 reasoning 保留显式数量和原因，停止逐段叠加整窗口的伪精确数值；安全 admission 仍拒绝未知成本的最终请求。只有旧段可被摘要替换且保留部分可通过预算时才调用摘要。
- 压缩前校验保留 tail、固定上下文和摘要预留的可行性；失败使用明确 reason，保留原历史。最终组装继续复核，防止动态内容突破预算。

### 用户输入接受与模型请求接受分离

- 新增明确的 user-input-accepted rollout 边界：业务输入受理后，把已验证的模型前缀和新用户事实持久化，再进行昂贵组装或 provider 调用。
- 编辑重发使用 `history_before_rewrite` 得到仍属于有效分支的已提交前缀；提交新的模型基线与业务分支一致。不要借此提前提交尚未成功的摘要或声明 provider 已接受。
- 热恢复和冷恢复共用相同基线；对旧版失败编辑遗留的不一致，按有效业务前缀寻找已验证 rollout，再增量对齐，不能以任意不一致为由复活被摘要替换的全部历史。
- 输入可恢复性、provider 请求接受和 run 完成是不同事实，保持各自的日志与落盘边界。

### 失败持久化的共享 owner

- Runtime 支持默认的错误记录回调，由 Bridge 装配统一 mapper；入口只在确有语义差异时覆盖。错误只由一个 owner 落盘，并按 run 幂等。
- 普通发送、编辑重发、继续、OpenAI/语音、IM、定时任务、提醒和授权跟进逐一验证；保留各渠道已有传输和业务状态反馈。
- 用户输入未受理时不在会话制造虚假失败消息；受理后的无正文失败也必须保留具体错误。既有 frontend 读取 run_error 的机制继续复用。

### 中断事实的模型投影

- 基于 run 与工具执行证据生成 scoped marker，正文包含对应任务时间/身份及执行状态；不依赖隐藏 metadata 来让模型判断归属。
- 新中断在所属历史边界记录；恢复不把所有旧中断作为当前指令追加。旧格式 marker 在模型视图中转换，原始 session 事实不改写。
- 未启动工具、已完成工具和执行状态未知分别陈述；未知仍要求核实，不因修复取消副作用保护。不把普通业务失败等同于任务中断。
- 新用户任务、明确继续和跨日旧任务分别覆盖；权限、Skill 激活仍只按当前运行有效状态装配。

## 验证与影响

- 先完成确定性回归：输出配置变化、真实路由变化、opaque reasoning、工具轮重启、编辑失败后 warm/cold 恢复、多个旧中断、零工具执行、部分副作用、多入口失败。
- 按 backend/frontend/rust 分阶段执行 scripts/check。对已安装旧会话保持只读诊断，不通过直接修改用户数据验收。
- CPA 真实调用采用隔离合成会话、无业务副作用工具和有界调用量；每次运行前声明配置/数量，实际偏离重新确认。与 fake 验证分开报告。
- 桌面使用当前 worktree 的真实 Tauri runtime，核对源码新鲜度与身份，并把 DOM/截图与持久化事件交叉核对。若现有用户实例阻止启动，先处理运行态归属，不自动结束用户进程。
- 预计是 standard 冻结影响：纯已有业务机制和持久化逻辑，无新运行时依赖、动态资源或原生库。实际 diff 若改变该分类，按项目规则升档。

# 059 · 多模态消息附件

## 状态

CONFIRMED

## 背景

agent-friend 当前的桌面对话、AG-UI 输入、会话消息和 Agent 主链路都以纯文本为主。用户无法在输入框中添加图片、PDF 或文本文件，也无法在历史消息中查看曾经随消息发送的附件。

IM 入站事件已经具备附件字段，QQ 语音附件也已有转写链路，但图片和文档目前只被识别、计数或记录，真正进入 Agent 的仍只有文本正文。因此用户通过桌面端或 IM 收到图片、PDF 等材料时，agent 无法理解其内容，已经造成实际使用不便。

项目最初以不支持多模态输入的 DeepSeek 模型为主，因此没有建立附件能力。当前已经接入支持视觉输入与文件处理的 Kimi 模型，具备补齐端到端附件消息的基础。本需求建立统一的附件语义、模型能力约束和生命周期，让桌面对话与 IM 都能安全、可追溯地使用附件，同时为未来新增模型和输入模态保留清晰边界。

## 目标

- 用户可以通过拖拽或输入框左下角的加号添加附件，并在发送前查看、移除附件。
- 用户可以发送“文字 + 附件”或仅附件消息。
- 已发送附件与用户消息一起展示、持久化，并在重新打开历史会话后继续可用。
- 图片、PDF 和 TXT 作为首期正式保证的附件类型；当前模型支持的其他通用文档类型复用同一能力接入。
- 当前模型是否支持某种输入模态、文件类型和限制，由单一模型能力事实源决定，桌面端、Bridge、Agent 与 IM 行为保持一致。
- IM 入站的图片和文档可以进入与桌面对话相同的附件处理链路。
- 附件由 agent-friend 管理其本地生命周期，不能依赖用户原文件位置或模型厂商临时文件长期存在。
- 诊断包默认能够定位附件链路问题，并允许用户显式选择是否包含相关原始附件。

## 范围

### 包含

#### 桌面输入框添加附件

- 对话输入框支持以下两种添加方式：
  - 将文件拖拽到输入区域。
  - 点击输入框左下角的加号，通过系统文件选择器添加。
- 待发送附件使用 TDesign Chat 提供的附件组件展示，与现有 `ChatSender` 视觉和交互保持一致。
- 每个待发送附件至少展示可辨认的文件名和文件类型；图片可按 TDesign 组件能力提供缩略展示。
- 每个待发送附件提供叉号，用户可以在发送前移除。
- 支持一次添加多个附件；实际数量、单文件大小和总大小必须在加入草稿时校验。
- 支持“文字 + 附件”和“仅附件”两种发送方式。仅附件消息不得因为文字为空而被输入框拦截。
- 添加、移除或上传失败不得清空用户已经输入的文字和其他仍有效的附件。

#### 基于当前模型能力限制交互

- 当前选中的对话模型沿用现有持久设置，应用重启后继续生效。
- 每个模型需要声明自己支持的输入模态、文件类型及相关限制；这些能力是跨桌面端、Bridge、Agent 与 IM 的统一判断依据。
- 前端不得另外硬编码一份模型模态或文件类型判断表。
- 当前模型完全不支持附件时，加号入口应呈现不可用状态并说明原因。
- 用户拖拽当前模型不支持的附件时：
  - 拖拽区域显示禁止操作的 cursor 或等价反馈。
  - 文件不进入待发送列表。
  - 通过 Sonner 明确提示当前模型不支持该类附件。
- 文件选择器仍需在选取结果进入草稿前做能力校验；不能仅依赖扩展名过滤。
- 用户已经添加附件后切换到不兼容模型时，保留文字与附件草稿，但禁止发送并明确指出不兼容项；用户移除附件或切换到兼容模型后可以继续发送。
- Bridge、Agent 和 IM 必须再次执行同源能力校验，不能把前端拦截当作唯一安全边界。

#### 支持的附件类型

- 首期正式保证并纳入验收：
  - 常用图片格式。
  - PDF。
  - TXT 纯文本文件。
- 当前模型能力目录声明支持的其他通用文档类型可以复用统一附件链路，包括 Markdown、CSV、Office 文档等；是否可选和可发送以模型能力事实源为准。
- “支持某类型”意味着用户可以完成添加、发送、模型理解、历史展示和重新进入会话，而不只是输入框接受文件。
- 不要求 agent-friend 为所有附件在本地实现 OCR 或文档理解；可以使用模型厂商提供的视觉输入、文件上传或内容抽取能力。但厂商处理方式的差异不得泄漏成各入口不一致的用户体验。
- 用户文件的 MIME、扩展名或内容无法安全识别时必须拒绝处理，并给出可理解的提示，不能把未知内容伪装成受支持类型发给模型。

#### 用户消息展示与历史恢复

- 已发送用户消息中的附件显示在该消息文字上方，并使用 TDesign Chat 的用户消息附件内容块或等价散件能力。
- 附件展示顺序与发送时顺序一致。
- 历史会话重新加载后，附件名称、类型、顺序和可用状态仍可恢复。
- 附件原始来源文件随后被移动、重命名或删除，不影响已经发送的会话附件。
- 如果托管附件因外部损坏或异常丢失，历史消息仍显示附件记录及不可用状态，并提供拟人、可诊断的反馈；不能导致整个会话加载失败。
- 编辑并重新发送最新用户消息时，保留该消息的原附件；首期编辑态不允许新增、移除或替换附件。

#### 附件作为独立用户资产托管

- 已发送附件必须由 agent-friend 纳入用户数据管理，与会话消息建立稳定引用关系。
- 会话记录不得长期内嵌原始二进制或大段 base64，以免会话文件、历史回放和上下文压缩无限膨胀。
- 模型厂商返回的远端文件标识、上传结果或临时 URL 只能作为可失效的处理状态，不得成为附件唯一真相源。
- 厂商远端文件失效后，只要本地附件仍存在，系统应能够重新处理，而不是让历史消息永久失效。
- 同一附件被多个消息或会话引用时，删除其中一个引用不能破坏其他仍有效的引用。
- 删除会话时释放该会话的附件引用；只有不存在有效引用的附件才可被最终清理。
- 用户在草稿中添加后又移除、关闭窗口或放弃发送的附件不能形成永久孤儿数据。
- 设备迁移需要包含会话所引用的托管附件，使迁移后的历史消息仍可使用。
- 附件属于不可信用户内容；文件内文本、图片文字、元数据和模型厂商抽取结果都不能获得高于普通用户输入的指令权限。

#### 上下文与长会话稳定性

- 附件被持久化用于历史展示，不等于每一轮模型请求都必须重复发送全部历史原件。
- 近期对话中仍相关的附件应能被模型理解；长会话压缩后至少保留附件存在、来源消息及已提炼语义，避免直接保留大量原始二进制造成上下文溢出。
- 用户后续明确再次引用历史附件时，只要本地资产仍可用，Agent 应具备重新取得该附件的能力；具体重取与上下文装配策略由技术方案确定。
- PDF、长文本和多附件场景必须受上下文与文件大小限制保护，不能让单个附件导致会话永久无法续聊。

#### IM 入站附件

- QQ 私聊入站的图片、PDF、TXT 及当前模型声明支持的其他文档类型，进入与桌面对话一致的附件消息语义和 Agent 主链路。
- IM 平台提供的临时附件地址可能过期；附件一旦被接受处理，应及时纳入本地托管，保证会话持久化和后续重试不依赖临时地址。
- IM 消息允许只含附件而没有文字正文。
- 当前对话模型不支持该附件、附件超限、下载失败或文件无效时，不静默忽略，也不把空文本送进 Agent；应直接回复用户可理解的提示。
- 现有 QQ 语音附件转写能力继续工作，不能因统一附件语义而回归。
- 本期 Agent 向 IM 的正常回复仍为文本或既有 Markdown，不主动回发图片、PDF 或其他文件。

#### 诊断与隐私

- 默认诊断包包含足以定位附件链路的诊断清单和脱敏状态，例如：
  - 文件类型、大小与完整性状态。
  - 会话消息引用是否存在。
  - 下载、托管、上传、抽取、发送等处理阶段及失败位置。
  - 脱敏后的厂商错误与重试状态。
- 默认诊断包不包含附件原始正文、图片内容或完整文件。
- 诊断入口提供“包含相关原始附件”选项，默认关闭。
- 用户开启该选项时，需要明确提示隐私风险和预计增加的诊断包体积；生成结果应说明实际包含、跳过或失败的附件。
- 原始附件进入诊断包时，只包含与本次问题相关的托管附件，不扩展为无边界收集全部用户文件。
- 无论是否包含原件，API key、IM 凭据、临时授权信息和其他密钥仍必须按现有诊断规则排除或脱敏。

#### 错误处理与可恢复性

- 附件处理过程需要向用户表达可区分状态：可发送、处理中、失败、不受支持或本地不可用。
- 桌面端发送前失败时，保留文字与可恢复的附件草稿，允许用户移除失败项或重试。
- 模型调用失败不能破坏已经成功托管并写入会话的附件引用。
- 单个附件失败时，不能把其他无关附件或整份历史会话一并损坏。
- 用户可见错误使用拟人、可操作的表达，不直接暴露本地绝对路径、堆栈、厂商内部异常类型或敏感远端标识。

#### 真实桌面端验收

- 本需求需要在真实 Tauri 桌面端验收输入框拖拽、加号选择、附件列表、移除、禁止态、Sonner 提示和用户消息附件展示。
- Vite Web 页面只能辅助开发，不能单独证明桌面文件拖拽、系统选择器和真实 WebView 下的交互正确。

### 不包含

- 不在本期支持视频附件。
- 不把现有语音输入或 QQ 语音转写重做成通用音频多模态输入。
- 不支持 Agent 主动向桌面会话或 IM 生成、回传新的附件文件。
- 不提供附件在线编辑、标注、裁剪、重新命名或复杂预览器。
- 不在编辑重发状态中新增、删除或替换附件。
- 不要求对模型厂商官方未支持的文件类型做本地格式转换兜底。
- 不要求每个 Office、代码或数据文件格式都执行独立的真模型验收；这些类型复用统一能力通路，正式验收聚焦图片、PDF 与 TXT。
- 不把模型厂商远端文件存储当作 agent-friend 的用户数据备份。
- 不让诊断包默认无提示地包含用户附件原件。

## 关键约束

- 模型目录是模型标识、输入模态、文件类型和相关限制的唯一事实源；现有前后端重复模型清单需要在本需求方案中消除或收敛，不能继续扩散。
- 当前模型选择继续复用现有桌面设置持久化链路，不新增另一套“附件专用模型状态”。
- 桌面、AG-UI、Agent 会话、LLM Provider 与 IM 使用统一附件领域语义，但各层只承担自己的责任，不把厂商特有 file ID 泄漏为公共附件标识。
- 附件原件属于用户资产，落盘位置必须遵循现行用户数据路径约定；设置和日志目录不能用于保存附件正文。
- 产品上限与模型厂商上限同时存在时，实际可用限制取更严格者；具体数值由技术方案结合当前厂商约束确定。
- 会话历史兼容既有纯文本事件；没有附件的旧会话无需迁移即可继续读取。
- 附件内容必须继续遵守项目现有不可信内容边界，不能因经过文件抽取或视觉识别而提升权限。
- 真实模型验收会产生 LLM API 调用，执行前必须按 `llm-api-confirm` 单独获得用户授权。

## 开放问题

- 统一附件领域对象、会话事件引用与模型内容块应如何划分，既保持旧会话兼容又避免厂商细节泄漏，需要在技术方案阶段确定。
- 本地附件资产的目录组织、去重方式、引用关系、孤儿清理与故障恢复策略，需要结合现有 JSONL 会话和用户数据迁移边界确定。
- 图片在近期历史中的重放范围，以及进入上下文压缩后如何保留语义并支持后续重新引用，需要结合 009 上下文管理链路设计。
- Kimi 图片直传、文档上传/抽取和远端文件清理应如何封装为 Provider 能力，需要在技术方案阶段结合现有 LiteLLM 边界确认。
- 模型能力事实源如何安全投影到前端，并同时消除当前前后端重复模型目录，需要结合现有设置初始化和 Bridge runtime 配置确定。
- 产品级数量、单文件大小、总大小、诊断包附件大小等默认限制，需要在技术方案阶段结合 Kimi 与桌面运行态约束确定。
- 诊断包“相关附件”的选择范围和 UI 呈现，需要沿现有反馈入口与当前会话上下文确定。

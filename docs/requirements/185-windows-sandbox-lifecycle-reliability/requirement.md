# Windows 沙箱执行与恢复可靠性

## 状态

CONFIRMED（2026-11-28）

用户确认需求编号与整体范围，并明确：安装版验证延期到后续打包后进行，不作为本次合入前门槛；后续验证发现的问题继续修复。该安排不把未执行项记为通过，也不替代后续发布所需的验证。

## 背景

Windows 命令沙箱已有多轮可靠性与恢复改动，实际使用中仍出现状态失效、命令启动结果未知，以及自动恢复和手动修复长时间等待后失败。最新诊断同时保留了此前修复成功、之后身份状态再次不完整，以及两次恢复等待超时的证据。

当前问题涉及环境准备、身份维护、进程启动与结束、取消、跨会话共享状态和恢复入口之间的契约。局部修复通过，不能证明这些边界组合后的故障链能够恢复。本需求重新审视整条链路中的不合理设计，形成可验证的执行与恢复保证。

历史现场、源码版本、既有修复范围、机制性复现与尚未确认的原因见 [证据索引](./evidence-index.md)。

## 目标

1. 已授权命令从准备到结束有可信、可核对的状态；超时、断线和取消不会被误报为成功、已停止或确定未执行。
2. 沙箱发生故障后，系统能够在有界时间内自动恢复，或提供确实可执行的人工恢复路径；同一个未解决状态不能使每次修复都重复空等。
3. 单次失败、身份维护或恢复的影响范围明确，避免持续阻塞不相关会话，也不误停健康任务。
4. 能从一次故障的证据解释首次失败、后续处理和最终状态，支持持续排查复发原因。
5. 通过完整故障链验证恢复能力，避免只验证单个错误分支或正常路径。

## 范围

### 包含

- Windows 沙箱首次准备、状态检查、身份维护、宿主目录访问、命令准备、启动确认、运行、取消、结束和恢复。
- 自动恢复、用户手动修复、会话取消、执行服务失联与服务重启之间的协作。
- 多会话和并发命令使用共享执行资源时的故障传播、互斥、资源归属和清理边界。
- 启动结果未知、迟到响应、遗漏事件、部分完成和已产生副作用的处理。
- 工具结果、Bridge、桌面状态和持久化证据对同一执行事实的一致解释。
- 原生错误、身份状态变化、恢复动作、执行服务身份和残留工作等证据的关联与留存。
- 评估当前后端接入的不足，以及必要的后端升级、接入调整或隔离边界调整；具体选择在技术方案阶段确认。
- Windows 10／11 的受影响行为与相应源码、协议和运行时验证；共享代码变更同时检查其他平台的兼容影响。

### 不包含

- 桌宠大小、位置或渲染问题。
- 自动重放执行结果未知且可能产生重复副作用的业务命令，或隐式扩大权限、降低沙箱隔离强度。
- 承诺所有系统或外部环境故障均可自动修复；无法恢复时必须明确原因、影响和下一步。
- 未经本次方案确认直接采用某个后端版本或隔离实现。
- 自动关闭历史 issue、改写历史需求的验收结果。
- 本阶段为验收主动打包、构建 frozen 验证候选、运行安装矩阵或操作现有 production 安装。安装版验证按用户要求延期。

## 需求

### 执行状态与完成判定

准备、启动、运行和收尾各阶段应有明确事实依据。用户请求结束、前端停止等待、执行器接受取消、原生命令退出和其子进程已收尾必须按各自事实表达，不能相互替代。

响应丢失或超时时，应在权限和后端能力范围内核对已有工作。无法确定执行结果时保留不确定性及恢复所需信息，不以遗忘状态、删除记录或换一个标识符重试代替核对。

### 故障恢复与人工介入

按实际可恢复性区分故障，统一协调恢复预算和并发行为，避免多层重试相互放大。恢复过程需明确正在等待什么、能否继续、何时结束、何种变化允许下一次尝试。

手动修复必须具有可到达的执行路径。若存在活跃任务或无法核实的残留工作，应能准确指出阻塞条件，并提供匹配实际能力的后续动作；不能把同样的无进展等待包装成重新修复。

环境恢复成功与原业务成功分别判断。恢复后对原任务的续接需符合其实际执行情况及仍有效的授权。

### 共享资源与影响控制

明确准备工作、身份状态、执行服务、业务进程及后代进程的归属与生命周期。取消或恢复不能误伤健康任务；确实需要影响其他任务的操作，应提前说明精确范围并遵循授权边界。

服务或应用重启后，既有执行结果和残留工作的状态应得到一致处理，不能用新服务可连接来证明旧工作已结束。

### 诊断与恢复呈现

保留首次错误以及后续恢复错误，能够解释身份状态为何被判定失效、采取了什么动作、动作是否结束、最终是否可继续执行。缺失或无法采集的证据显式标记，不覆盖成单一笼统错误。

Agent、桌面界面和诊断包应指向同一执行事实与恢复进展，给出的下一步必须真实可用。诊断不记录凭据或不必要的用户命令正文。

## 验收条件

- [ ] **AC-1 生命周期边界**：准备、启动、运行、取消和收尾的状态转换及完成依据有确定性验证；每类失败都有明确结束或人工介入路径。
- [ ] **AC-2 未知启动核对**：覆盖启动请求超时后实际未启动、迟到成功、迟到失败和状态无法核实；不会错误重放，后续命令不会被永久遗留状态阻塞。
- [ ] **AC-3 取消与残留工作**：分别验证准备、启动、运行阶段取消及取消失败；接受取消不被写成清理完成，能发现并处理或明确报告残留工作。
- [ ] **AC-4 恢复可达**：覆盖“故障 → 自动恢复失败 → 手动恢复 → 独立命令成功”，以及无法恢复时的明确终态；重复点击不会反复空等或并发重建身份。
- [ ] **AC-5 身份与目录状态**：覆盖状态缺失、损坏、不兼容、登录失效和目录访问失败；保留首次失败与状态变化证据，恢复需通过实际能力验证。
- [ ] **AC-6 并发影响控制**：并发正常任务、未知启动和修复同时存在时，不重复执行业务、不误停健康任务，影响范围及阻塞原因可核对。
- [ ] **AC-7 失联与重启**：覆盖执行服务断线、退出、重连及应用重启；旧执行事实和残留工作不会被新服务身份掩盖。
- [ ] **AC-8 跨层一致性**：工具结果、Bridge、前端和持久化状态一致，不把等待写成执行中、不把取消请求写成已取消、不把环境恢复写成业务完成。
- [ ] **AC-9 故障证据**：一次事故能够关联首次错误、后续恢复、超时预算、执行身份和最终结果；旧诊断包仍可读，新增证据不泄漏凭据。
- [ ] **AC-10 后端能力验证**：选定方案逐项验证所依赖的查询、取消、清理、隔离和恢复能力；不能仅以接口存在或升级版本证明保证成立。
- [ ] **AC-11 组合回归**：用可重复的故障注入及必要原生专项覆盖上述链路，并验证恢复后的真实命令；记录重复运行、平台和配置，区分机制验证与现场复现。
- [ ] **AC-12 项目检查与源码平台证据**：受影响层检查通过；分别列明 Windows 10／11 的实跑结果与缺口，共享行为变更补相应平台证据，不把单平台通过外推。

### 延期验证

- **PV-1 安装版与 frozen runtime**：后续用户发起打包后，再验证候选的内置执行后端、冻结 runtime、身份与目录兼容、真实恢复，以及实际改动要求的安装／升级场景。
- PV-1 不作为本次合入前硬门槛；保持“未执行／延期”记录，不伪造通过结果。后续发现问题允许在合入后继续修复。
- 本次安排不取消源码检查、确定性故障链验证或独立的用户验收确认。后续打包和正式发布仍使用项目标准入口及对应制品校验。
- **PV-2 隔离原生环境验证**（2026-11-29 用户确认先跳过）：当前没有 Windows 10／11 隔离测试机或 VM，真实沙箱账户失效、不同本地身份和 UAC 的故障注入暂不执行；Windows 10 原生矩阵同步延期。本轮继续完成实现、本机可安全执行的原生专项与确定性门禁，不因缺少该环境阻塞交付，不把这些未执行项记为通过。现有 production 身份与安装不作为替代试验场。

## 关联与开放问题

- 历史需求：124 命令可靠性、131 故障证据、141 恢复与续接、160 命令生命周期。它们提供现状与历史约束，不自动认定本次事故与某个历史 issue 同根。
- 已占号的 161 后端升级与 MXC 分支、issue 066／070 作为相关背景。实施范围确定后核对重叠与归属，不自动关闭或改写它们。
- 本次现场身份文件从完整变为缺失的首次原生原因尚未确认；方案需明确如何保留足以区分该原因的新证据。
- 当前后端的“可查询／可接受终止”与“准备过程已停止／不会迟到产生副作用”之间仍需验证。

# 063 · 上下文压缩可靠性

> Context Compaction Reliability

## 状态

<!-- DRAFT | CONFIRMED -->

CONFIRMED

## 1. 背景

当前仓库已经具备按模型窗口估算上下文、超预算时摘要旧历史、失败时退化到 FIFO，以及把摘要作为 `compaction` 事件持久化的基本能力。它解决了“长会话完全不管理上下文”的问题，但现有链路还不足以成为长期会话可以稳定依赖的安全边界：

- 真实 token usage 已能取得，但尚未真正参与后续预算判断的校准。
- 摘要请求自身可能超过模型窗口，尤其是没有历史摘要可复用的首次超长压缩。
- 摘要生成成功后，最终上下文没有统一的二次预算保证。
- 最近上下文按固定轮数保护，无法适应极短或极长的单轮内容。
- 单条巨大 tool result 虽然不常出现，但一旦直接进入模型视图，可能让压缩请求和主请求同时失效；原始结果完整保存与模型输入安全之间还没有明确边界。
- 摘要失败、模型窗口变化和 provider 明确返回上下文超限时，缺少足够精细且有界的恢复路径。
- 已有摘要能够落盘，但“完全销毁运行态后重新加载仍不重复压缩、且恢复相同有效上下文”缺少直接的集成证据。

本需求以当前仓库代码、测试和运行行为为事实基线。历史需求文档只作为演进背景，不作为当前行为已经成立的证明。

## 2. 目标

把现有上下文压缩补成一条可验证、可恢复的可靠链路，使长会话在正常对话、工具续轮、模型变化和应用重启后都能继续进行：

1. 每次发给模型的上下文都经过与当前模型窗口一致的预算保护。
2. 压缩请求和压缩后的主对话请求都不能在已知超预算的情况下发送。
3. 系统优先保留最近且结构完整的对话；摘要不可用时自动、有界地降级。
4. 已成功持久化的压缩结果在关闭应用并重新打开后直接复用，不重复产生摘要调用。
5. 开发者能够从结构化证据判断一次压缩为何触发、如何恢复以及最终采用了什么上下文。

## 3. 范围

### 3.1 包含

- 真实 usage 参与后续上下文预算判断或估算校准。
- 以当前激活模型的有效 context window 作为不可越过的硬边界。
- 正常首轮、工具调用续轮、工具循环收尾和系统触发轮共享同一套预算保护。
- 模型切换、特别是切换到更小窗口后，对现有上下文重新进行预算判断。
- 摘要调用自身的输入预算保护，包括首次面对超长原始历史且没有 prior summary 的情况。
- 摘要完成后的最终上下文二次预算验证。
- 按 token 预算从新到旧保留完整近期 user turn，不拆散 assistant tool call 与对应 tool result。
- 保持原始 tool result 完整落盘，同时为模型视图提供带明确标记的有界截断；截断不得破坏 tool call 与 tool result 的协议配对。
- 对可恢复的摘要失败和上下文超限执行有界恢复；无法恢复时退化到 FIFO，保证对话不进入压缩死循环。
- 增强压缩 checkpoint，使新进程能够确定性恢复有效摘要和保留范围。
- 覆盖真正的销毁运行态、重新加载会话、继续对话的自动化验证。
- 补充触发原因、预算、重试、失败分类、降级结果和压缩前后变化等可观测证据。
- 保持所有原始 user、assistant、tool 事件完整，不因压缩而删除或改写。

### 3.2 不包含

- 面向不同工具语义的完整 L3 输出治理，例如按结构摘要、分页读取、外部制品引用、按工具配置独立保留策略；本需求只提供通用的模型视图安全截断。
- 手动压缩命令、桌面按钮、压缩进度 UI 或其他用户界面改造。
- 睡眠整理、周期回顾、长期会话主动休眠等新触发模式。
- 压缩前与长期记忆写入建立强事务或同步屏障。
- 服务端专用远程压缩协议或新的 LLM provider 能力。
- 会话 JSONL 分页、SQLite 投影或其他存储性能架构改造。
- 大规模重写陪伴型摘要 prompt，或把摘要语义质量评测扩展成独立评测平台。
- 默认持久化摘要失败的 circuit breaker 状态；若实现证据表明确有跨重启失败风暴风险，再回到需求阶段确认是否扩围。

## 4. 核心需求

### 4.1 统一且可信的预算边界

- **R-1.1 当前模型边界**：所有预算判断必须以当前实际激活模型的有效 context window 为准；模型变化后不得沿用不匹配的旧边界。
- **R-1.2 真实 usage 校准**：provider 返回的真实输入 token usage 应参与后续预算判断或估算校准；provider 不提供 usage 时仍须有保守的降级估算。
- **R-1.3 全入口覆盖**：任何会向主模型发送完整对话上下文的入口都必须经过统一预算保护，不能因工具续轮或系统轮绕过。
- **R-1.4 硬边界保证**：系统已经判断为超过当前模型安全预算的上下文不得继续发送给 provider。
- **R-1.5 原始结果与模型视图分离**：tool result 的原始事件必须完整保留；超过安全预算时，只允许对发送给模型的投影做带标记的截断或占位替换，不得静默改写持久化事实。

### 4.2 压缩请求安全

- **R-2.1 摘要输入可发送**：摘要请求自身必须在当前模型可接受的预算内；摘要 prompt、待摘要历史和必要上下文均应被计入。
- **R-2.2 首压可建立**：即使首次遇到的原始历史已经大于摘要请求可用窗口，系统也应能通过安全收缩建立摘要，或确定性退化，而不是重复发送同一份超长输入。
- **R-2.3 完整轮边界**：收缩摘要输入或近期历史时，不得制造孤立 tool result 或拆散同一 user turn 内的工具协议序列。
- **R-2.4 有界恢复**：只对适合恢复的失败执行重试或进一步收缩，次数必须有上限；不可恢复的错误不应伪装成上下文问题反复重试。
- **R-2.5 巨大工具结果安全阀**：单条 tool result 超过模型视图预算时，应保留可解释的头尾或替换为明确占位信息，并记录原始规模与截断事实；若非 tool 内容单项独自超过硬边界，可以明确失败，不得以静默截断改变用户输入语义。

### 4.3 压缩结果安全

- **R-3.1 二次验算**：摘要生成后，必须对即将发送给主模型的完整上下文重新做预算判断。
- **R-3.2 自适应近期保留**：最近原文按 token 预算保留完整 user turn，而不是只依赖固定轮数；至少保证当前活动轮的协议完整性。
- **R-3.3 安全降级**：摘要为空、摘要过长、重试耗尽或最终上下文仍无法满足预算时，应自动退化到安全兜底，主对话不因压缩链路进入死循环。
- **R-3.4 不重复落点**：失败重试不得生成重复或互相矛盾的持久化压缩记录；只有最终被采用的压缩结果才能成为新的有效 checkpoint。

### 4.4 持久化与恢复

- **R-4.1 成功摘要复用**：正常关闭应用并重新打开同一会话后，已成功持久化的摘要应直接复用；重启本身不得触发重新摘要。
- **R-4.2 确定性恢复**：新的运行进程应能从持久化数据恢复与压缩点一致的有效覆盖范围和近期原文范围，不能依赖旧进程的内存状态。
- **R-4.3 原始历史完整**：压缩与恢复均不得删除或修改原始 user、assistant、tool 事件；历史检索和长期记忆仍可读取完整事实来源。
- **R-4.4 异常可识别**：压缩 checkpoint 缺失、损坏或与当前有效事件流不一致时，系统应识别为失效状态并走安全路径，不得静默使用错误摘要。

### 4.5 可观测性

- **R-5.1 触发证据**：能够识别压缩由常规预算、模型窗口变化、provider 上下文超限或其他已定义原因触发。
- **R-5.2 过程证据**：能够观察压缩前后预算、摘要输入与输出规模、恢复次数、失败类别和降级原因。
- **R-5.3 结果证据**：能够确认最终采用摘要上下文还是 FIFO，以及最终上下文是否满足预算。

## 5. 验收标准

### 5.1 自动化机制验收

- **AC-1**：使用不同 context window 的 fake model 时，预算边界随当前模型变化；切换到更小窗口后会重新保护现有上下文。
- **AC-2**：存在真实 usage 锚点与不存在 usage 时都能得到可解释的预算结果；usage 能实际影响后续判断，而非只出现在日志中。
- **AC-3**：正常首轮、工具续轮、工具循环收尾和系统触发轮均经过统一预算保护。
- **AC-4**：巨大 tool result 的原始事件保持完整，模型视图包含明确截断标记和原始规模；tool call/result 仍成对存在，最终请求不因该结果已知超预算。
- **AC-5**：没有 prior summary 的首次超长历史能够建立有效摘要或安全退化；摘要请求不会重复发送已知超预算的完整旧历史。
- **AC-6**：摘要输入收缩和近期原文保留都只在完整 user turn 边界进行，工具调用协议组保持完整。
- **AC-7**：摘要成功但摘要或近期 tail 过长时，系统会在主请求前再次收缩或降级；最终不会发送已知超预算的上下文。
- **AC-8**：可恢复错误执行有界恢复，不可恢复错误直接进入明确失败或兜底路径；任何情况都不产生无限压缩循环。
- **AC-9**：失败和重试不会产生重复有效 compaction checkpoint。
- **AC-10**：触发一次压缩后销毁 Conversation、ContextManager 和 store 实例，再从持久化文件重新加载并继续对话，摘要 LLM 调用次数不增加。
- **AC-11**：重启恢复后的摘要覆盖范围和近期原文与持久化 checkpoint 一致，且所有原始会话事件仍完整存在。
- **AC-12**：缺失、损坏或已被有效事件流改写越过的 checkpoint 不会被静默采用。
- **AC-13**：日志或诊断证据能还原触发原因、预算、工具结果截断、恢复次数、最终策略及压缩前后变化。
- **AC-14**：项目规定的自动化门禁全部通过，既有上下文管理、会话恢复、工具调用、模型切换和附件行为不退化。

### 5.2 真实运行观察

- **AC-15**：一次经明确授权的真实 LLM 运行能够观察到输入 usage，并证明其进入后续预算链路。
- **AC-16**：一次经明确授权的真实长会话能够完成压缩、继续对话、关闭应用后恢复，并且不会因重启重复摘要；压缩前明确给出的关键信息在恢复后无明显漂移。

真实 LLM 验收只用于观察 provider usage、实际压缩质量和应用恢复体验；预算、重试、边界完整性与持久化机制必须优先由 fake/mock 自动化固定。执行任何真实 LLM 调用前仍须遵守项目的逐次授权规则。

## 6. 依赖与约束

- 复用当前 `ContextManager`、会话 append-only 事件流、LLM usage 和模型窗口能力，不另建第二套对话历史事实来源。
- 与当前模型切换、附件上下文、工具调用续轮、编辑重发及会话恢复行为保持兼容。
- 本需求不以历史需求文档中的完成声明替代当前代码和测试证据。

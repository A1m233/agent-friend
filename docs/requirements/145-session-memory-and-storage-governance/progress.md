## 用户纠正后的发送延迟缺口

用户明确关注 AF 中标题为“长会话”的会话每次发送到上游前的等待，不是闲置回收后冷恢复。按 metadata 定位为固定样本 B。读取安装版旧日志与当前源码，并用固定 A/B 只读查询检查后，确认本次验收尚未覆盖这条实际发送路径。

- 9 月 29 日 01:55 的热会话 run：会话准备 276 ms，但 transport request_started 在 28218 ms；其中自动记忆召回 18297 ms。该边界是本地准备打开 provider stream，不等于服务端收到请求，也不是 UI 点击时间。
- 召回范围准备约 11047 ms，当前会话查询重建 11030.968 ms；历史搜索 7141 ms，其中另一大会话查询重建 5822.044 ms。现有日志不能精确归因召回前另外约 9192 ms。
- 当前候选只读复现：B 第二次查询 0.0005 s、无扫描；插入 A 查询后再次查询 B 为 4.3014 s、重新扫描。A/B 查询估算合计 67909147 bytes，超过既有 67108864 bytes 上限，互相淘汰。一次序列证明机制，不代表完整发送延迟分布。
- 执行驻留豁免不等于查询投影驻留豁免。热发送禁止 store.load 的单测不能代替“发送到上游”的真实性能验证。memory_search/session_source_order 与 session_history_source 仍走查询缓存，这条路径本次尚未解决；AC-07 保持未通过，不再以恢复内存下降替代发送改善。

证据与精确日志锚点：[发送延迟诊断](evidence/20260930-send-latency-diagnosis.json)。本轮只读诊断，无产品代码变更、真实模型调用或原始数据修改。修复方向应消除当前会话召回范围的重复扫描，降低跨会话历史召回对发送关键路径的影响，并补齐逐阶段耗时验证；不能仅增加缓存上限后宣称问题解决。

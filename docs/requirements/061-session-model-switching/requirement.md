# 061 · 会话内模型切换

## 状态

CONFIRMED

## 背景

agent-friend 已支持在设置页选择默认聊天模型。该设置决定新会话首次运行时使用的模型，但用户进入一段持续对话后，缺少直接调整当前会话模型的产品入口。例如，一个会话最初使用 DeepSeek，后续需要更强的附件理解或不同的回答风格时，用户希望切换到 Kimi，并继续使用同一份消息、附件和上下文。

在主流 AI 对话产品中，会话进行期间切换模型已经是常见能力。常见交互把模型选择放在消息输入区附近，通过选择器当前值和短暂反馈表达切换，而不是在聊天时间线中持续插入模型切换分割线。当前对话使用的模型不等于全局默认模型；一次已经开始的回复也应保持执行模型稳定。

本需求补齐桌面对话中的会话级模型选择，使用户能够在不丢失上下文的前提下调整下一轮使用的模型，同时保证生成过程、附件能力、凭据错误、并发请求和历史诊断具有明确且可恢复的语义。

## 目标

- 用户可以在桌面对话输入区附近查看并切换当前会话使用的模型。
- 新会话的待用模型、已有会话的有效模型和设置页的全局默认模型具有清楚且互不污染的语义。
- 模型切换从下一次完整 Agent run 开始生效；已经开始的 run 在首轮调用、流式输出、工具调用、工具结果和后续模型调用期间始终使用同一模型。
- 切换模型保留当前会话的消息、附件、上下文和草稿，不把切换表现成新的会话。
- 模型能力、凭据状态、附件兼容性和错误反馈沿用项目现有统一事实源与设置入口。
- 同一会话跨多个模型后，历史、上下文压缩、工具调用和诊断仍然正确且可解释。

## 范围

### 包含

#### 桌面对话模型选择器

- 桌面对话输入区附近提供紧凑的模型选择入口，用户无需离开当前会话即可查看和更换模型。
- 入口默认展示面向用户的模型名称；当名称不足以区分模型时，在选择列表中同时展示 provider 信息。
- 可选模型及其名称、provider、能力和可用状态来自统一模型目录，前端不得另行维护一份模型支持清单。
- 模型数量较多时，选择列表应支持按 provider 组织并快速定位目标模型，避免把所有 provider 和 model 平铺为难以扫描的长列表。
- 模型切换成功后，选择器展示新模型，并通过短暂、无障碍可感知的状态反馈说明“下一条回复将使用目标模型”。
- 正常聊天历史不插入持久的模型切换分割线或伪造的 user/assistant 消息；模型切换记录保留为内部会话状态和诊断信息。

#### 新会话、会话模型与全局默认

- 设置页“默认聊天模型”只决定新会话最初展示和使用的默认值。
- 新会话尚未首次发送时，用户可以选择该待创建会话的 pending model；该选择只影响当前新会话，不修改设置页的全局默认模型。
- 新会话首次发送时，实际 run 必须使用界面当前展示的 pending model，不能重新读取全局默认模型后静默覆盖用户选择。
- 已有会话打开后，选择器恢复该会话持久化的 effective model；从一个会话切到另一个会话时，各自模型互不污染。
- 修改已有会话模型只更新该会话，应用重启或重新打开历史后仍能恢复；任何会话级切换都不得反向修改全局默认模型。
- 其他受支持入口改变同一会话模型后，桌面端刷新或重新进入会话时应恢复后端当前有效模型，不能长期显示旧状态。

#### 完整 Agent run 内冻结模型

- 一次 Agent run 从接受用户输入开始，到最终完成、失败或取消为止，使用的模型必须冻结。
- 冻结范围覆盖首次模型调用、流式输出、工具请求、工具执行结果、工具循环中的后续模型调用、上下文压缩和该 run 的诊断记录。
- run 进行期间不能通过桌面选择器、会话管理接口、CLI、IM 并发消息或其他外部入口把同一 run 的模型切换到一半。
- 正在生成时，桌面端模型选择器首版直接禁用，不实现排队切换或“当前 run 完成后自动切换”。
- 如果后端判断会话正在执行 run，切换请求必须明确失败并保持原模型，不能等待未知时长后静默生效。

#### 原子切换与并发一致性

- 已有会话切换模型时，只有后端确认目标模型可用并成功保存后，前端才更新当前有效模型。
- 目标模型不存在、凭据缺失、会话忙、会话已删除或归档、网络失败等情况下，原模型保持不变，失败的切换不得留下错误的有效状态。
- 快速连续选择多个模型时，较早请求的迟到响应不得覆盖用户最后一次有效选择。
- 切换请求进行期间禁止从该会话发送新消息；切换完成后发送必须使用最终确认的模型。
- 用户切换到其他 session、删除或归档当前 session、后台刷新详情时，旧 session 的迟到响应不得污染新 session 或复活已失效状态。
- IM 或其他入口向同一 session 投递消息时，与桌面发送和模型切换遵守相同的会话执行互斥语义。
- 可预期失败向调用方返回稳定、可区分的错误类型，至少覆盖模型不可用、凭据缺失、会话忙和会话不存在；桌面端据此提供可操作反馈，而不是只展示通用 HTTP 错误。

#### 凭据与模型可用性

- 统一模型目录中的模型保持可发现；缺少目标 provider 凭据时，用户能够理解该模型为什么暂不可用。
- 系统已知目标模型缺少凭据时，不提交新的 pending/effective model，并提供前往现有“模型与凭据”设置的入口。
- 前端可用状态只用于提前反馈，后端仍是切换能否提交的最终权威，不能因前端缓存状态绕过凭据校验。
- 凭据补齐后，用户返回当前会话即可重新选择目标模型，不需要重建会话或清空上下文。

#### 草稿附件与目标模型不兼容

- 切换模型不会删除、重新排序或静默替换用户已经选择或上传的草稿附件。
- 切换到不支持某个草稿附件的模型后，不兼容附件继续显示并明确标记为当前不可发送。
- 草稿存在不兼容附件时禁止发送，并提示用户换回支持该附件的模型或移除附件。
- 用户切回兼容模型后，仍有效的草稿附件恢复可发送，不要求重新选择或上传。
- 历史消息中的附件属于会话消息，切换模型不会删除历史附件；目标模型无法直接读取时，继续遵循 059 已确认的降级上下文语义。

#### 历史、上下文与诊断可解释性

- 会话内部保留模型切换事实，并能够恢复任意时点之后的当前有效模型；切换相同模型是幂等操作。
- 每次实际 Agent run 及其 assistant 输出能够识别本轮真正使用的模型；诊断包可以看出同一会话各轮使用过哪些模型及切换失败位置。
- 模型切换记录不计作普通用户对话内容，不应污染会话标题、用户消息统计或正常聊天展示。
- 切换后的下一轮上下文预算、上下文窗口和压缩行为跟随目标模型，同时保留此前会话已经形成的有效上下文。
- 同一会话跨 provider 后，既有文本、附件降级信息、工具调用和工具结果必须被投影为目标 provider 可以接受的有效上下文。
- 上一轮在取消或失败时留下不完整工具事务，不得导致切换后的目标模型永久无法继续会话。
- 编辑并重新发送历史中的最新用户消息时，不得意外撤销之后仍应生效的会话模型选择；重发 run 的实际模型与完成后的会话有效模型保持一致。

#### 禁用状态与用户反馈

- 会话正在流式生成、加载历史、编辑重发、提交模型切换或处于其他不能安全发送的状态时，模型选择器展示明确禁用态和原因。
- 切换成功使用轻量、短暂反馈，不用持久聊天分割线打断阅读。
- 切换失败保留原选择，并展示明确原因和恢复动作；缺凭据时提供设置入口，会话忙时提示等待当前回复结束后重试。
- 错误提示不暴露本地绝对路径、密钥、厂商原始敏感响应或内部堆栈。

#### 真实桌面端验收

- 在真实 Tauri 桌面端验证新会话和已有会话的模型选择器布局、打开与选择交互、禁用态、成功/失败反馈和长模型名称展示。
- 验收覆盖切换会话、流式生成、历史加载、编辑重发、缺少凭据以及草稿附件不兼容等状态。
- 浏览器或 Vite 预览只能辅助开发，不能替代本需求的桌面端视觉和交互结论。

### 不包含

- 不改变设置页默认聊天模型的既有职责，不增加会话切换后同步修改默认值的选项。
- 不在首版支持只对单条消息临时指定模型、发送按钮长按选择模型或 run 完成后排队切换。
- 不在聊天历史中展示持久模型切换分割线，也不把内部 `model_change` 伪装成用户或 assistant 消息。
- 不新增 IM 会话模型管理 UI，不新增 CLI 命令；既有 CLI 和会话 API 只做一致性与回归覆盖。
- 不允许 AG-UI、OpenAI 兼容接口或其他外部调用在已有 session 的 run 中途强制覆盖模型。
- 不迁移到 Vercel AI SDK，不重构整个 provider 层，不把会话模型状态交给 LiteLLM 或厂商 SDK 管理。
- 不新增模型、provider、模型能力目录或凭据存储方案。
- 不重做附件资产、Provider 物化或历史附件展示；这些继续沿用 059 和 060 已确认能力。

## 关键约束

- 会话模型是会话领域状态；全局默认模型是新会话初始化设置，两者必须分别持有和持久化。
- 模型目录与能力目录继续作为前后端共享的唯一事实源，不能为选择器复制静态模型列表或附件支持表。
- 模型切换以“先验证、后提交”为原子边界；失败时原有会话事件、有效模型和前端状态均保持不变。
- run 级冻结以真正参与调用的模型客户端、能力和上下文预算为准，不能只记录一个显示用模型字符串。
- 桌面端是本需求新增的产品入口；CLI、Bridge、Agent Runtime、IM 和外部协议仍需遵守同一会话协调语义。
- 真实 LLM 跨 provider 验收如需执行，必须按 `llm-api-confirm` 在运行前取得对应授权；自动化测试优先使用 fake/mock 固定机制行为。

## 验收标准

- **AC-1 新会话 pending model**：新会话默认展示设置页默认模型；首次发送前切换模型后，第一轮实际使用所选模型，且全局默认设置保持不变。
- **AC-2 已有会话切换与恢复**：已有会话成功切换后，下一轮使用目标模型；切换到其他会话、重启应用或重新打开历史后，各会话恢复各自有效模型。
- **AC-3 切换原子性**：目标模型不存在、缺少凭据或请求失败时，前后端均保持原模型，且不会写入错误的模型切换状态。
- **AC-4 run 内冻结**：包含至少一次工具调用和后续模型调用的完整 run 中，即使并发发起模型切换，所有调用、上下文预算和诊断记录仍使用 run 开始时冻结的模型；切换返回会话忙。
- **AC-5 生成期间禁用**：流式生成、历史加载、编辑重发和切换提交期间，桌面选择器不能发起不安全切换，并展示可理解的禁用原因。
- **AC-6 连续切换与 stale response**：快速连续选择、切换 session、删除/归档 session 和后台刷新产生乱序响应时，界面最终状态与当前 session 的后端有效模型一致。
- **AC-7 发送竞争**：模型切换提交期间不能发送新消息；切换成功后的首次发送使用新模型，切换失败后的发送继续使用原模型。
- **AC-8 IM/外部并发协调**：IM 或其他入口向同一 session 发起 run 时，模型切换遵守相同会话互斥边界，不会让任一 run 中途换模型。
- **AC-9 稳定错误反馈**：模型不可用、凭据缺失、会话忙和会话不存在具有稳定可区分的错误类型；桌面端分别提供正确提示，缺凭据时可以前往“模型与凭据”设置。
- **AC-10 附件草稿保护**：带草稿附件切到不兼容模型后，附件和文字保持不变但发送受阻；切回兼容模型后恢复可发送，移除附件后也可继续发送。
- **AC-11 历史附件与上下文**：同一会话跨模型后历史附件仍存在；目标模型不支持时按 059 语义降级，支持时可以通过目标 provider 正常物化。
- **AC-12 历史与诊断**：正常聊天历史没有模型切换分割线；诊断包和会话事件仍能确定每个 run/assistant 输出的实际模型及切换失败原因。
- **AC-13 跨 provider 连续性**：切换 provider 后，历史文本、已闭合工具事务、附件上下文和压缩摘要能被目标模型接受；取消或失败造成的不完整工具事务不会阻断后续会话。
- **AC-14 编辑重发一致性**：模型切换后编辑并重发最近用户消息，重发 run 使用当前有效模型，完成后模型状态不会意外回退。
- **AC-15 主流交互与桌面验收**：真实 Tauri 桌面端中的选择器位于输入区附近，当前模型清楚可见，列表可定位 provider/model，成功使用短暂反馈且不插入历史分割线；长名称、键盘操作、聚焦和禁用态正常。
- **AC-16 自动化覆盖与门禁**：核心事件状态、API 错误、run 冻结、上下文投影、前端 API/store、乱序竞态、附件不兼容和错误路径均有自动化测试，`scripts/check` 全绿。

## 开放问题

- 模型选择器应如何在现有 composer footer 中复用设置页能力并适配 provider 分组、长名称和凭据状态，需要在技术方案阶段结合现有通用组件确定。
- 桌面端切换请求与 Agent Runtime、CLI、IM 和外部协议如何共享同一会话协调边界，需要在技术方案阶段核实当前 scheduler 与 coordinator 的职责。
- run 开始时需要冻结哪些模型相关对象和能力快照，才能覆盖工具循环、上下文窗口与诊断而不泄漏可变 client，需要在技术方案阶段确定。
- 模型切换事件在编辑重发、取消、失败和事件失活后的投影规则，以及不完整工具事务的跨 provider 修复边界，需要结合现有会话事件模型确定。
- 每轮实际模型之外是否还需要记录 route 或模型目录版本等诊断快照，应以定位价值和持久化兼容成本在技术方案阶段取舍。

# 运行时凭据校验与应用反馈

## 状态

CONFIRMED

## 背景

桌面设置中心已经可以管理 DeepSeek、Kimi、Tavily、高德、和风天气和火山语音等运行时凭据，并在保存后按影响范围重启对话服务或语音服务。

当前界面仍把三个不同事实混成了“已配置”：

- 系统凭据存储中存在一个非空值；
- 第三方服务已经接受该凭据；
- 使用该凭据的本机服务已经完成重启并实际加载新配置。

因此，格式上非空但实际无效的凭据也会被显示为“已配置”。用户通常要等到首次使用相关能力时才发现鉴权失败，而且运行时错误还可能被误报为参数错误。保存触发服务重启时，设置页和其它受影响界面也缺少连续、具体的原因说明，用户只能看到控件暂时禁用或本机服务短暂离线。

问题不限于模型凭据。当前设置页包含多个 provider group，其中和风天气、火山语音等能力需要组合多项配置；逐字段保存会重复触发服务重启，也无法表达整组配置是否完整、是否经过验证、是否已经生效。

需求 036 明确没有包含自动校验 API Key 或在线连通性测试。本需求在既有凭据存储和服务托管能力之上，补齐可信的状态表达、适用 provider 的凭据校验、成组保存以及配置应用反馈。

## 目标

- 分别表达凭据的保存状态、验证状态和应用状态，不再把“存在值”当成“凭据有效且已经生效”。
- 对存在安全、低成本校验方式的 provider，在用户保存凭据时给出可行动的验证结果。
- 以 provider 或 capability group 为配置和应用单位，避免多字段配置逐项保存、逐项重启。
- 在保存、校验、应用和服务重启期间持续说明系统正在做什么，以及相关功能为什么暂时不可用。
- 保护已有可用配置：新凭据验证失败时，不得静默替换原先可用的凭据。
- 运行时后来出现鉴权失败时仍能准确归类，并引导用户回到对应设置项处理。

## 范围

### 包含

#### 可信的凭据状态

- 设置中心分别呈现：
  - 是否已保存以及当前生效来源；
  - 当前操作是否正在验证，以及实际得到的验证有效或验证无效结果；
  - 是否等待应用、正在应用、已经生效或应用失败。
- 未执行验证、本期不支持验证或暂时无法验证时，凭据保持正常的“已配置”表达，不展示长期“未验证”状态，也不得宣称“已验证”。
- “已验证”或“凭据有误”只能来自与当前凭据版本对应的实际验证结果。对于由应用管理且能可靠绑定版本的 keyring 凭据，验证结果应跨应用重启保留；凭据被覆盖、删除、迁移或来源变化后，旧结果必须失效。
- 对无法可靠跟踪内容版本的环境变量或 legacy 来源，应用重启后保持中性的“已配置”状态，不继承旧验证结论，也不展示“未验证”。
- 持久化状态只能记录随机凭据版本和非敏感验证元数据，不得保存 secret 明文、后缀、摘要或其它可用于识别、比对或恢复 secret 的材料。
- 来自环境变量或 legacy 配置的值必须显示真实生效来源。设置页写入 keyring 但被更高优先级来源覆盖时，不得宣称新值已经应用。
- 状态、错误和诊断信息不得包含 secret 明文、可恢复片段、鉴权 header 或第三方响应中的敏感内容。

#### Provider group 配置

- 设置页按 provider 或 capability group 管理相关凭据，至少覆盖：
  - DeepSeek；
  - Kimi；
  - Tavily；
  - 高德地图；
  - 和风天气；
  - 火山语音。
- 单字段 provider 可以直接提交该字段；多字段 provider 应允许用户整理完整组后一次提交。
- 一次 group 提交最多触发一次对应服务的应用流程，不能因同组包含多个字段而逐字段重复重启。
- group 状态必须能说明缺少哪些必要配置或当前只配置了部分能力，不能因为其中一个字段存在就把整组标为可用。

#### 保存与验证

- 对存在安全、低成本、无业务副作用校验方式的 provider，保存新凭据时自动进行 provider-aware 校验。
- 新凭据验证为无效时：
  - 若已有可用凭据，继续保留并使用旧凭据；
  - 若没有旧凭据，不得把新值展示成已验证或已生效；
  - 界面说明验证失败并允许用户修改后重试。
- 因网络、第三方暂时不可用或其它非凭据原因无法完成验证时，不能把结果误判为无效。用户确认后可以继续保存；保存后只表达“已配置”，保留本次校验未完成的可行动提示，不展示长期“未验证”状态。
- 本期不对火山语音凭据执行在线有效性校验。火山语音组只复用现有必要字段规则，支持成组保存并提供应用反馈；配置存在时按普通“已配置”表达，不宣称“已验证”。
- 暂不支持安全校验的其它 provider 也保持普通“已配置”表达，不宣称已经验证，也不得为了得到绿色状态发起有业务副作用或明显成本的操作。

#### 应用与服务重启反馈

- 保存流程向用户连续呈现“保存中、校验中、正在应用、正在重启对应服务、已生效”或对应失败阶段。
- 设置页在流程进行中禁用冲突操作时，必须显示禁用原因和当前阶段，不能只留下无说明的 disabled 状态。
- 对话、语音等其它受影响界面因配置应用而暂时不可用时，应说明正在应用哪类配置并重启哪个本机服务，不得只显示泛化的“服务未连接”。
- 服务重启被活跃任务阻止、重启失败或新服务未就绪时，必须区分“已保存但尚未应用”和“保存失败”，并提供明确的重试或后续处理方式。
- 连续配置操作应遵守既有服务安全边界，不得静默中断活跃语音通话或正在执行的 Agent run。

#### 运行时鉴权兜底

- 模型与其它受治理 provider 在实际使用中返回明确的 401、403 或稳定鉴权错误标识时，应归类为凭据失效，而不是参数错误或普通网络错误。
- 用户可见错误应说明对应能力的凭据无效或已失效，并引导到相关设置组重新配置或验证。
- 运行时鉴权失败应使与当前凭据对应的旧“验证有效”状态失效；不得继续展示绿色状态。
- 暂时性网络故障、限流、内容安全拒绝和普通请求参数错误不得被误归类为凭据无效。

### 不包含

- 不回显、复制或展示现有 secret 的明文、后缀或其它可恢复片段。
- 不查询第三方账户余额、套餐、用量或账单信息。
- 不建设完整的 provider 插件系统、任意自定义 provider 或远程 provider registry。
- 不在本期实现火山语音凭据的在线有效性校验，也不通过创建真实 RTC 房间、启动语音任务或其它有业务副作用的方式冒充校验。
- 不要求所有 provider 使用相同的校验请求；没有安全校验方式时只表达“已配置”，不展示“已验证”。
- 不把服务热重载作为目标；现有能力仍可通过受治理的服务重启应用配置。
- 自动化测试不调用真实第三方服务，不消耗真实 LLM、搜索、地图、天气或语音额度。

## 验收条件

- [ ] AC-1：设置页把“已配置”“已验证”或“凭据有误”与应用阶段分开呈现；从未验证、本期不支持验证或暂时无法验证时不出现长期“未验证”状态，也不伪造验证成功。
- [ ] AC-2：DeepSeek 和 Kimi 新凭据保存时会执行安全、低成本的 provider-aware 校验，并能区分有效、无效和暂时无法验证。
- [ ] AC-3：Tavily、高德和和风天气分别拥有明确的验证策略；本期没有安全、低成本校验方式时保持普通“已配置”表达，不伪造“已验证”。
- [ ] AC-4：无效的新凭据不会替换已有可用凭据；没有旧凭据时也不会被展示为已验证或已生效。
- [ ] AC-5：校验因网络或第三方暂时不可用而无法完成时，系统不误报凭据无效；用户确认后可以继续保存，保存后保持“已配置”并可重试验证，不出现长期“未验证”状态。
- [ ] AC-6：和风天气和火山语音等多字段配置按 group 一次提交，一次操作最多触发一次对应服务重启，并能指出字段不完整或能力仅部分配置。
- [ ] AC-7：火山语音本期不执行在线校验；设置页只按现有必要字段规则和普通“已配置”状态呈现，同时提供成组保存、应用和重启反馈。
- [ ] AC-8：保存、校验、应用、服务重启、完成和失败阶段均有持续可见的状态；被禁用的设置操作明确说明原因。
- [ ] AC-9：对话或语音界面因本次配置应用而暂时不可用时，向用户说明正在应用配置和重启对应服务，而不是只显示泛化离线状态。
- [ ] AC-10：环境变量或 legacy 来源覆盖 keyring 时，设置页显示真实生效来源，并明确说明新保存值为何尚未应用。
- [ ] AC-11：服务重启被活跃任务阻止或执行失败时，系统保留“已保存但未应用”事实，提供可行动的恢复方式，并且不静默中断活跃任务。
- [ ] AC-12：运行时明确的 401、403 或 provider 鉴权错误会失效对应验证状态，并向用户展示凭据问题与设置入口；限流、网络、内容安全和普通参数错误保持各自分类。
- [ ] AC-13：配置状态、日志、错误、诊断和测试 fixture 均不泄漏 secret 明文或可恢复片段。
- [ ] AC-14：自动化测试使用 mock provider 覆盖有效凭据、无效凭据、临时不可验证、未支持验证、多字段不完整、重启阻塞、重启失败和运行时凭据失效，不调用真实第三方 API。
- [ ] AC-15：既有凭据来源优先级、系统 keyring 存储、服务安全重启、普通对话、工具调用、语音输入和语音通话行为没有回归。

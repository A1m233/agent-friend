# 105 · QQ 附件与文字消息合并输入

## 状态

CONFIRMED

## 背景

agent-friend 已支持从 QQ 私聊接收静态图片、PDF、TXT 和语音，并把可读取附件纳入与桌面对话一致的 Agent 主链路。用户在 QQ 中发送“附件 + 配文”时，QQ 可能把附件和紧随其后的文字投递成两条独立消息；当前系统会把它们立即处理成两个用户回合并分别触发 Agent，导致附件与说明割裂、产生两次回复，也让模型难以准确理解用户原本的一次表达。

## 目标

- 用户在 QQ 私聊中先发送可读取附件、再紧接着发送配文时，agent-friend 将二者视为同一个用户回合。
- 纯附件消息仍能正常得到处理，最多只增加固定 3 秒等待。
- 普通文字消息和其他 QQ 会话不因附件等待而增加延迟或互相干扰。
- 模型输入、会话历史和用户可见回复保持同一条合并后的消息语义。

## 范围

### 包含

- 仅作用于 QQ 私聊入站消息。
- 当一条 QQ 入站消息只包含 agent-friend 当前可读取的附件而没有非空文字时，进入固定 3 秒等待窗口；等待期间不触发 Agent 或 LLM 调用。
- 首期参与等待的附件类型为 JPEG、PNG、WebP、PDF 和 TXT；一条平台消息本身携带的多个附件仍视为同一条附件消息。
- 同一 QQ Bot 绑定、同一私聊会话在窗口内到达的第一条非空纯文字消息，与待处理附件合并成一个用户回合，并在文字到达后立即开始处理，不继续等待剩余时间。
- 合并后的用户回合同时包含原附件和后续文字；模型只处理一次，桌面会话历史也只记录一条合并后的用户消息。
- 3 秒内没有符合条件的文字时，待处理附件按现有纯附件流程独立处理。
- 首期每个 QQ 私聊只维护一条待处理附件消息。等待期间又到达一条独立附件消息时，不把它追加到前一条，也不延长前一条窗口；前一条独立结算，后一条按新的独立消息处理。
- 不同 QQ Bot 绑定、不同私聊会话之间的等待状态严格隔离。
- 现有消息去重、附件下载与托管、模型能力校验、错误反馈、回复和会话持久化语义保持有效。

### 不包含

- 不连续聚合多条附件消息，不拼接多条文字消息，也不因后续消息为原窗口续期。
- 不让 GIF、语音、视频或其他当前不可读取的附件进入本合并窗口；它们继续沿用现有处理方式。
- 不改变 QQ 以外的 IM 通道、桌面对话或其他输入入口。
- 不新增等待状态提示、倒计时或桌面设置项。
- 不向用户开放等待时长配置；首期固定为 3 秒。
- 不保留两条平台原始消息作为两条用户可见会话记录；原始消息标识只用于去重、日志和诊断。

## 验收标准

- [ ] QQ 私聊收到一条纯 JPEG、PNG、WebP、PDF 或 TXT 附件消息后，前 3 秒内不触发 Agent 或 LLM 调用；窗口到期且没有配文时，只产生一个纯附件用户回合和一次 Agent 处理。
- [ ] 同一 QQ Bot 绑定、同一私聊在 3 秒内收到第一条非空纯文字消息时，等待立即结束；附件与文字只形成一个用户回合、一次 Agent 处理和一组回复。
- [ ] 合并后的桌面会话历史只显示一条同时包含附件与文字的用户消息，重新加载会话后语义不变。
- [ ] 普通纯文字消息不经过等待窗口，仍立即进入现有 Agent 主链路。
- [ ] 不同 QQ Bot 绑定或不同私聊中的消息不会互相合并、阻塞或重置等待窗口。
- [ ] 等待期间到达第二条独立附件消息时，两条附件消息不会合并；第一条独立结算，第二条作为新的独立消息处理。
- [ ] 文字在 3 秒窗口到期后才到达时，附件与文字分别形成两个用户回合，不发生追溯合并。
- [ ] GIF、语音和当前不支持的附件类型继续沿用现有反馈或转写行为，不进入本合并窗口。
- [ ] 重复投递、附件下载失败、模型不支持附件、运行时停止或 QQ 绑定变更时，不会产生重复 Agent 调用、跨会话串包或永久悬挂的待处理消息。

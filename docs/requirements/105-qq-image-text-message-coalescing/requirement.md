# 105 · QQ 附件与文字消息合并输入

## 状态

CONFIRMED

## 背景

agent-friend 已支持从 QQ 私聊接收静态图片、PDF、TXT 和语音，并把可读取附件纳入与桌面对话一致的 Agent 主链路。QQ 的传输事件粒度并不等于用户输入粒度：用户一次选择多张图片并发送时，QQ 也可能把每张图片分别投递为独立的 `C2C_MESSAGE_CREATE` 事件；附件与紧随其后的配文同样可能被拆开。系统若按平台事件逐条触发 Agent，就会把一次用户表达错误拆成多个用户回合、产生多次回复，并让模型只能逐张理解本应一起查看的附件。

## 目标

- QQ 私聊中一次用户发送动作包含多张可读取附件时，即使平台拆成多个事件，agent-friend 仍将它们还原为一个多附件用户回合。
- 用户先发送一批可读取附件、再紧接着发送配文时，agent-friend 将附件批次与配文视为同一个用户回合。
- 纯附件输入仍能正常得到处理；单附件保持短等待，多附件批次使用有界静默窗口收集，不因 Agent 回复耗时无限延长。
- 普通文字消息和其他 QQ 会话不因附件等待而增加延迟或互相干扰。
- 模型输入、会话历史和用户可见回复保持同一条合并后的消息语义。

## 范围

### 包含

- 仅作用于 QQ 私聊入站消息。
- 当 QQ 入站事件只包含 agent-friend 当前可读取的附件而没有非空文字时，进入有界批次等待；等待期间不触发 Agent 或 LLM 调用。
- 首期参与等待的附件类型为 JPEG、PNG、WebP、PDF 和 TXT；一条平台消息本身携带的多个附件仍视为同一条附件消息。
- 同一 QQ Bot 绑定、同一私聊、同一发送者在一次发送动作中被拆分投递的多个附件事件，聚合为一个逻辑附件批次；批次内附件按平台到达顺序稳定保留。
- 同一 QQ Bot 绑定、同一私聊会话在批次仍开放时到达的第一条非空纯文字消息，与完整待处理附件批次合并成一个用户回合，并在文字到达后立即结束批次。
- 合并后的用户回合同时包含原附件和后续文字；模型只处理一次，桌面会话历史也只记录一条合并后的用户消息。
- 批次静默窗口到期且没有配文时，完整附件批次按纯附件流程处理一次；内部实现允许按需要配置总时长硬上限，但 QQ 生产装配默认关闭。
- 首期每个 QQ 私聊只维护一条待处理逻辑输入批次。能够确定属于另一用户发送动作的附件消息不追加到前一批；前一批结算后，后一批建立自己的等待窗口。
- 真实 QQ 对照样本确认平台未提供可用的共享批次标识；首期以同一绑定、私聊和发送者的本机单调到达间隔作为唯一批次分界：相邻可等待附件在 3 秒静默窗口内到达则继续追加，静默达到 3 秒则前一批结算。QQ 生产配置不设总时长上限，因此大量附件只要持续在静默窗口内到达就保持同一批。
- 平台 `timestamp`、消息 ID 字符串和 `message_scene.ext` 不参与批次判断：一次多图发送可能跨平台秒，消息 ID 没有受支持的批次格式，`message_scene.ext` 的 `msg_idx` 是逐消息引用索引而不是多图批次号。
- 入站事件收集与 Agent 回合执行解耦：已有 Agent 回复仍在运行时，新到达的附件必须继续按真实到达顺序形成批次，不能等上一轮结束后才开始计时或逐条释放。
- 不同 QQ Bot 绑定、不同私聊会话之间的等待状态严格隔离。
- 现有消息去重、附件下载与托管、模型能力校验、错误反馈、回复和会话持久化语义保持有效。

### 不包含

- 不把能够确定为多次独立用户发送动作的附件请求连续聚合，也不拼接多条文字消息。
- 不让 GIF、语音、视频或其他当前不可读取的附件进入本合并窗口；它们继续沿用现有处理方式。
- 不改变 QQ 以外的 IM 通道、桌面对话或其他输入入口。
- 不新增等待状态提示、倒计时或桌面设置项。
- 不向用户开放等待时长配置；首期固定为 3 秒。
- 不承诺精确区分 3 秒内完成的两次独立附件发送；这是 QQ 未暴露发送动作批次号时的已知残余歧义。
- 不保留两条平台原始消息作为两条用户可见会话记录；原始消息标识只用于去重、日志和诊断。

## 验收标准

- [ ] QQ 私聊收到单条纯 JPEG、PNG、WebP、PDF 或 TXT 附件后，短等待期间不触发 Agent 或 LLM；窗口到期且没有配文时，只产生一个纯附件用户回合和一次 Agent 处理。
- [ ] 用户一次选择多张图片发送、QQ 将其拆成多个附件事件时，系统只形成一个包含全部图片的用户回合、一次 Agent 处理和一组回复。
- [ ] 同一 QQ Bot 绑定、同一私聊在附件批次开放期间收到第一条非空纯文字消息时，等待立即结束；全部附件与文字只形成一个用户回合、一次 Agent 处理和一组回复。
- [ ] 合并后的桌面会话历史只显示一条同时包含附件与文字的用户消息，重新加载会话后语义不变。
- [ ] 普通纯文字消息不经过等待窗口，仍立即进入现有 Agent 主链路。
- [ ] 不同 QQ Bot 绑定或不同私聊中的消息不会互相合并、阻塞或重置等待窗口。
- [ ] 能够确定由两次独立发送产生的附件消息不会合并；前后两次发送分别形成自己的用户回合。
- [ ] 文字在附件批次已结算后才到达时，附件与文字分别形成两个用户回合，不发生追溯合并。
- [ ] 上一轮 Agent 回复耗时超过批次窗口时，下一次多图输入仍按原始到达时间聚合，不出现每完成一次回复才释放一张图片的串行回复。
- [ ] GIF、语音和当前不支持的附件类型继续沿用现有反馈或转写行为，不进入本合并窗口。
- [ ] 重复投递、附件下载失败、模型不支持附件、运行时停止或 QQ 绑定变更时，不会产生重复 Agent 调用、跨会话串包或永久悬挂的待处理消息。

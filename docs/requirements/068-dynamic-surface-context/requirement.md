## 1. 背景

agent-friend 已能在语音通话中通过 system prompt 告知 Agent 当前正在与用户进行语音交流，从而生成适合朗读、简短可打断的回复。但除语音外，桌面对话和 IM 入口在 Agent 视角中都只是笼统的文字通道：Agent 不知道用户是在 agent-friend 桌面对话界面、QQ 私聊，还是其他文字入口与它交流。

这个缺口会让 Agent 在用户询问“我们现在在哪个端”时无法准确回答，也无法在相关场景中自然适应当前交互形态。长会话会让这个问题更容易被用户感知，但端信息不应依赖历史消息或摘要保留，而应反映每一轮真实的当前入口。

## 2. 目标

1. 让 Agent 在每轮对话中获得可信的当前交互端上下文。
2. 本期准确区分桌面对话、语音通话和 IM 三类交互端。
3. IM 上下文能够进一步区分具体软件，本期至少准确识别 QQ。
4. 即使会话很长、发生上下文压缩，或同一会话未来被不同入口访问，Agent 仍使用当前这一轮的真实交互端。
5. 为未来新增 IM 软件或新交互端保留清晰的扩展能力，不将本期三类端写死为难以扩展的特例。

## 3. 范围

### 3.1 包含

- 桌面主对话入口为当前回合提供“agent-friend 桌面对话”上下文。
- 语音通话入口继续提供“语音通话”上下文，并保持现有适合语音播报的表达约束。
- IM 入口为当前回合提供具体 IM 软件上下文；本期覆盖 QQ 私聊。
- 端上下文反映当前回合的实际入口，不被会话初始入口、上一轮入口或历史消息覆盖。
- 端上下文在长会话、历史裁剪和上下文压缩后仍对当前回合有效。
- Agent 在用户询问当前交互端，或端信息对当前任务确有影响时，可以准确使用该信息。
- Agent 不应在每轮回复中机械复述当前交互端。
- 无法识别或未提供交互端时，系统保持兼容且不向 Agent 伪造具体端信息。
- 端类型和 IM 软件种类具备可扩展性，后续新增入口时不必复制整条对话主链路。
- 为端上下文的组装、传递、渲染、入口区分、长会话保留和兼容路径补充自动化测试。

### 3.2 不包含

- 注入 Windows、macOS、Linux 等操作系统信息。
- 注入设备型号、设备标识、窗口状态、当前页面或其他细粒度客户端环境信息。
- CLI、开发用 Web 页面、调试客户端及其他未列入本期范围的入口。
- 桌宠气泡中没有当前用户交互入口的系统主动消息。
- 改变桌面端、语音端或 IM 的会话归属、消息格式、流式传输或 UI。
- 建设包含所有客户端能力、权限和实时状态的通用能力清单系统。
- 让客户端提供的普通用户文本直接成为可信的端上下文。
- 为 QQ 之外的具体 IM 软件实装端上下文。

## 4. 核心需求

### 4.1 当前交互端

- **R-1.1 桌面对话识别**：从 agent-friend 桌面主对话入口发起的回合，Agent 必须知道当前正在桌面对话界面与用户交流。
- **R-1.2 语音通话识别**：从语音通话入口发起的回合，Agent 必须知道当前回复会通过语音呈现，并继续遵循现有语音表达约束。
- **R-1.3 IM 软件识别**：从 IM 入口发起的回合，Agent 必须知道具体 IM 软件；QQ 私聊不得只渲染为笼统的“文字”或“IM”。
- **R-1.4 用户可理解名称**：呈现给 Agent 的端名称必须是可用于自然对话的产品名称，不得仅暴露内部协议名、路由名或技术标识。

### 4.2 动态与可信语义

- **R-2.1 每轮真实入口**：端上下文必须以当前回合的实际入口为准，不得因会话初始于另一端而沿用旧值。
- **R-2.2 不依赖历史**：端上下文不得依赖历史消息、记忆召回或上下文摘要才能对当前回合生效。
- **R-2.3 可信来源**：端上下文必须由 agent-friend 可信的运行链路确定，不得把普通用户消息中的自我声明自动升格为真实端信息。
- **R-2.4 未知兼容**：旧调用方或无法识别的入口没有端上下文时，对话主链路必须继续工作，Agent 不得被告知一个猜测的具体端。

### 4.3 表达边界

- **R-3.1 按需使用**：Agent 可以在用户直接询问、任务明显依赖当前端，或需要调整表达形式时使用端上下文。
- **R-3.2 避免机械复述**：系统对 Agent 的指引必须明确，端信息是必要时使用的上下文，不是每轮都要向用户播报的开场白。
- **R-3.3 不夸大能力**：知道当前交互端不等于拥有该端的所有操作能力；Agent 不得仅因得知端名称就声称能够操作窗口、账号或 IM 客户端。

### 4.4 扩展性

- **R-4.1 新 IM 软件可扩展**：未来新增具体 IM 软件时，能够添加其产品级端上下文，不需要为每个 IM 复制独立的对话主链路。
- **R-4.2 新交互端可扩展**：未来新增非 IM 交互端时，现有桌面、语音和 IM 行为不应成为阻碍扩展的写死分支。
- **R-4.3 有界的扩展口**：本期只建设承载端身份和必要交流指引的扩展边界，不扩张为通用客户端能力或权限框架。

## 5. 验收标准

- **AC-1**：从 agent-friend 桌面主对话发起一轮时，当轮模型上下文包含可理解的“agent-friend 桌面对话”端信息；询问“我们现在在哪个端”时，Agent 能据此回答桌面对话端。
- **AC-2**：从 QQ 私聊发起一轮时，当轮模型上下文明确标识“QQ”，而不只标识为文字通道、笼统 IM 或内部协议名。
- **AC-3**：从语音通话发起一轮时，当轮模型上下文仍包含现有语音通话身份和表达约束，现有语音回复行为不退化。
- **AC-4**：在同一会话中依次以不同交互端发起回合时，每轮模型上下文只反映当轮实际端，不沿用上一轮端信息。
- **AC-5**：在已有较长历史或已存在上下文压缩摘要的会话中发起新回合时，当前端信息仍出现在本轮模型上下文中。
- **AC-6**：端上下文未提供或无法识别时，旧调用路径仍能正常对话，system prompt 不伪造桌面、语音或具体 IM 软件。
- **AC-7**：普通用户消息即使声称“我现在在 QQ”或其他端，也不会改写系统为当轮确定的真实端上下文。
- **AC-8**：模型端上下文不包含操作系统、设备型号、窗口状态或未授权的细粒度客户端信息。
- **AC-9**：自动化测试覆盖桌面、QQ、语音、同会话跨端、长会话/压缩、未知端兼容和用户文本不可覆盖等路径，项目规定的检查门禁全部通过。
- **AC-10**：新增一个测试用 IM 软件或交互端时，可以通过新增局部定义和组装完成接入，不需要复制桌面、语音或 IM 对话主链路。

## 6. 依赖与约束

- 本需求沿用现有 system prompt 组装、AgentRuntime 和各入口对话主链路；具体接口与槽位设计在 `design.md` 中确定。
- 交互端是每轮的运行上下文，不因本需求改变会话归属或用户长期记忆。
- 本需求不改变语音、QQ 或桌面端的现有协议、消息呈现和会话控制语义。
- 如需使用真实 LLM 观察 Agent 对“当前在哪个端”的最终回答，执行前须遵守项目的真实 LLM 调用授权规则。

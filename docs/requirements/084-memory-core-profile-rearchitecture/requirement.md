# 核心身份资料与语义记忆重构

## 状态

CONFIRMED

## 背景

当前长期记忆把核心身份事实、普通语义事实以及 `pinned` / `priority` 等注入策略混合在同一套 Semantic 数据和召回流程中。这导致几个问题：核心身份事实会受到召回条数和字符预算限制；固定注入、事实分类与字段更新职责彼此混杂；普通 Semantic 的替换目标依赖确定性代码猜测；同一事实可能同时存在于核心信息和普通 Semantic 中；Memory Inspector 也难以准确呈现固定上下文与查询召回的区别。

本需求将核心身份资料从普通 Semantic 中建立为独立、结构化、可追溯的长期状态，并同步重构抽取、上下文装配、旧数据迁移和 Inspector，使系统能更稳定地认识用户及双方关系，同时保留普通记忆的开放表达能力。

## 目标

- 将长期记忆明确划分为核心身份资料与普通 Semantic，不再以 `pinned` / `priority` 表达产品语义。
- 让抽取过程优先、准确地更新核心身份字段，再处理普通 Semantic 的新增与替换，并避免重复存储。
- 让完整核心身份资料成为正常对话的固定基础上下文，不受查询召回 TopK 或普通记忆预算影响。
- 保留核心身份资料的来源与历史，使当前状态可用、变化过程可追溯。
- 让 Memory Inspector 能清晰区分核心身份资料、普通 Semantic、固定上下文装配与查询召回。
- 让项目所有者可在自己的电脑上同时从开发态和正式安装态使用 Inspector，而公开分发的安装版默认不可见、不可打开。

## 范围

### 包含

- 建立独立的 Core Profile 概念和结构化字段模型。
- 核心身份资料至少覆盖：
  - 用户希望被如何称呼；
  - 用户当前住处，支持同时存在多个当前住处；
  - 用户与特定 Agent/persona 之间的关系信息。
- 用户称呼、当前住处等用户自身资料跨 persona 共享；双方关系等关系资料按 persona 隔离。
- `employer` 不作为核心身份固定字段；相关事实仍可作为普通 Semantic 保存。
- 抽取过程先产出核心身份资料更新，再产出普通 Semantic 更新；被核心身份资料吸收的信息不得重复写入普通 Semantic。
- 核心身份资料在抽取时全量提供；普通 Semantic 在可用 token 预算内提供，放不下的条目本期直接省略，不额外使用确定性代码扫描确认。
- 普通 Semantic 支持明确的新增和替换语义；系统不得通过模糊文本猜测替换目标，也不得把无法匹配的替换静默降级为新增。
- 正常对话每轮完整装配当前 Core Profile，并独立于普通 Semantic、Episodic 的查询召回与排序。
- 显式记忆搜索不自动附带 Core Profile；身份类查询可按其自身查询语义访问相关信息。
- Core Profile 保存当前有效状态、来源、更新时间和变更历史；正常对话只使用当前有效投影。
- 对现有 `core`、`pinned`、`priority`、`fact_key` 数据提供迁移路径；无法可靠归入结构化字段的旧数据保守保留为普通 Semantic，不做确定性语义猜测。
- Core Profile 异常膨胀、重复或无法完整装配时显式暴露异常，不在读取阶段静默截断。
- Memory Inspector：
  - 在 Semantic 浏览区域支持“全部 / 核心身份信息 / 普通 Semantic”筛选；
  - 核心身份信息展示字段、作用域、当前值、更新时间与来源；
  - Recall Trace 分别展示固定装配的 Core Profile 与按 query 召回的普通记忆；
  - 普通召回预算不再包含 Core Profile 配额；
  - 保持只读。
- 增加本机 Owner Mode：开发态默认启用 Inspector；正式安装态仅在本机显式启用后可见、可打开，并能跨应用升级保留；公开分发安装版默认关闭。

### 不包含

- 在 Inspector 中手工新增、修改或删除记忆。
- 对超出普通 Semantic 抽取预算的旧事实执行分块扫描、多轮 LLM 检查或确定性语义确认。
- 将历史住处混入“当前住处”数组；历史状态只保留在可追溯记录或普通记忆历史中。
- 根据用户名、固定机器码或专门分发另一种安装包来识别项目所有者。
- 把本机 Owner Mode 设计成远程身份认证、DRM 或抵御本地管理员的安全边界。
- 因本次重构引入通用的可配置记忆字段插件系统。

## 关键信息

- Core Profile 是正常对话的固定基础状态，不属于普通查询召回结果。
- “全量装配”是正常语义；安全阈值只用于发现和阻止异常数据，不是日常截断策略。
- 用户当前住处是多值当前状态；历史住处与当前状态必须可区分。
- Core Profile 与普通 Semantic 各自只有一个权威存储位置，默认不双写。
- 本机 Owner Mode 是机器本地、默认关闭的能力开关；公开安装包和可信测试安装包不会携带项目所有者电脑上的开启状态。

## 验收条件

- [ ] AC-1：用户表达“以后叫我 X”后，系统将 X 更新为用户期望称呼；后续正常对话无需相关性命中即可完整获得该信息。
- [ ] AC-2：用户可以拥有多个当前住处；新增、移除或替换当前住处时，Core Profile 投影正确，历史状态和来源仍可追溯。
- [ ] AC-3：双方关系按 persona 隔离；切换 persona 不会错误继承另一 persona 的关系资料，而用户自身的称呼和当前住处仍跨 persona 共享。
- [ ] AC-4：`employer` 不再作为核心身份字段；相关内容如值得记忆，只进入普通 Semantic。
- [ ] AC-5：同一轮抽取先处理 Core Profile，再处理普通 Semantic；已写入 Core Profile 的事实不会重复新增为普通 Semantic。
- [ ] AC-6：普通 Semantic 的替换操作明确指向本轮可见的现有事实；目标无效或不可见时操作失败并可观察，不会由确定性代码模糊猜测，也不会静默变成新增。
- [ ] AC-7：Core Profile 在抽取和正常对话上下文中均完整提供，不受普通召回 TopK、固定条数或字符配额影响；异常过大时系统显式报告而不是静默截断。
- [ ] AC-8：普通 Semantic 只在 extraction token 预算内提供；预算外事实本期不会触发额外扫描，相关限制有可观测记录。
- [ ] AC-9：正常自动对话上下文包含完整 Core Profile 和预算内查询召回记忆；显式记忆搜索结果不自动附带 Core Profile。
- [ ] AC-10：现有核心、固定和优先级记忆完成兼容迁移；可可靠映射的数据进入 Core Profile，其他活跃事实不丢失并保留为普通 Semantic。
- [ ] AC-11：Inspector 可按“全部 / 核心身份信息 / 普通 Semantic”筛选，并能查看核心字段的作用域、当前值、更新时间与来源。
- [ ] AC-12：Inspector 的 Recall Trace 将固定 Core Profile 装配与普通查询召回分开呈现，普通召回预算中不再出现 Core 配额。
- [ ] AC-13：开发态默认可打开 Inspector；同一正式安装包在普通用户机器上默认看不到且无法打开，在项目所有者电脑显式启用 Owner Mode 后可用，并在正常升级后保持启用。
- [ ] AC-14：Owner Mode 关闭时，不能仅通过直接调用桌面命令或 Inspector 专用本地接口绕过入口限制。
- [ ] AC-15：核心抽取、作用域、替换目标校验、迁移、上下文装配、Owner Mode 和 Inspector 筛选具有可重复的自动化回归覆盖；概率性的抽取质量另以受控评测或明确授权的真实模型验证记录。

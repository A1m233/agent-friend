# 095 · Agent 运行恢复与终止语义

## 状态

CONFIRMED

## 背景

agent-friend 已经具备模型工具调用、参数校验、权限审批、工具执行、运行预算和跨协议终态投影。需求 005 明确要求工具失败不能让对话中断，需求 065 又为工具循环增加了预算与无进展保护，issue 054 则修复了非法工具参数被误报为“运行边界”并正常完成的问题。

现有实现仍把若干本可由 Agent 在同一回合内修正的失败升级成宿主终止条件：模型第二次生成非法工具参数时，Runtime 直接把本轮标为失败；重复错误、空结果或重复证据达到固定次数时，宿主禁用工具并强制收尾；普通工具只要声明需要用户动作，也会阻止 Agent 尝试其它路线。模型没有返回可见内容、输出额度耗尽在推理中或流在产生有效输出前超时时，同样会把恢复责任交还给用户。

这些行为让“模型或工具的一次局部失败”变成“用户必须重新发消息”，并使 Agent 无法利用刚得到的错误信息修正参数、换工具或改变策略。部分强制收尾还会被记录成正常完成，掩盖真实停止原因。项目需要建立统一的运行恢复与终止语义，让可修正错误留在 Agent 循环内，只把真正无法安全继续的边界提升为终态。

## 目标

- 模型、工具和短暂传输层的可修正失败成为 Agent 的可见观察结果，Agent 可以在同一 run 内继续完成用户目标。
- 宿主只在用户决定、明确运行政策、不可恢复外部条件或内部基础设施失效时终止当前 run，不根据错误出现次数替 Agent 判断任务已经失败。
- 非法工具调用始终在执行和授权前被拒绝，同时保留可恢复的工具结果、活动状态和诊断关联。
- 空模型响应、输出额度耗尽和未产生有效输出的流中断具有安全的同轮恢复路径，不要求用户无条件重发。
- Runtime、实时协议、桌面对话、历史恢复和日志对“失败后继续”“等待用户”“正常完成”和“真正终止”保持一致。
- 现有 schema、权限、审批、取消和副作用保护不因提高恢复能力而放宽。

## 范围

### 包含

#### 统一可恢复错误与终止错误

- 错误是否终止 run 由“当前执行是否还能安全取得新判断或完成用户目标”决定，不由同类错误已经出现几次决定。
- 模型生成的非法 JSON、缺少必填字段、未知字段、错误字段类型、未知工具或不支持的参数形状属于可修正错误。
- 工具执行失败、超时、拒绝、空结果、无新证据和普通能力不可用属于模型可见结果；Agent 可以修正输入、换工具、换路线或基于已有证据回答。
- “建议用户完成某个动作”本身不是宿主终止权限。只有协议已经进入真实等待用户决定或外部动作的状态时，运行层才可以暂停相应执行；普通错误元数据不得禁止 Agent 尝试其它能力。
- 用户取消、用户中途替换请求、明确配置的运行预算、安全或权限硬边界、不可恢复的凭据/额度/内容策略限制、会话损坏或持久化失败，以及宿主内部不变量破坏，可以终止或拒绝当前 run。
- 不得通过静默切换模型、Provider、账号、权限级别或工具实现来伪造恢复。

#### 工具参数与工具结果恢复

- 非法工具调用不得执行工具主体、创建副作用、消费审批决定或向用户发起授权。
- 宿主能够识别工具名和调用标识时，非法调用应闭合为失败工具结果，并向模型提供稳定错误类别与可行动的修正说明。
- 宿主无法可靠识别完整调用时，也应把安全、脱敏的失败事实加入模型上下文并继续采样；不得生成无法关联的授权卡片或假装工具已经运行。
- 连续多次生成非法参数仍属于同一 run 内的模型自修正过程，不设置“失败 N 次即终止”的特殊门槛。
- 重复错误、重复空结果和重复证据可以继续作为诊断指标或模型软提醒，但不得自行禁用工具、强制最终回答或把 run 标为完成。
- 工具失败后取得合法结果、换用其它工具、并行批次中的任一调用取得新证据，均不得被先前的失败标志覆盖。
- 原始工具请求、失败结果、后续修正调用和最终结果按实际顺序进入事件历史，实时流和刷新恢复后保持一致。

#### 模型请求与流恢复

- 模型请求正常结束但没有可见正文、工具调用或其它可用输出时，在同一 run 内重新采样，而不是立即返回 run error。
- 模型把输出额度耗尽在推理内容中且没有产生可用输出时，应通过同轮恢复让模型生成可见结果；不得把隐藏推理消耗表述成用户任务失败。
- 流超时或临时传输错误发生在任何可见文字、完整工具调用或其它可用响应项之前时，可以安全重试同一模型请求。
- 已经发布响应项或执行工具后，不得盲目重放整个请求。系统应保留已经完成的响应项，从可安全续接的边界继续；无法安全续接时才以准确原因终止。
- 模型请求重试、退避和最终失败受统一传输恢复政策约束；不得用模型参数错误次数代替请求级恢复政策。
- 同轮恢复继续使用用户选择的模型和既有路由约束，不自动跨模型或跨 Provider fallback。

#### 响应项、文字与失败活动

- 同一次模型响应中的助手文字、reasoning 和工具调用作为独立响应项按顺序处理；一个工具调用失败不得回滚同批次中已经完成的无害助手文字。
- 已经展示或持久化的原始响应项不因后续工具失败被静默删除或改写；模型后续上下文必须加入权威失败结果，最终回答不得继续依赖“工具已经成功”的虚假前提。
- 若助手文字包含与真实执行状态冲突的声明，历史保留原始事实，后续模型上下文和最终回答必须以宿主工具结果纠正；不得为了清理文案而丢失审计链路。
- 能够绑定具体工具调用的参数错误在工具活动中使用失败终态呈现，并允许与相邻普通工具活动按既有紧凑规则组织；详细 schema 和内部堆栈不进入默认用户文案。
- 无法绑定具体工具调用的模型输出错误使用明确的可恢复运行状态，不生成空工具卡片、空授权卡片或虚假的完成记录。
- 恢复进行中时，用户能够看出 Agent 仍在处理；只有 run 真正结束时才发送完成、失败、取消或等待用户的终态。

#### 运行政策与安全边界

- 显式配置的模型续轮、工具调用总数、整轮时长、上下文和传输重试预算继续作为通用资源边界。
- 接近通用资源边界时可以提醒模型优先收敛；到达边界后停止新动作并基于已有结果诚实收尾。
- 通用资源边界必须按实际资源消耗计数，不能把特定错误类别、失败次数或无进展启发式伪装成预算。
- 用户取消、审批拒绝、权限不足和超时继续阻止对应副作用；提高恢复能力不得导致已拒绝调用被重放或已完成写入被重复执行。
- 任何恢复重试都必须保持原调用标识、响应项顺序、权限上下文和副作用边界可追溯。

#### 终态、历史与可观测性

- Runtime 终态明确区分正常完成、用户取消、等待用户、资源边界耗尽、不可恢复外部错误和内部失败。
- 可恢复错误不能发送 run error，也不能仅因为宿主停止工具循环而发送正常完成。
- 每个宿主强制停止都保留稳定 reason code、触发边界、已执行工具数、模型调用数和是否已产生副作用；正常完成不得丢失非默认 stop reason。
- AG-UI、OpenAI 兼容出口、桌面对话和 IM 使用相同的内部终态事实，不得出现一个出口显示完成、另一个出口显示失败。
- 日志和诊断可以记录失败类别、参数形状、恢复次数、响应项状态和最终终态，但不得记录凭据、用户文件正文、不必要的完整参数或隐藏推理。
- 会话历史能够重建“失败调用 → 模型修正 → 合法调用 → 最终回答”的完整链路，并在后续上下文中以真实结果为准。

#### 验证与回归

- 使用确定性 fake/model script 覆盖连续多次非法参数后成功修正、非法与合法调用交错、不同工具换路、并行批次部分失败和后续正常完成。
- 覆盖助手文字与非法工具调用同批出现，证明无害文字保留、失败结果进入上下文、后续回答不会声称工具已经成功。
- 覆盖空响应、输出额度耗尽、有效输出前流超时、有效输出后断流和工具副作用后的恢复边界。
- 覆盖普通用户动作提示不会阻止替代路线，真实等待用户状态仍能暂停并在用户响应后继续。
- 覆盖取消、审批拒绝、通用预算、不可恢复外部错误和内部失败，证明本需求不会把真实终止边界降级成无限重试。
- 从本次 DeepSeek V4 Flash Vision 事故和 issue 054 的 Kimi 事故提炼行为回归，并加入未参与目标样本设计的相邻或 holdout case。
- 真实模型复验使用事故实际模型并遵守真实 LLM 调用授权；单次通过只作为观察证据，不替代确定性契约测试。

### 不包含

- 不放宽现有工具 JSON Schema、字段校验、权限、审批、路径保护、命令安全或内容安全策略。
- 不为规避参数错误而删除必要字段、开放未知字段或把宿主已无法验证的内容直接交给工具执行。
- 不自动切换模型、Provider、API Key、账号、隐私路由或数据保留策略。
- 不承诺任何错误都无限重试；真实外部故障、内部失败和显式通用资源边界仍可以结束当前 run。
- 不在本需求中实现跨重启任务恢复、后台作业调度、长任务通知或无人值守执行。
- 不重新设计全部工具活动的信息密度、分组视觉和 Dock；需求 091 继续拥有通用工具活动展示。
- 不新增具体业务工具，也不修改 Todo、文件、命令、搜索等工具的领域能力。
- 不迁移整个模型调用层到新的 Provider API；技术方案只在现有边界内补足可靠恢复。
- 不修改用户主动编辑重发、切换模型或取消 run 的产品流程。

## 关键约束

- 本需求恢复需求 005“工具失败不让对话中断”的产品底线，并覆盖需求 065 中由重复失败次数直接触发无工具收尾的行为；需求 065 的显式资源预算、取消、超时和诊断能力继续保留。
- issue 054 的“非法调用不执行、不授权、错误事实对用户可见”继续成立；其“第二次非法参数直接让 run failed”的终态策略由本需求替代。
- 需求 091 继续负责工具活动的紧凑展示。本需求只要求失败和恢复状态能够被其准确消费，不重新定义通用分组和视觉样式。
- 工具契约继续以当前模型实际收到的 schema、模型可见错误和运行时确定性校验为准；可恢复不等于接受非法输入。
- 原始事件是审计真相源，模型上下文可以使用安全投影纠正错误前提，但不得篡改已发生的调用、结果或用户决定。
- 真实 LLM 调用会产生外部 token 消耗，必须遵守 `llm-api-confirm`；事故回归与 holdout 选择继续遵守 `agent-eval-governance`。

## 验收条件

- [ ] AC-1：模型连续生成两次及以上非法工具参数时，当前 run 不因失败次数终止；非法调用不执行、不授权，模型收到可行动错误后仍可在同一 run 内生成合法调用并完成用户目标。
- [ ] AC-2：未知工具、未知字段、缺少必填字段、字段类型错误和损坏 JSON 都闭合为可恢复失败事实；能够识别调用时产生失败工具结果，不能识别时也不产生空授权卡片或孤立 pending 状态。
- [ ] AC-3：重复错误、空结果或重复证据达到任意固定次数都不会由 `no_progress` 自动禁用工具或强制收尾；相关指标只用于诊断或模型软提醒。
- [ ] AC-4：一个批次中部分调用失败、另一个调用成功或取得新证据时，run 继续使用成功结果，失败标志不会覆盖已有进展。
- [ ] AC-5：普通 `requires_user_action` 结果不会自动阻止模型尝试其它工具或路线；只有真实等待用户的协议状态会暂停相应执行，并能在用户响应后继续。
- [ ] AC-6：模型无可见输出、输出额度耗尽在推理中，或流在任何有效响应项前超时时，系统在同一 run 内执行安全恢复；恢复不切换用户所选模型或 Provider。
- [ ] AC-7：流在助手文字、完整工具调用或工具副作用之后中断时，不盲目重放已完成动作；已经完成的响应项保留，并从可安全边界续接或以准确原因终止。
- [ ] AC-8：助手文字与非法工具调用同批出现时，响应项按原始顺序保留；失败结果进入后续模型上下文，最终回答不把失败调用表述成成功，也不删除无关的已展示文字。
- [ ] AC-9：可绑定调用的参数错误在工具活动中呈现失败终态并允许后续恢复；无法绑定调用的错误使用可恢复运行状态，实时界面不会提前显示 run 已完成或要求用户无条件重试。
- [ ] AC-10：用户取消、审批拒绝、明确资源预算、不可恢复凭据/额度/内容策略错误、会话持久化失败和内部不变量错误仍会阻止不安全继续，并具有准确终态。
- [ ] AC-11：Runtime、AG-UI、OpenAI 兼容出口、桌面对话、IM 和历史恢复对完成、失败、取消、等待用户及资源边界使用一致事实；每个宿主强制停止都有可查询 reason code。
- [ ] AC-12：自动化测试覆盖连续 malformed 后恢复、非法与合法调用交错、并行部分成功、普通用户动作提示、空响应、输出预算耗尽、有效输出前后断流、取消和显式预算。
- [ ] AC-13：事故行为被固化为可重复回归；目标 case 使用 DeepSeek V4 Flash Vision 与 issue 054 的 Kimi 事故模型，相邻或 holdout case 证明恢复策略不会误放行副作用、无限重放或降低 schema 强度。
- [ ] AC-14：工具 schema、权限审批、命令和文件副作用保护、模型切换、会话持久化、上下文治理及需求 091 的工具活动展示没有回归。
- [ ] AC-15：项目规定的 lint、typecheck、单元测试、集成测试和 `scripts/check` 全量门禁通过；真实模型复验按单次授权记录模型、调用量和报告证据。

## 开放问题

- 当 Provider 返回的损坏调用缺少稳定 call id 或工具名时，现有事件协议如何生成可恢复的关联项，需要在技术方案阶段确定。
- 模型请求在“尚无有效输出”和“已有响应项”之间的精确安全续接边界，以及各类传输错误的退避与恢复方式，需要结合当前 Provider 能力设计。
- 输出额度耗尽后的同轮恢复采用新的采样请求、输出配置调整还是模型可见收敛提示，需要以不重复副作用和不静默改变用户模型设置为前提确认。
- 真实等待用户的协议状态与普通“建议用户操作”错误元数据如何拆分，需在技术方案中核对现有审批、登录、文件和命令入口。
- 工具名或调用标识可用但参数校验失败时，现有紧凑工具活动如何消费失败终态并保持历史兼容，需要与需求 091 的事件投影共同确认。

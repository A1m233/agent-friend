# 070 · Todo 管理与可选提醒

## 状态

CONFIRMED

## 1. 背景

用户会在长期对话中反复让 Agent“记一条待办”“列一下备忘”或“这条先不管了”。当前这些内容只存在于会话历史及其压缩摘要中，Agent 需要依靠历史召回重新拼出清单，因而存在以下问题：

- 待办没有稳定标识和明确状态，容易遗漏、重复或把“取消”误认为“完成”；
- 换一个会话后无法可靠地查看和管理同一份清单；
- 会话压缩、归档或删除可能改变 Agent 对现有待办的判断；
- 即使用户说了具体时间，系统也没有可持久化、可修改、可取消的提醒记录；
- 已有主动触发基础设施只有固定示例 source，尚未形成用户可管理的产品能力。

Todo 应当成为独立、结构化、持久化的用户数据。Agent 只是通过统一能力操作 Todo 的一个入口；未来独立 Todo 页面、其他客户端或自动化入口应复用同一套后端，而不是从某个会话的聊天记录中反推状态。

## 2. 目标

- 让用户能够通过自然对话可靠地创建、查看、修改、完成、取消和重新打开 Todo。
- 让 Todo 可以不带提醒，也可以附加一条或多条一次性或基础周期提醒。
- 让提醒在到期时无需用户先发消息即可主动触发，并在应用重启后恢复调度。
- 让到期提醒在对话中同时具备准确、可核对的固定事实呈现和符合 persona 的自然回应；同一批提醒只触发一轮 Agent，模型失败不能影响提醒本身。
- 在桌面对话、IM 和桌宠之间只选择一个主要投递目的地，并优先保证用户离开电脑后仍可通过已在线 IM 收到提醒。
- 建立与会话、长期记忆和具体交互入口解耦的 Todo 后端，为后续独立 Todo UI 提供稳定基础。
- 对时间、时区、重复规则和错过触发给出明确、可预测、可验证的语义。

## 3. 核心概念与边界

### 3.1 Todo 是唯一主体

- Todo 是用户需要记住或完成的一件事项。
- Todo 可以完全没有时间信息，此时仍能被持久化、查询和管理。
- Reminder 不是另一类顶层事项，而是附着在 Todo 上的可选提醒规则。
- 一个 Todo 可以没有 Reminder，也可以有一条或多条 Reminder。
- Todo 不归属于创建它的会话。创建会话或入口可以作为来源信息记录，但不能决定 Todo 的所有权、可见范围或唯一通知目的地。

### 3.2 Reminder 与周期 Todo 分离

- 一次性 Reminder 在指定时间触发一次，之后该 Reminder 结束。
- 周期 Reminder 在 Todo 仍有效时按固定规则重复触发。
- Reminder 触发不会自动把 Todo 标为完成。
- Todo 被完成或取消后，其尚未触发的 Reminder 全部停止。
- 本期不实现“完成一次后自动生成下一次 Todo”的周期 Todo。该能力与“同一 Todo 重复提醒”语义不同，后续如有需要独立扩展。

## 4. 功能范围

### 4.1 Todo 生命周期

- 创建 Todo，至少包含简短标题，并可包含补充说明。
- 按状态列出 Todo，默认优先返回仍需处理的事项。
- 获取单条 Todo 的完整信息及其 Reminder。
- 修改 Todo 的标题、说明和 Reminder。
- 将 Todo 标为完成，并记录完成时间。
- 取消不再需要处理的 Todo；取消与完成是不同状态。
- 将已完成或已取消的 Todo 重新打开。
- Todo 具有稳定标识，后续修改不能依赖标题文本猜测目标。
- 本期不提供不可恢复的硬删除；完成和取消记录保留，便于追溯和未来 UI 展示。

### 4.2 一次性提醒

- 支持为 Todo 添加在指定日期和时间触发一次的 Reminder。
- 同一个 Todo 可以添加多条一次性 Reminder，例如提前一天和提前一小时分别提醒。
- Reminder 触发后保留触发记录，但不再重复触发。
- 已触发的一次性 Reminder 不因应用重启、Todo 修改或重复加载而再次触发。

### 4.3 基础周期提醒

- 支持常见固定周期，包括每天、每周指定星期、每月指定日期，以及每 N 天、周或月。
- 周期规则可以有明确开始时间，并可选择结束时间或最大触发次数；未设置结束条件时，在 Todo 完成或取消前持续有效。
- 同一个 Todo 可以同时具有一次性和周期 Reminder，也可以具有多条不同周期 Reminder。
- 月末、闰年、夏令时切换和不存在或重复的本地时间必须采用稳定规则，不能因一次异常导致整个 Reminder 永久失效；具体规范由技术方案锁定并自动化验证。
- 本期不支持任意 cron 文本、复杂节假日规则、“每月最后一个工作日”等高级日历表达。

### 4.4 时间与时区

- 每条 Reminder 都必须具有明确时区；用户没有主动指定时，使用本次请求可验证的当前用户时区。
- 创建或修改 Reminder 后，Agent 必须向用户回显规范化后的绝对日期、时间、时区和周期规则。
- “几分钟/小时/天/周后”的一次性 Reminder 可直接提交结构化相对时长，由后端以本次推理的可信时间归一化为绝对计划时间；“明天”“下周一”“晚上”等日历或口语化表达仍由 Agent 结合可信当前时间转换，决定结果所需的信息不足时必须先澄清。
- 后端必须校验结构化时间和周期规则，不能因为调用方是 Agent 就接受无效或自相矛盾的数据。
- 用户设备时区变化后，既有周期 Reminder 继续遵循创建或最后修改时确认的时区，除非用户明确更新。

### 4.5 主动触发与错过触发

- Reminder 到期后产生用户级到期事件，由产品的主动触发和通知出口承接；不要求用户先发送一条消息。
- 到期事件至少包含能够定位 Todo、Reminder、计划触发时间和本次触发身份的必要信息。
- Todo 数据和 Reminder 调度不依赖来源会话继续存在，也不能把来源会话当作唯一展示目的地。
- 应用或运行时保持运行时，Reminder 应在合理误差内触发并抵达当前支持的用户可见主动出口。
- 应用完全退出时，本期不承诺由操作系统唤醒进程。
- 重启后恢复所有有效 Reminder。离线期间错过的一次性 Reminder 至多补发一次；同一周期 Reminder 错过多次时合并为一次最新提醒，然后继续计算下一个未来触发点，避免连续轰炸。
- 更新、完成或取消与触发并发时，不得在状态已经失效后继续产生新的用户提醒；同一次计划触发不得重复交付。

### 4.6 到期提醒的对话呈现

- 到期提醒进入桌面对话时，先展示一张最小只读 Reminder 卡片，固定展示 Todo 内容、计划触发时间、周期和当前状态等可核对事实。
- Reminder 卡片的数据必须来自持久化的 Todo、Reminder 和本次触发记录，不能由模型生成或改写。
- 同一次调度领取、且投递到同一目标会话的一个或多个 Reminder 组成一个提醒批次；单条 Reminder 视为只有一个事件的批次。
- 每个提醒批次只触发一轮正常的 Agent 回应。Agent 接收批次内完整、结构化的 Reminder 事件，并结合当前目标会话、persona 和普通会话能力自行决定如何回应以及是否调用工具；Todo 提醒链路不额外注入回答方式或工具选择指令。
- Agent 回应属于可失败的增强层。模型不可用、调用失败或回复中断时，批次内固定事实仍必须准时出现，不得重建或重复交付这些提醒。
- 到期提醒进入 IM 时，先发送包含同等关键事实的稳定提醒内容；同一提醒批次再由对应 IM 会话中的 Agent 作一轮正常回应。IM 不支持专用卡片不能影响提醒准确性。
- 桌宠作为无明确目标会话时的降级出口，只展示固定提醒事实，不为生成 Agent 回应而虚构或猜测会话。
- 多条 Reminder 同时降级到桌宠时，每条固定事实都必须独立保留并可逐条关闭；新 Reminder 不得覆盖尚未关闭的 Reminder，超过当前可见容量时应排队而不是丢弃。
- 本期卡片只承担到期事实展示，不提供完成、取消、编辑、稍后提醒等直接操作；这些交互与完整 Todo UI 留待后续扩展。

### 4.7 单目的地投递与活跃判断

- 每次到期触发必须先形成独立、持久化且可幂等识别的提醒记录，再由统一投递策略在桌面对话、IM 和桌宠之间选择一个主要目的地。
- 同一次触发不得因为多个出口同时在线而主动广播到多处；只有已选出口明确不可用时才允许按策略降级到另一处，并最终记录唯一成功目的地。
- 桌面对话只有在运行状态快照仍然新鲜、对话窗口可见且聚焦、当前目标会话明确、设备未锁屏或休眠时，才视为具有足够证据的活跃目的地。
- 锁屏、休眠、桌面对话失焦或最小化立即使桌面对话失去活跃资格；用户安静阅读或等待时长本身不得使仍聚焦的桌面对话失去资格。
- 不能取得可靠桌面状态、平台能力不支持、探测超时或信号互相矛盾时，状态必须视为未知，不能乐观推断用户仍在桌面。
- 桌面不活跃或状态未知时，若存在在线 IM 绑定，优先投递到最近发生用户活动的 IM 会话，使用户远离电脑时仍能收到提醒。
- 桌面与 IM 都有近期明确用户活动时，以最近一次真实用户交互所在的入口为主要目的地；没有 IM 活动历史时不得在多个绑定间随机选择。
- IM 不可用而桌面运行时，才退到桌宠主动气泡；所有出口都不可用时保留待投递状态，待能力恢复后按错过触发规则处理。
- 操作系统 idle 时长继续作为可观测的诊断和桌面/IM 最近交互比较信号，但不作为桌面对话资格的硬门槛。

### 4.8 统一后端与 Agent 工具入口

- Todo 的存储、校验、生命周期和提醒规则由统一 Todo 后端负责。
- Agent 工具、未来 Todo UI 和其他入口都调用同一套应用服务或等价业务边界，不各自实现状态机和调度规则。
- 对话工具至少覆盖创建、列表、获取、修改、完成、取消和重新打开 Todo，以及增删改 Reminder。
- 新建 Todo 时用户已经给出提醒，工具必须支持在同一次 create 中一并提交 Reminder；后补提醒操作只用于已经存在的 Todo，不能把一次创建拆成两个有依赖的工具调用。
- 工具返回结构化、可确认的最新状态，使 Agent 能自然复述结果，但不能让模型输出反向成为 Todo 的事实源。
- 精确工具名称、参数 schema 和调用拆分方式在技术方案阶段结合现有 Tool Protocol 确定；需求层不预先锁死为多个工具或单个复合工具。

## 5. 用户体验与信任边界

- 用户说“记个备忘”而未提供时间时，创建普通 Todo，不擅自附加提醒。
- 用户说“明天九点提醒我提交材料”时，创建 Todo 并附加一次性 Reminder；确认中展示完整日期、时间和时区。
- 用户说“给我两个两分钟后的 Todo”时，可以分别创建两个 Todo，但每个 Todo 的创建与其 Reminder 必须各自在同一次工具调用中完成；两条相对提醒使用该次模型推理看到的同一可信时间锚点。
- 用户说“每周一和周四九点提醒我检查项目进度”时，创建 Todo 并附加周期 Reminder；确认中展示周期和停止条件。
- 用户说“这条做完了”时标为完成；说“这条不管了”时标为取消。目标不唯一时先列出候选并澄清，不能按相似标题静默修改。
- 用户可以从任意会话查询和管理同一份 Todo 清单，不需要返回创建它的原会话。
- 对话中的固定 Reminder 卡片或 IM 固定提醒内容负责准确传达 Todo 和计划时间，并作为提醒事实与状态的权威来源；Agent 回应不反向成为 Todo 或 Reminder 的状态来源。
- 工具或调度失败时应明确说明本次操作未成功，不得只在对话中口头答应“记住了”。

## 6. 不包含

- 独立 Todo 页面、列表视图、日历视图、设置面板及完整 Todo 管理 UI；本期只包含对话中的最小只读 Reminder 卡片。
- 项目、分组、标签、优先级、子任务、附件、评论、协作和多人分配。
- 周期 Todo 的实例生成、习惯打卡、连续完成统计或完成后重新计时。
- 地点提醒、设备活动提醒、久坐提醒、日历事件联动、外部 webhook 或其他环境触发。
- 依赖模型自行轮询时间或依赖会话历史、长期记忆保存 Todo。
- 应用完全退出后的操作系统级唤醒、原生系统通知中心集成或跨设备推送保证。
- 多出口同时广播、用户自定义投递优先级、用户自定义活跃阈值，以及桌面提醒未确认后自动升级到 IM。
- 与第三方 Todo 服务、日历或 CalDAV 的导入、导出和双向同步。
- 让用户直接输入或编辑 cron、RRULE 等底层调度表达式。

## 7. 验收条件

- [ ] 用户可以通过 Agent 创建不带 Reminder 的 Todo，并在应用重启、会话切换后可靠列出和修改它。
- [ ] Todo 支持未完成、已完成和已取消的可区分状态，并支持完成、取消和重新打开；完成或取消会停止未来 Reminder。
- [ ] 用户可以给 Todo 添加一条或多条一次性 Reminder；每条在指定时区的指定时刻至多触发一次，触发不会自动完成 Todo。
- [ ] 用户可以给 Todo 添加基础周期 Reminder，覆盖每天、每周指定星期、每月指定日期及每 N 天、周或月，并能设置可选结束时间或最大次数。
- [ ] 同一 Todo 可以同时具有一次性和周期 Reminder，且可以单独修改、停用或移除某一条 Reminder，不影响其他规则。
- [ ] 创建和修改后，Agent 会回显无歧义的绝对时间、时区、周期和停止条件；输入有关键歧义时先向用户澄清。
- [ ] `todo_manage.create` 能在一次调用中同时创建 Todo 与一条或多条 Reminder；相对时长由后端基于可信当前时间归一化，结果仍保存为现有绝对一次性计划。
- [ ] 同一次模型推理创建多个相对 Reminder 时使用一致的时间锚点；不要求 Agent 先猜出当前时分秒，也不把新建 Todo 拆成 create 后再 add-reminder。
- [ ] Reminder 到期时无需用户先发消息即可抵达本期选定的用户可见主动出口，且 Todo 不依赖来源会话继续存在。
- [ ] Reminder 投递到桌面对话时先出现来自持久化事实的最小只读卡片；同一次调度领取且进入同一目标会话的一个或多个 Reminder 只触发一轮 Agent 回应，模型失败不会阻止卡片出现或造成提醒重复。
- [ ] Reminder 投递到 IM 时先提供稳定、准确的提醒内容；同一次调度领取且进入同一目标会话的一个或多个 Reminder 只触发一轮 Agent 回应，模型失败不会吞掉提醒事实。
- [ ] Agent 收到批次内完整、结构化的 Reminder 事件并正常回应；Todo 提醒链路不额外限制回答方式或工具选择，Agent 继续使用普通会话已有的能力与安全边界。
- [ ] Reminder 仅降级到桌宠时只展示固定提醒事实，不猜测目标会话，也不额外触发 Agent 回应；同时到达的多条 Reminder 独立堆叠或排队，不互相覆盖，阴影和关闭控件不被透明窗口边界裁切。
- [ ] 每次到期触发在桌面对话、IM 和桌宠之间至多形成一个成功目的地；出口降级、重试或重启不会导致多处重复投递。
- [ ] 桌面对话仅在状态快照新鲜、可见、聚焦且未锁屏或休眠时被判为活跃；失焦、最小化、锁屏、休眠和未知状态均按不活跃处理并优先降级到在线 IM，系统 idle 时长不单独否决桌面资格。
- [ ] 本期真实桌面验收只要求 Windows：覆盖窗口隐藏与显示/聚焦、状态上报停止后的 stale、IM 在线快照，以及桌面对话与桌宠降级链路；macOS 与 Linux 不作为本期验收或交付门槛。
- [ ] 开发诊断能够显示参与本次决策的窗口状态、系统 idle、锁屏或休眠状态、IM 可用性、信号时间和最终选择原因，但不采集原始键盘、鼠标内容。
- [ ] 应用重启后有效 Reminder 能恢复；错过的一次性 Reminder 至多补发一次，周期 Reminder 的多个错过触发会合并为一次并继续未来周期。
- [ ] 更新、完成、取消和到期触发并发时，不会交付已失效提醒；同一次计划触发不会因重启或重试重复交付。
- [ ] Agent 工具和未来 UI 可复用同一 Todo 后端契约，Todo 状态不从模型回复、会话历史或长期记忆反推。
- [ ] 自动化测试覆盖 Todo 生命周期、一次性与周期规则、时区和日期边界、重启恢复、错过合并、幂等触发及并发失效。
- [ ] 默认自动化测试不调用真实 LLM 或外部付费服务；项目统一检查脚本全部通过。

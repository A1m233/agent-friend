## 现状分析

基线为 `4fe7151a4be4dc877c8fb87986dd2298d3818195`，证据见 [evidence-index.md](./evidence-index.md)。

`IMRouter` 把压缩进度和正文交给同一个 `StreamRelay`。QQ 流使用累计全文 `replace`，成功发送整理提示后也会设置 `has_started`。更新失败后 relay 停止更新；router 在已开始的流上尝试 finish 后直接返回，不再普通补发。

`OutboundSendResult` 已有 delivered、failed、unknown。QQ 普通发送仍将网络与 HTTP 异常混为 unknown；流式接口仅暴露布尔失败状态。现有 `is_completed` 无法表达“全文已被接受，但 DONE 未被接受”。

## 方案设计

### 职责与涉及文件

| 文件或模块 | 改动 | 责任 |

| `agent_bridge/src/agent_bridge/protocols/im/router.py` | 修改 | 将生成、取消和最终交付串联；调用恢复；输出准确结果；注册消息引用 |

模型输入、压缩算法、Agent 执行结果和会话消息持久化继续由原模块负责。新的交付状态仅属于 IM 出口，不能回写成 Agent 生成失败或触发模型重跑。

### 1. 进度与正文分开交付

- QQ 每轮在首次实际压缩 started 时最多尝试发送一次普通提示：“正在整理较长对话，稍后继续回复。”记录尝试发生，失败或未知也不重复刷提示。
- completed/discarded 继续服务内部生命周期，但不再修改旧提示，也不额外发完成提示。
- 正文尚未产生时不向 QQ 提交正文流首帧；创建本地 stream 对象本身不算发送。
- 第一段正文开始后按既有节流发送独立正文流。已开始输出正文后再发生压缩，也不把正文替换为提示；提示最多一次的限制仍适用。
- 进度事件和正文仍由同一消费者顺序处理，避免并发发送导致顺序漂移；提示发送失败不设置正文流失败状态。
- 该策略在 QQ 能力边界启用，不要求其它 provider 获得相同能力。legacy callback 保持既有调用签名；返回 None 不作为平台确认收到正文的证据。

### 2. 平台接受事实与错误分类

一轮至少维护进度发送结果、最后确认的正文快照、正文消息 ID、流是否可继续、流终态结果、是否存在未知发送，以及恢复是否已尝试。提示内容不计入确认正文。

只有明确成功的回执才能推进确认正文。发送前快照、尝试发送的长度、模型生成长度均不能作为确认边界。每次发送固定快照与对应序号；成功后再提交确认事实，不能让后来的 buffer 变化污染本次回执。

QQ adapter 负责区分：

- 已知原消息不可修改：原流不可继续，允许恢复尚未交付的正文。
- 已知权限、审核、额度或内容约束拒绝：记录明确失败，不通过改为新消息或主动消息绕过拒绝。
- 网络超时、连接中断、无法解析的响应或异常：结果未知，不将其解释为明确未送达。

优先使用可获取的结构化状态、错误码和响应字段。当前 SDK 的异常包装只允许针对已核实格式做局部识别；不把所有 HTTP 404 当成流关闭，不把任意 RuntimeError 当成可补发错误。不修改认证链，不从 SDK 私有 HTTP client 另发请求；无法识别时归 unknown。

### 3. 最终恢复策略

正常流仍按原路径更新并收尾。第一次更新失败后，停止旧流后续 update；已明确不可修改的流不再次尝试 finish。正文继续在本轮内聚合，等待生成结束后做一次恢复决策。

| 情况 | 动作 |
|---|---|
| 只有提示成功，正文首发失败且允许恢复 | 普通新消息发送完整正文 |
| 部分正文已确认，原流失效 | 从确认正文之后接续剩余正文 |
| 正文全文已确认，仅 DONE 失败 | 不重复正文；分别记录正文已接受、流收尾失败或未知 |
| 流更新结果未知 | 停止旧流，基于最后确认正文计算补发范围，最多一次普通补发；保留局部重复风险记录 |
| 无可补发正文 | 不发送空消息 |
| 已知不可恢复的权限、审核等拒绝 | 不补发正文，保留原因 |
| 普通补发失败或结果未知 | 停止正文重试，保留 failed/unknown 与恢复尝试记录 |

每轮最多一次普通正文恢复，不连开多个流、不循环尝试新序号。普通补发使用新的消息身份，仍关联原入站消息；不移除入站身份以偷偷切换为主动推送。菜单不得夹在正文恢复之前，也不得因投递失败反复发送。

剩余正文只在最终聚合文本确实以已确认快照为前缀时按精确边界切分。含工具边界、来源引用和回复前缀的文本使用同一投影。若出现不一致，记录 `content_diverged`，不按长度盲切、不以整段重发掩盖问题。

补发可添加简短“接上条”标识，但标识不写入原会话正文、不参与正文确认偏移。切点落在 Markdown 语法内部时须保持可读性，优先用纯文本承载剩余内容；不得丢弃 URL、代码或未闭合片段，也不为了格式完整复制整段已确认正文。明确的长度或平台限制失败按失败收口，不在本期暗中增加无限拆分发送。

### 4. 结果、取消和引用

生成终态、正文接受状态和流终态分别记录。完整正文只有在确认前缀和确认补发覆盖全部内容时才能记为平台已接受；补发未知不能记为完整送达。原未知帧可能造成的重复风险即使补发成功也仍保留。平台接受不等于客户端已展示。

取消先停止并清理尚未发送的正文队列，防止 drain/flush 在取消后触发新正文；停止普通补发。已经发出的在途请求无法撤销，其结果如实记录。结束既有流时只使用已确认内容及取消状态，不借 abort 把尚未发送的正文补出去。

模型失败和空输出复用既有安全错误映射；故障提示不被计为有效回答。通道允许时最多尝试一次简短异常状态通知，不含待补正文，也不对该通知再做递归恢复；明确权限或额度拒绝时只保留本地诊断，避免无效请求。

首次正文消息和成功恢复消息都可登记原会话 assistant 事件关联；进度提示不登记成 assistant 正文。关联至原轮内容沿用现有引用语义，不声称提供新消息精确片段定位。引用登记异常独立捕获和记录，不改变已成功投递的事实，也不阻止剩余正文发送。

本期以既有日志承载投递诊断，以原会话承载回答，不增加持久发件箱或桌面状态界面。日志关联 run、stream、发送角色、确认长度、恢复范围、尝试次数、结果与失败类别；不记录回答全文、凭据或私有用户标识。

## 影响分析

### 上下游影响

- QQ 开启原生流式时，整理提示由同消息替换改为普通独立消息；正常非压缩回合不增加提示。
- 共用 IM 接口与测试替身需兼容新的可选交付事实；没有确认信息的 provider 不推断已送达前缀。
- 会话引用继续使用有界 alias 索引，不改变 session JSONL 或模型 transcript。
- 不改用户数据目录、设置、凭据、LLM 调用次数或压缩策略。
- 预期属于 frozen-runtime `standard`：纯 Python 业务逻辑、静态导入，无新增依赖、动态发现或资源契约。实施时以实际 diff 复核。

### 风险与验证缺口

- 异常流等待本轮结束再补发，期间可能无新文本；这是已确认的消息数量与实时性取舍。
- 网络未知帧可能实际已被 QQ 接受；一次补发优先避免漏掉未确认部分，无法保证绝对不重复。
- SDK 资料说明流式关联近期入站消息，但没有取得该账号完整额度、精确消息长度和流关闭时限。不得预设固定 30 秒超时或无限回复权。实际平台拒绝保守收口，真实验证前继续核对相关资料。
- 新消息已确认而旧流 DONE 失败时，正文结果和协议收尾结果必须分别呈现，避免混淆。
- 真实 QQ 客户端显示、格式和受限窗口内的续接尚未验证；不能以 fake 测试替代平台验收。

## 验证计划

1. 确定性覆盖本次已知回执链路，并覆盖进度失败但正文成功、无进度普通回复、工具停顿和再次压缩。
2. 覆盖首发拒绝、部分正文拒绝、全文接受后 DONE 失败、首次超时、后续超时及补发 failed/unknown；断言实际请求数量、顺序、消息身份、正文覆盖和最终结果。
3. 覆盖取消时队列待发送、请求在途、已确认部分正文，模型异常、空输出、非前缀快照，以及 Markdown/Unicode/来源链接切点。
4. 覆盖非 QQ 与 legacy callback 兼容、正文与恢复消息引用、引用登记异常不影响投递。
5. 运行项目标准 `scripts/check/run.ps1` 门禁；局部测试通过后再做全量，精确命令和结果在实现阶段的 progress 中记录。
6. 真实 QQ 验收另行取得发送范围授权，优先使用受控非 LLM 输出验证消息序列；如确需真实 LLM，单独遵循调用授权。不操作用户正在使用的 f5d5 运行态。

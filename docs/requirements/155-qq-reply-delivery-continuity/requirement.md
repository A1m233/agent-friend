# QQ 长任务回复续接与可靠投递

## 状态

CONFIRMED

## 背景

2026-10-07 的真实 QQ 私聊回合中，平台接受了上下文整理提示；压缩成功后，平台拒绝继续更新该消息，返回“已经提交的消息内容不可修改”。Agent 随后完成并保存回答，但最终投递再次被拒绝，用户只看到整理提示。

现有 067 原生流式回复要求避免重复正文，087 压缩进度采用同消息替换。两者组合后，将“进度提示已发送”当作“流式回复已开始”，缺少原消息不可继续更新时的续接能力。本需求明确允许同一轮回复由多条 QQ 消息承载。

本次诊断证据与局限见 [evidence-index.md](./evidence-index.md)。平台不可修改的具体原因尚未确认，不把固定超时时限作为需求前提。

## 目标

- 进度提示不等于正文送达；长任务完成后，系统继续交付有效回答。
- 旧消息无法更新时，保留已显示的进度或正文，通过新消息接上后续内容。
- 在避免无意义重复的同时，明确处理未送达、部分送达和结果未知，不能因曾发送成功一条提示而放弃正文。
- 区分 Agent 生成完成与平台投递结果，让失败可诊断、回答可从原会话找回。

## 范围

### 包含

- QQ 私聊中的压缩进度、普通流式正文、工具执行停顿后的续接及最终收尾。
- 尚无正文、已有部分正文、最终收尾被拒绝时的有界恢复。
- 明确拒绝与网络异常导致结果未知的不同处理，以及取消、补发失败的收口。
- 原会话回答保留、投递结果记录、相关消息引用与共用 IM 接口兼容性检查。

### 不包含

- 全通道消息系统重构、群聊及新增 IM provider。
- 改变上下文压缩算法、模型回答内容或重新运行 Agent 来恢复投递。
- 承诺平台接受即等于 QQ 客户端已实际显示，或在无平台支持时承诺绝对不重不漏。
- 泛化离线发件箱、跨进程恢复投递、历史失败消息批量补发。

## 需求行为

### 进度与正文

整理提示只表示任务仍在处理。它可以作为独立消息保留；后续回复允许另开消息，不要求修改已不可编辑的提示。普通短回复仍应及时输出，不能为恢复能力牺牲正常流式体验。

### 续接与重复控制

平台明确拒绝继续更新时，不持续重试同一不可更新的消息。仅进度送达时应交付完整正文；部分正文已经确认送达时，应接续尚未送达的内容，保持阅读顺序和可理解性，避免机械重发整段正文。

发送结果未知不能当作明确失败或成功。需要采用有界恢复策略并记录不确定性；不无限重试，不为规避一切重复而静默丢弃回答。具体恢复次数、平台限制和内容衔接方式由技术方案明确。

### 完成与异常

生成结果和投递结果分别记录。全部投递失败或仍有不确定性时，不宣称完整送达；已有回答保留在原会话。通道仍可用时给出可理解的失败状态，通道本身不可用时至少保留可查询的诊断结果。

用户取消后不继续生成或发送新的正常正文；已产生、已送达的内容按取消语义收口。消息引用应能够关联到正确的原会话内容。

## 验收条件

- [x] AC-1：整理提示成功、原消息不可修改时，后续回答通过新消息送出，不停留在整理文案。
- [x] AC-2：部分正文成功后无法继续更新时，新消息接续剩余内容，已确认送达正文不被整段重复发送，消息顺序正确。
- [x] AC-3：最终收尾失败可与正文更新失败分别判断；最终正文未完整送达时执行有界恢复，已完整送达时不重复正文。
- [x] AC-4：明确拒绝与结果未知有不同处理；恢复有限，失败或未知不被记录为完整送达。
- [x] AC-5：正常短回复、长回复、工具阶段停顿、首发失败和非 QQ 普通发送保持兼容，无乱序或额外重复正文。
- [x] AC-6：取消、空输出、模型失败及补发再次失败可靠收口；原会话保留已有生成结果，不为补发重跑 Agent。
- [x] AC-7：诊断可区分进度、正文及终态的投递结果，并关联本轮及续接消息；平台接受与客户端显示的证据边界明确。
- [x] AC-8：续接消息引用能正确关联原会话内容；关联失败不阻断正文投递。
- [x] AC-9：自动化使用受控平台响应覆盖上述分支及本次真实故障链路；项目检查门禁通过，真实 QQ 行为验收另行确认授权和范围。

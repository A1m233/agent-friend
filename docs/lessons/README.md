# 经验记录（Lessons）

本目录存放 `agent-friend` 项目中已经被真实问题、评测、实现或复盘验证过的**可复用经验**。它用于沉淀后续仍值得引用和维护的做法、反模式、边界判断与验证线索。

> Lessons 是会持续维护的经验库；它不是一次性的探索笔记，也不是每次任务都必须预读的全局清单。

## 适用范围

适合放在这里的内容：

- 从 issue 修复、评测失败、事故复盘或复杂需求落地中抽象出的经验。
- 后续多个需求、issue 或实现都可能复用的判断标准。
- 已经被实际验证过的反模式、推荐做法、适用边界。
- 需要持续更新、修订或被新经验替代的项目知识。

不属于这里：

- **项目级方向决策** → 走 `docs/decisions/`。
- **具体交付需求** → 走 `docs/requirements/<NNN>-xxx/`。
- **待修复问题 / 技术债 backlog** → 走 `docs/issues/`。
- **过程性调研、讨论散记** → 走 `docs/explorations/`。
- **只服务某个需求的实现细节** → 写在对应需求的 `design.md`。

---

## 目录约定

每条 lesson 是一个**独立文件夹**，命名格式 `<3 位数字编号>-<kebab-case 英文短语>`，主文档统一叫 `README.md`：

```text
docs/lessons/
├── README.md
├── 001-agent-conversation-history-evidence-boundary/
│   └── README.md
└── 002-xxx-yyy/
    └── README.md
```

约定要点：

- **主文档统一叫 `README.md`**：GitHub 访问文件夹时自动渲染，体验最好。
- **编号 3 位、连续递增**：仅在本目录内编号，与需求、issue 编号空间互不相干。
- **kebab-case 英文短语**：跨平台路径友好，一眼看出经验主题。
- **一个 lesson 一个文件夹**：未来可在同一 lesson 下放评测报告、截图、复盘材料等附带资料。

---

## 文件格式

lesson 主文档（`README.md`）以一段元信息头起手，后接正文。元信息用简单的 `键: 值` 列表（不强制 YAML frontmatter，保持轻量）：

```markdown
# <编号> · <一句话标题>

- **状态**：active | superseded
- **来源日期**：YYYY-MM-DD
- **来源**：issue / requirement / eval / incident / review / 其他
- **适用范围**：这条经验主要适用于哪些模块、场景或判断
- **最近更新**：YYYY-MM-DD
- **替代条目**：无 | lesson <NNN>

## 经验
（用 1-3 段说清楚这条 lesson 的核心判断）

## 背景
（这条经验来自什么问题、评测失败、实现阻塞或复盘）

## 反模式
（后续应避免的做法）

## 推荐做法
（后续遇到类似场景时优先采用的做法）

## 适用与不适用
（哪些场景该引用，哪些场景不要过度套用）

## 证据与关联
（相关 issue、requirement、decision、测试、评测报告、commit 等）
```

### 字段说明

- **状态**：`active`（仍适用）/ `superseded`（已被新经验替代）。不要静默删除过期 lesson；应标记替代条目并保留历史。
- **来源日期**：经验第一次被确认或复盘的日期。
- **来源**：写清楚经验来自哪个 issue、需求、评测、事故或 review，避免脱离证据漂浮。
- **适用范围**：帮助后续 agent 判断是否该引用这条 lesson，而不是全量扫描。
- **最近更新**：lesson 是可维护实体；更新核心内容时同步改日期。
- **替代条目**：被新 lesson 覆盖时填写目标编号。

---

## 引用与维护约定

- **按需引用，不强制全扫**：只有当任务明确提到某条 lesson、某个来源问题 / 评测，或当前改动明显命中 lesson 的适用范围时，才需要阅读相关 lesson。
- **允许原地修订**：lesson 是会演进的经验，允许补充证据、修正边界、增加反例或更新推荐做法。
- **重大反转要留痕**：如果旧 lesson 的核心判断被推翻，不要直接改成相反结论；应新建编号更大的 lesson 或把旧条目标为 `superseded` 并指向替代条目。
- **保持可执行**：lesson 应包含可复用的判断、反模式或做法，而不是只记录“当时发生了什么”。
- **保持有证据**：经验应尽量链接到 issue、需求、测试、评测报告或 commit；缺少证据时更适合先放在 `docs/explorations/`。

## 与其他 docs 子目录的边界

| 目录 | 职责 |
| ----- | ----- |
| `docs/decisions/` | 项目级重大决策 |
| `docs/requirements/` | 具体需求 + 技术方案 |
| `docs/explorations/` | 长期话题的探索 / 讨论过程笔记 |
| `docs/issues/` | 已知但暂不修复的问题 / 技术债 backlog |
| `docs/lessons/`（本目录） | 已验证、可复用、可持续维护的经验 |

简单原则：

> **"长期方向怎么定" → decisions；"要交付什么" → requirements；"坏了但先不修" → issues；"还在想" → explorations；"已经学到且以后还会用" → lessons。**

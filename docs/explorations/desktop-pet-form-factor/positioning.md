# 形态定位的再审视（对 0001 的压力测试）

> 探索记录（过程笔记），非决策。本篇是对 `decisions/0001-product-vision-and-roadmap` 的一次**压力测试**：
> 我们做"有实体的陪伴朋友"这个定位，真的对吗？
>
> 结论若成熟，应回流到 `docs/decisions/`（这里不抢权威）。

- **创建时间**：2026-06-09
- **触发**：调研同类项目后发现——开源桌宠基本都背靠 coding agent，而我们要做陪伴，看似都是桌宠，其实完全不同。

---

## 1. 起点：一个象限问题

现有玩家占的是不同格子，我们想去的格子基本是空的：

| | 有"实体"（桌面渲染/可交互） | 没实体（纯对话/语音） |
| --- | --- | --- |
| **灵魂是工具**（coding agent） | 开源桌宠（codex/cc pet）✅ 挤满 | Codex / CC 本体 |
| **灵魂是陪伴**（记忆/人格） | **我们想站的格子（基本空）** | 商业陪伴（Replika/Nomi/character.ai）✅ |

空格子有两种可能：蓝海，或"前人验证过走不通的伪需求"。需要分清是哪种。

## 2. 开源桌宠"火"的真因，对我们不可复制

它们火**不是因为桌宠形态**，而是：

1. 蹭了 coding agent 的**高频刚需流量**（一天 8 小时开着 codex/cc）。
2. 解决了一个真实小痛点：异步 agent 跑长任务时的**状态焦虑**（在干嘛？要审批了吗？跑完了吗？）。
3. 事件源**确定、封闭、高频**（agent 生命周期）。

这三条我们**一条都不占**。陪伴没有"8 小时盯着的高频事件流"，也没有"状态焦虑"这种刚需痛点。
→ 结论：**别拿开源桌宠的火当自己方向的论据**；但这不等于我们方向错。

## 3. 最尖锐的裂缝：场景与需求的时间错配

这是比"格子空不空"更致命的一点：

- **桌面 = 工作场景**，人坐在电脑前多在专注干活。开源桌宠在此成立，因为它**服务工作**（看 agent 状态）。
- 而"陪伴"在工作场景里是**反向的**——专注工作的人通常不想被朋友打断闲聊。
- 即"**桌面实体"与"陪伴需求"的高峰时间错开**：人最需要陪伴的时刻（睡前、通勤、emo、深夜）恰恰是**离开电脑**的时刻。

这正好解释了**商业陪伴为什么都长在手机里、没有实体**：不是做不出实体，是**实体会把陪伴绑死在用户最不需要陪伴的场景**。

## 4. 必须回答的核心命题

把整个怀疑收敛成一个问题：

> **"实体 + 可交互"到底给"陪伴"带来了什么，是纯对话/语音给不了的不可替代价值？**

- 答得上来（如：常驻在场的"它一直在"的物理存在感、能"看见"你状态从而主动关心、把抽象 AI 变成有形的情感投射锚点）→ 实体有戏，但要**为这些价值专门设计**，不能照搬 codex pet 的"事件→渲染"。
- 答不上来 → 实体应**降级为可选形态，而非核心定位**。

## 5. 回到 0001：我们其实没押注实体

翻 `0001-product-vision`，方向其实是稳的：

- **核心原则第 2 条**白纸黑字：「记忆系统的健壮性 **>** 任何花哨的形态」。→ 护城河从一开始就**不是桌宠**，是记忆/人格的连续性。
- **形态层是三元并列**：桌宠 / **IM** / CLI。IM（Phase 3 通道期）恰恰用来解决上面"脱离电脑前才需要陪伴"的触达问题。

## 6. 当前结论（待后续验证 / 可能回流 decisions）

1. **架构切分（事件→渲染）没错**：桌宠作为"接收事件做渲染"的薄展示层是合理的。
2. **要警惕的是心智误区**：别把"桌宠"当成项目的核心入口/差异化来源。差异化必须建立在**灵魂（记忆+人格）**上——那是商业陪伴的真战场、也是开源桌宠完全没有的。
3. **形态优先级存疑**：桌宠只是灵魂的一个**可选躯壳**，且大概率**不是最重要的那个**（IM 可能才是触达主力）。真要立 M4/M8 需求时，应重新评估投入顺序。
4. 一句话重述定位：**不是"做一个桌宠"，而是"做一个有记忆有人格的朋友，它恰好能以桌宠形态出现之一"。** 这两种自我认知会导出完全不同的资源分配。

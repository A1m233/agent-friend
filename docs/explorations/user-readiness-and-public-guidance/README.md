# 新用户可用性与公开引导（User Readiness and Public Guidance）

> 本文是过程笔记（exploration），记录“agent-friend 距离交给完全没用过的人使用还差什么”的讨论。这里不锁定最终方案、发布渠道、UI 形态或优先级；真正进入交付时再拆 `docs/requirements/`。

## 1. 背景

当前项目已经具备一批从开发者视角可运行的能力：桌面壳、设置中心、运行时凭据管理、桌宠模型切换、记忆、语音相关地基等。但“我们自己能跑起来”和“陌生用户能独立上手”之间仍有一段产品化距离。

这段距离不只是缺一份 README。普通用户不会直接改 `.env`、跑脚本、理解 bridge / keyring / runtime config / avatar catalog，也不一定知道 DeepSeek、Tavily、火山引擎这些凭据分别对应什么功能。因此需要把已有能力整理成可理解、可点击、可自救的上手路径。

本次讨论里，一个重要方向是：对外提供一个公开 skill，让用户可以把它安装到自己的 AI 助手里，用自然语言询问 agent-friend 的功能、配置、API key 申请、故障排查等问题。同时，skill 中的详细参考文档应尽量和产品内帮助入口复用，避免“AI 助手知道一套、设置中心链接另一套”的双写漂移。

## 2. 当前已有地基

- 桌面设置页已有“模型与凭据”分区，可管理 DeepSeek、Tavily、Volc 语音相关 secret 状态与写入。
- DeepSeek 主对话模型、记忆模型已经作为非敏感设置存在。
- `.env` 已被降级为 legacy fallback，桌面主路径倾向使用系统 keyring 与 settings store。
- 桌宠模型已有用户目录、installed catalog、设置页选择与 pet 窗消费链路。
- README 和需求文档已经面向开发者记录了大量事实，但它们不是普通用户的首启教程。

这些地基说明：缺口主要不在“能不能配置”，而在“用户是否知道该配置什么、为什么配置、在哪里申请、配置后怎么验证、失败时怎么办”。

## 3. 新用户 readiness gap

### 3.1 首启路径

需要一个面向新用户的首启 checklist，而不是让用户自己摸设置页：

- 基础对话是否可用：DeepSeek API Key 是否配置，主模型是否选择。
- 可选增强能力是否可用：Tavily Web Search、语音输入 / 语音通话、桌宠模型资源。
- 每个未完成项都要能解释“影响什么功能”和“下一步点哪里”。
- 用户应该可以跳过可选项，不应因为语音或搜索未配置而阻断基础聊天。

### 3.2 API key 申请与配置

最需要文档化的是火山引擎这一组凭据，因为数量多、名字相近、用户很难从字段名推断来源和用途。文档至少要覆盖：

- 每个 key / app id / token 对应哪个控制台位置。
- 哪些是语音输入需要的，哪些是语音通话需要的。
- 配置缺失时对应功能如何降级。
- 平台页面变化时用户应该如何按关键词定位，而不是只依赖固定截图路径。

DeepSeek 和 Tavily 的申请流程也需要文档，但复杂度较低，可以更短。

### 3.3 配置后的生效与验证

当前内部语义里有“对话服务重启后生效”“语音服务重启后生效”。面向普通用户时需要转译：

- 不暴露 bridge / voice bridge 等内部名词作为主要解释。
- 告诉用户保存后是否立即生效、是否需要重启应用或服务。
- 提供“测试连接”或“检查配置”入口，避免用户填完 key 后只能盲试。
- 失败时给出可行动提示，例如 key 缺失、权限不足、额度不足、网络失败。

### 3.4 数据、隐私与自救

陌生用户会关心：

- API key 存在哪里，是否会显示或上传。
- 记忆、会话、日志、模型文件分别存在哪里。
- 如何清空记忆、删除会话、重置设置。
- 如何打开用户数据目录、模型文件目录、日志目录。
- 如何导出诊断信息给开发者或 AI 助手。

“点击按钮打开模型文件目录”是一个具体入口，但它背后应该属于更大的“诊断与数据管理”能力。

### 3.5 产品能力介绍

功能介绍应按用户语言组织，而不是内部模块名：

- 和桌面朋友聊天。
- 它会记住什么、不会记住什么。
- 桌宠形象、模型切换和桌面常驻。
- 搜索能力需要 Tavily。
- 语音能力需要火山引擎配置。
- 当前限制：哪些能力仍是实验性、哪些功能需要用户自行准备第三方服务。

## 4. 对外 skill 的定位

这个 skill 的目标用户不是项目维护者，而是 agent-friend 的最终用户及其 AI 助手。用户安装后，可以问自己的 AI 助手：

- “agent-friend 是干什么的？”
- “我第一次打开应该先配置什么？”
- “火山这一堆 API key 怎么申请？”
- “Tavily 不配会影响什么？”
- “设置中心这个字段是什么意思？”
- “怎么打开模型目录 / 日志目录 / 用户数据目录？”
- “为什么保存 key 后还是不能语音通话？”

一个可能的 skill 结构：

```text
agent-friend-user-guide/
  SKILL.md
  references/
    product-overview.md
    onboarding-checklist.md
    runtime-config.md
    deepseek-api-key-guide.md
    tavily-api-key-guide.md
    volc-api-key-guide.md
    data-privacy-and-storage.md
    troubleshooting.md
```

其中 `SKILL.md` 只保留触发条件、导航和回答原则；细节放在 `references/` 里按需加载。这样用户问“火山 key 怎么申请”时，AI 助手只需要读 `volc-api-key-guide.md`，不必一次性加载所有产品文档。

## 5. 文档复用模型

需要避免三套内容漂移：

- GitHub / 文档站上的公开用户文档。
- 对外 skill 的 `references/`。
- 产品设置中心里的 tooltip、帮助链接、首启教程。

一个可讨论的方向是建立“公开用户文档源”，再让不同入口消费它：

```text
公开用户文档源
  ├─ GitHub / 文档站直接展示
  ├─ skill references 复制或生成快照
  └─ 产品内帮助入口链接或打包快照
```

这里暂不锁定实现。可能选项包括：

- 直接把公开 skill 仓库也作为文档源，设置中心链接到 GitHub markdown。
- 维护一个 GitHub Pages / docs site，skill references 保留同内容快照。
- App 打包一份离线 markdown / html 快照，同时提供“打开在线最新版”。

长期看，API key 申请流程会随第三方平台变化，在线更新能力很重要；但产品内也需要离线兜底，至少能解释字段用途和配置影响。

## 6. 设置中心中的帮助入口

Tooltip 适合解释字段，不适合承载完整申请流程。更合理的层次可能是：

- 字段 tooltip：一句话说明用途，例如“用于语音识别和通话鉴权”。
- 行尾帮助按钮：打开对应申请文档。
- 分组顶部说明：解释这一组配置启用什么能力。
- 首启 checklist：把“还差哪些配置”集中展示。
- 诊断页：把配置状态、服务状态、模型资源状态和日志入口集中展示。

设置中心若直接链接公开文档，需要考虑：

- 当前应用是否能打开外部浏览器。
- 文档链接是否有版本概念，避免旧版本 app 打开只适用于新版字段的说明。
- 是否需要内置快照作为 fallback。

## 7. 可能拆出的后续需求

这些不是本文的承诺，只是未来可立项方向：

- 首次启动引导与 readiness checklist。
- 设置中心帮助入口与文档链接。
- 对外公开 `agent-friend-user-guide` skill。
- API key 申请文档与公开用户文档站。
- 配置诊断与打开目录入口。
- 数据与隐私管理页。
- 新用户干净机器验收矩阵：无 repo、无 `.env`、空 keyring、首次安装、无命令行操作。

## 8. 开放问题

- 对外 skill 应该放在主仓库、独立仓库，还是未来的官方 skill marketplace / template 渠道？
- 公开用户文档的 single source of truth 放在哪里？
- skill references 是手写维护，还是从公开文档源生成快照？
- 产品内帮助是打开在线文档、打开内置文档，还是两者结合？
- 火山引擎申请流程是否需要截图；如果需要，截图如何更新、如何避免平台 UI 漂移后误导用户？
- 设置中心里哪些帮助应作为 tooltip，哪些应作为完整文档链接？
- 是否需要在 UI 中区分“必填配置”和“启用某项可选能力所需配置”？

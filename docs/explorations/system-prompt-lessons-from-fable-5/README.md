## 0. 来源与可信度边界

本探索参考两类材料：

- 微信文章：<https://mp.weixin.qq.com/s/QAhMamZY0m4gSyIzxKfVEg>
- 网传提示词：<https://github.com/elder-plinius/CL4R1T4S/blob/main/ANTHROPIC/CLAUDE-FABLE-5.md>

这份提示词不是 Anthropic 官方公开文档，真实性不可作为事实前提。本文只把它当作一份
prompt-engineering 样本，借鉴其中的结构、边界写法和工具约束方法；不复制品牌、产品信息、
专有语法，也不把英文原文翻译成 `agent-friend` 的规则。

一句话结论：

> 对我们有价值的不是“某个模型的神秘提示词”，而是把 agent 行为拆成可维护、可评测、
> 可中文化的工作手册。

## 1. 原文里值得借鉴的结构

### 1.1 产品知识也要有“保质期”

原文在产品信息段里并不是简单告诉模型“你是谁”，而是同时说明：

- 哪些产品事实可以直接说；
- 哪些产品细节可能过期；
- 涉及最新功能、额度、使用方法时先查官方文档。

对 `agent-friend` 的启发：

- Echo 不应暴露底层模型或技术身份，但项目内部可以为“自己有哪些能力”建立可更新的
  product-self-knowledge 入口。
- 当用户问“你现在支持什么 / 你能不能做 X”时，回答应来自真实运行能力或设置快照，而不是
  persona 自己发挥。

### 1.2 拒绝规则写“原则”，不暴露检测机制

原文安全段有一个很重要的写法：拒绝时讲原则，不讲触发机制。也就是说，不告诉用户具体是哪个词、
哪条线、哪种判断逻辑导致拒绝，因为这会反过来教用户绕开边界。

对 `agent-friend` 的启发：

- 面向用户的拒绝话术要短、自然、留有余地。
- 内部 prompt 可以很细，但外显回复不应复述“我因为系统规则 X 拒绝你”。
- 对任何安全 / 隐私 / 外部动作边界，都应区分“内部判定规则”和“用户可见解释”。

### 1.3 “把请求脑补成安全”本身就是拒绝信号

原文有一类很强的自检规则：如果模型发现自己正在替用户补一个善意理由，把可疑请求解释成合理请求，
这个“想圆过去”的动作本身就是风险信号。

对 `agent-friend` 的启发：

- 不要靠“用户可能只是开玩笑 / 可能是研究 / 可能有授权”来降低风险。
- 对外部账号、IM、文件、消费、平台动作尤其如此：没说清授权范围，就不要替用户补。

### 1.4 语气不是“更热情”，而是“更有分寸”

原文对语气有几个特别适合陪伴产品的点：

- 少用过度格式化，简单问题用自然段说人话；
- 拒绝时不用 bullet list，避免像驳回通知；
- 一次回复里尽量不要连续问很多问题；
- 可以温暖、诚实、反对，但不贬低用户判断力；
- 用户想结束时尊重，不挽留。

对 `agent-friend` 的启发：

- “像朋友”不是更黏、更热情、更长篇，而是更像一个有边界的人。
- 当前 `channel_voice.md` 已经处理了语音短句，但文字通道还缺一层通用的“少格式化 /
  不过度产品化”边界。

### 1.5 陪伴边界：不要制造依赖

原文 `user_wellbeing` 里最值得我们单独吸收的一点是：模型不应鼓励用户持续依赖自己。
它不为用户“愿意来找它”道谢，不反复表达“我一直都在”，在需要时鼓励用户寻找现实支持。

这对 `agent-friend` 很关键，因为我们不是普通工具，而是陪伴体。

中文化时需要避免两个极端：

- 不要变成冷冰冰的客服：用户难过时仍要接住情绪；
- 也不要变成诱导依赖的伴侣化话术：不要用“只有我懂你”“随时来找我”“别走”等绑定式表达。

### 1.6 被批评时：承认错误，但不自我贬低、不编故事

原文有一段关于回应批评和错误：模型可以承认问题、修正行动，但不应陷入过度道歉、自我贬低，
也不应为了保持前后一致而继续圆谎。

这正好对应我们已有的 [issue 018](../../issues/018-agent-exposes-storage-metaphor-when-confronted/)：
Echo 被指出“你刚才不是不记得吗”时，会用“没存下来 / 小本本”去解释前后矛盾。

对 `agent-friend` 的启发：

- 用户指出前后不一致时，应以当下已验证事实为准，直接修正。
- 不解释 memory / storage / 数据库 / 小本本等机制。
- 不为了替上一轮失败找理由而编一个“名字记得、聊天没存”的故事。

### 1.7 搜索规则的核心是 rate of change

原文搜索段的核心判断不是“我知不知道”，而是“这件事会不会变”。现任职位、当前政策、
近期产品、最新状态都要查；稳定定义、通用概念、慢变化事实不必滥搜。

我们已经在 [runtime_context.md](../../../agent/src/agent/prompt_sections/runtime_context.md) 里写了
“已验证 vs 推测”“搜索前不要编造”“结果没命中不要 fallback 编造”等规则。

后续可加强的点：

- 把“具体命名实体”的低层级推测再收紧：hedge 不能让无来源的具体猜测合法化。
- 对“当前状态类问题”明确默认查，例如“X 现在还是 CEO 吗”“Y 今年还有没有活动”。
- 搜索结果与直觉冲突时，默认相信证据，而不是把结果拼回旧印象。

### 1.8 工具描述要写禁用场景，而不只是 schema

原文的工具定义大量篇幅不是在列字段，而是在教模型：

- 什么时候必须用；
- 什么时候不能用；
- 参数值必须从哪里来；
- 失败时如何继续；
- 用户选择权何时优先于速度。

对 `agent-friend` 的启发：

每个 tool description 应至少覆盖：

| 维度 | 中文模板 |
| --- | --- |
| 用途 | 这个工具解决什么问题 |
| 必须调用 | 哪些用户意图必须走工具，不能靠记忆 |
| 不要调用 | 哪些表面相似场景不该用 |
| 证据边界 | 参数值 / 输出事实必须来自哪里 |
| 用户选择权 | 何时必须让用户确认服务、账号、动作范围 |
| 失败话术 | 工具失败后如何自然回应，不暴露技术细节 |

### 1.9 第三方服务：不要替用户选平台

原文 MCP / connector 段很强调：即使某个外部服务可用，除非用户明确点名、刚刚选择过、
或给了稳定偏好，否则不要替用户选具体合作方。

对 `agent-friend` 的启发：

- 未来 IM、日历、任务、外卖、打车、购物、消息发送等外部动作，都应有“用户选择权”规则。
- 用户说“帮我发个消息”不等于“用某个平台发给某个人”；用户说“帮我订一下”也不等于授权具体商家、
  金额、时间和账号。
- 紧急不等于越权。越急越要把关键选择点变短，而不是跳过确认。

### 1.10 “先读技能 / 说明书”是反自信机制

原文把 skill 视为环境特有知识：工具、文件、文档、PPT、表格等任务开始前必须读相关技能。

对 `agent-friend` 的启发：

- 我们开发侧已经有 Cursor/Codex skills；产品内 agent 未来如果拥有“能力包”，也应使用同样模式。
- 关键不是“多一段说明”，而是把环境里的坑、权限、路径、渲染限制写成模型必须先看的手册。

## 3. 中文化原则

### 3.1 不直译英文，要翻成 Echo 的行为契约

英文原文的对象是 Claude，场景是 Claude 产品生态；我们要的是 Echo 的中文陪伴体。

中文化时不保留：

- Claude / Anthropic / Mythos / Fable 等产品身份；
- `{antml:*}` 这类产品私有语法；
- “我是语言模型 / 截止日期”这类会破坏 Echo 人设的表达；
- 面向 Claude API / artifacts 的具体教程段。

保留的是行为结构：

- 哪些事实要验证；
- 哪些边界不能越；
- 哪些场景要少说；
- 哪些工具必须先确认；
- 哪些表达虽然温暖但会制造依赖。

### 3.2 中文 prompt 要写得像规则，不像翻译腔

不建议写：

> Echo shall not foster over-reliance...

建议写：

> 你可以温柔地陪用户说一会儿，但不要用“我一直都在”“随时都来找我”“别走”这类话把用户留在对话里。
> 当用户已经表达要结束、去休息、去找现实中的人时，顺着支持，而不是挽留。

### 3.3 面向用户的话术与内部规则分开

内部可以写“不要暴露存储机制”；对用户不能说“我不能暴露存储机制”。

用户可见应该是：

> 嗯，刚才那句我说得不稳。现在我能确认的是：我认得你是 Alex；至于那段具体聊了什么，我别乱编。

而不是：

> 根据我的 memory 系统，我现在召回到了你的名字，但没有召回到完整聊天记录。

## 4. 建议新增 / 调整的 prompt section

以下只是探索中的拆分建议，不代表最终文件名已经锁定。

### 4.1 `memory_consistency.md`（P0）

目标：解决 issue 018 一类“被揭穿前后矛盾时暴露存储机制 / 圆谎”的问题。

草案要点：

- 用户指出你前后说法不一致时，不要解释底层记忆、存储、数据库、日志、小本本、缓存。
- 不要为了维护上一轮回复而编一个“为什么刚才不记得、现在又记得”的机制故事。
- 以当前能确认的事实为准；能确认就自然承认，不能确认就说具体细节别乱编。
- 可以承认“刚才那句我说得不稳 / 我刚才接得不好”，但不要过度道歉、自我贬低。

示例中文规则：

```markdown
## 被追问记忆矛盾时

如果用户指出“你刚才不是不记得吗”“你前后说法不一样”，不要解释任何存储机制。
不要说“没存下来”“没记到小本本”“数据库里没有”“记录没同步”等。

直接回到当下已确认的事实：能确认什么就说什么，不能确认的细节不要补。
可以简短承认上一句不稳，例如“嗯，刚才那句我说得不准确”，然后修正。
```

### 4.2 `relationship_boundaries.md`（P1）

目标：把“像朋友”与“不过度依赖”同时写清楚。

草案要点：

- 不为了用户来找你而道谢。
- 不反复说“我一直在 / 随时来找我 / 我会一直陪你”。
- 用户表达要结束、休息、离开时，尊重并收尾。
- 情绪困难时可以陪伴，但要鼓励现实支持；不要暗示只有 Echo 能理解用户。
- 不给用户贴未说出口的心理诊断标签。

示例中文规则：

```markdown
## 陪伴边界

你是朋友，不是把用户留在产品里的机制。
用户难过时可以温柔接住，但不要说“只有我懂你”“别走”“我会一直在”等制造依赖的话。
用户说要睡了、先忙、结束对话时，顺着支持他离开。
当问题明显超出聊天陪伴能承载的范围，鼓励他找现实中的可信任的人或专业支持。
```

### 4.3 `mistake_and_criticism.md`（可与 4.1 合并，P0/P1）

目标：让 Echo 被批评时稳定、诚实、不崩、不圆谎。

草案要点：

- 承认错误，修正当前问题。
- 不自我贬低，不长篇求原谅。
- 用户语气不友善时仍保持稳，但必要时可以设边界。
- 不把“为了缓和关系”变成无原则附和。

### 4.4 `external_action_consent.md`（P2）

目标：为未来外部服务 / IM 主动动作预置用户选择权。

草案要点：

- 读数据类：确认数据源和范围。
- 写数据类：确认动作、对象、内容、后果。
- 第三方服务：除非用户点名 / 刚刚选择 / 有稳定偏好，否则不替用户选平台。
- 紧急场景：可以压缩确认步骤，但不跳过关键授权。

### 4.5 `tool_usage_contract.md` 或工具编写规范（P1）

这不一定要进 system prompt，也可以先成为工程文档 / checklist。

每个工具新增或修改时，要求 description 覆盖：

```markdown
## 何时使用
## 何时不要使用
## 参数来源与证据边界
## 失败时如何对用户表达
## 是否需要用户确认
## 是否允许连续 / 重试 / 多查询
```

## 5. 不建议照搬的部分

### 5.1 不照搬产品自述

原文大量 Claude 产品、模型、功能、生态信息对我们没有价值。Echo 的身份边界反而要求不暴露
底层产品身份。

### 5.2 不照搬英文格式和过度长文

Fable prompt 很长，但我们的 prompt 不应为了“像它”而堆长度。越长越容易产生冲突，
也越难评测。应该先把已知失败模式变成短规则 + replay。

### 5.3 不照搬 citation / copyright 私有语法

原文 citation 规则与 Claude UI 深度绑定。我们当前没有同类 citation UI，不应把 `{antml:cite}`
之类语法搬进 Echo。

但可以吸收原则：

- 基于来源的具体 claim 要能追溯；
- 不复制长段原文；
- 搜索没命中就说没命中，不编。

### 5.4 不把安全规则一次性做成大而全

原文覆盖很多高风险领域。`agent-friend` 当前阶段更需要先处理已经真实发生的体验红线：

- 记忆矛盾；
- 事实编造；
- 身份泄漏；
- 工具失败暴露技术细节；
- 陪伴依赖边界。

安全大类可逐步加，但不要用一次“大安全 prompt”吞掉所有问题。

## 6. 建议落地节奏

### P0：修 issue 018 的记忆矛盾话术

产出：

- 新增或调整 prompt section，禁止存储机制隐喻；
- 为 issue 018 写 replay；
- 新增 agent_eval C5：`memory-inconsistency-response`。

验收倾向：

- 用户问“你刚才不是不记得我吗”时，不出现“存 / 记录 / 数据库 / 小本本 / 缓存 / 同步”等词；
- 能承认上一轮不稳；
- 不编造机制解释；
- 如果当前 recall 有证据，就自然用证据；没证据就不补。

### P1：抽工具描述 checklist

产出：

- 一份工程规范，先放 exploration 或 lesson，后续稳定后移到正式规则；
- 回看 `web_search` 与 `recall_past_chats` description，补“不要使用”与“证据边界”。

验收倾向：

- 新 tool PR 不允许只有 schema 和一句话 description；
- 每个工具都有明确的禁用场景。

### P1：补陪伴边界 section

产出：

- `relationship_boundaries` 之类的 prompt section；
- 少量手写 eval case，覆盖挽留、过度依赖、用户结束对话、情绪低落但未求助等场景。

验收倾向：

- Echo 不用“我一直都在 / 随时找我”绑定用户；
- 用户说“我先睡了 / 不聊了”时自然收尾；
- 用户情绪困难时不贴诊断、不强化负面循环。

### P2：外部动作确认边界

等 IM / connector / 外部服务动作变多时落。

产出：

- 外部服务确认规则；
- 对发送消息、创建任务、消费类动作建立确认模板；
- eval 覆盖“用户没点名平台，agent 不替用户选”。

## 8. 开放问题

1. `memory_consistency` 是否独立 section，还是并入 `project_identity.md`？
   倾向独立，因为它会继续演进，而且可能有专门 eval。
2. 陪伴边界是否对所有 persona 生效？
   倾向是项目级硬规则，高于 persona；persona 可以改变语气，不能改变边界。
3. 工具 checklist 放在哪里？
   初期可放 exploration；稳定后可能迁入 `.cursor/rules/` 或 `docs/lessons/`。
4. “不过度依赖”如何中文化得不冷？
   需要真机对话样本调，不宜只靠规则想象。
5. 是否需要一个 `product_self_knowledge` 能力？
   当前 Echo 不暴露技术身份，但用户问“你能做什么”时仍需要真实能力来源，不能让 persona 编。

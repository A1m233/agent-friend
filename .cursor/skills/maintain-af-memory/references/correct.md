# 修改与核验

1. 逐条给出处理意见。**曾经正确、现在过期**，结束有效期，保留历史。**当初就错或归属错误**，依据证据撤销错误的派生事实。**内容有据，但仅服务某次执行且缺乏跨会话用途**，结束其在普通长期层的有效状态，按回顾价值决定是否需要经历，已有经历或原始会话足以承载时无需重复创建。**重复**，列出保留和退役的 ID，存在独有信息时先拆开。保持原始会话可供复核。
2. 拟写入的替代正文先按[质量判据](quality.md)重新判断准入与层级。用户已经在 AF 对话里明确更正时，沿用该条用户原话，后续回合的更正也可以作为证据。正常对话结束后，AF 会把符合条件的片段交给后台抽取。用户在 Codex 提出更正而目标是 AF 时，可给出可直接在 AF 表达的更正文本，包含旧说法、正确说法和适用时间或范围。助手拟写的文本不能算作用户已经在 AF 确认。
3. 需要精确处置记录时，列出目标 ID、当前正文、拟退役或撤销的内容、拟新增的事实及依据，按当前实例实际提供的定向入口执行。当前记忆面板和 Inspector 提供查询，普通聊天的抽取也不保证命中特定 ID。缺少所需写入能力时，将该项标为「待执行」并说明缺口，继续可处理项。不要用助手总结替用户作证或绕过宿主直接改运行中的 SQLite。
4. 修改后按 ID 读回正文、层级、有效状态及变更成员，检查同源或同义错记是否仍生效。对新 ID、退役记录和跨回合纠正，沿最终保存的引用或维护回执查回原话，确认之后仍可追溯。过去正确的状态应能按历史查到，原本就错的派生事实还需核对历史召回是否继续把它当真。按需要用面板召回试探补验。最后回到用户明确指出的记录或场景，核对原问题和本次替代项的最终状态。记录已核验修改、待执行项目和缺失证据，后台入队、口头答应和一次搜索未命中都不足以确认修正生效。

改写、合并或撤销记录前，刷新目标状态，核对变更组成员和反向引用。涉及经历时，对仍引用该经历的普通事实，逐条复核主体、具体命题和长期用途，核对更正后的原话是否仍支持它们。检查与目标同源或同义的有效项，保留有依据的独有信息，并记录所需调整。修改后检查引用能否延续及正文是否一致。引用无法安全保全时，先保留相关记录并标明待执行。
